## 5. 差异与勘误（写给下游 worker）

1. **`obj+0x72C` / `obj+0x83E` 不在本表**：二者由外层 `0x51dbb4` 自己读（`0x51dbdc/0x51dbf0` 的 `movw`），
   文件落点 `0x5EA2..0x5FB4` / `0x5FB4..0x60C6`，语义 = 怪物击杀 / 捕获计数（137 x u16，`274 = 4 + 135 x 2` 亦通）。
   134 行之后还有 `[obj+0x950]` 表驱动的 552 B 变长块（怪物尺寸记录）。凡引用「134 行字段表」时不要把这三块算进来。

2. **重生成后的 `file_off` 已含循环补偿**：行 66/67 各被读 21 次（步长 60，只读 +0/+40），行 68/69 各 15 次；
   因此 134 个静态站点实际消耗 12,951 B（不是静态 size 之和 11,591）。
   旧文档里 128B 族「`char_off 0x408F..0x480E`」、288B 族「`0x33B7..0x3EF7`」是**修正前坐标**，现行值是
   `0x45DF..0x4CDF`（128B）与 `0x3907..0x4447`（288B）。`systems.md` / `quests.md` 引用的旧值需按 +0x550 平移。

3. **12 B 运行期位图的容量矛盾（待收口）**：`DEVELOP.md` / `quests.md` 说 `obj+0x35F0/+0x35FC/+0x3608` 是「按 questId 寻址」的运行时位图，
   但每槽只有 12 B = 96 bit，装不下 2048 个 questId。合理解释是 `0x523e44` 先做 `questId -> idx` 再按 idx 置位（即一个 96 项的工作集），
   或该三槽另有对象。**下游不要按 questId 直址写这个字段。**

4. **dirty 档在 68B 族上的 FF 涂块可以精确归因到编辑器旧版「猫装备解锁」写点**（本文新算，供复核）：
