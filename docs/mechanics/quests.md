## 核心机制

### 1. 任务分类与规模

| 池 | 条数 | 说明 |
|---|---|---|
| 村（Village） | 375 | 单机村任务，★1–★10 |
| 集会所（Guild/Hub） | 569 | ★1–★7 + G★1–G★4 |
| 特殊许可（Permit） | 228 | 18 只二名：12×16 + 6×6 |
| 斗技大会（Arena） | 17 | 全部在竞技场舞台 |
| 配信（Event） | 166 | DLC，不参与推进链 |

`quests.json` 只覆盖村+集会所 944 条，其 `keyType` 分布：`key` 118 / `urgent` 30 / `pre-req` 18 / `normal` 778。

`keyType` 语义（本文采用的实现口径）：

| 值 | 含义 | 实现用途 |
|---|---|---|
| `urgent`（紧急） | **该星级入口**：出现在上一星级关键任务全清之后，完成它才"开放"本星级 | 判定星级开放 |
| `key`（关键） | 本星级内必做任务；全清后触发下一星紧急 | 判定能否进下一星 |
| `pre-req`（前置） | 属于**其他村**的委托链任务，是某条关键任务的先决条件 | 只作依赖边，不是本村关键 |
| `normal` | 普通/高难度/配信式追加任务 | 不影响推进 |

### 2. 星级推进总规则（可直接编码）

```
初始：星级 1 开放（村★1 / 集★1 的"初始任务"直接可见）
对每个星级 N：
  若 urgent(N) 已 clear            → 星级 N 开放
  若 key(N) 全部 clear             → urgent(N+1) 出现
```

注意三点（wiki 明确写出的例外）：

1. **紧急任务挂在"新星级"名下**：如村★2 的「跳跃的不法者」是进入 ★2 的紧急，出现条件写「村★1的关键任务全部完成之后」。
2. **同星级内存在额外前置**：某些关键任务要求「本星级另外 N 个任务完成 + 与某 NPC 对话」或「某委托已受理」。见 §3/§4 表的"出现条件"列。
3. **非任务门槛**：HR、村贡献度、狞猛化任务计数、大型怪物狩猎数、二名许可等级。见 §5–§9。

#### 2.1 统一判定函数（把 §3–§11 的条件串归一）

```
IsAvailable(q):
  if q is entry_urgent:  return all_cleared(keys(q.tier - 1))
  if not TierOpened(q.tier): return false
  return AllPrereqs(q)          # 关键/普通一律适用

TierOpened(N):  return IsCleared(entry_urgent(N))

AllPrereqs(q) 的七类检查（与 wiki 条件串一一对应）：
  1. quest_done(list)          「村★N A B 完成之后」
  2. talk_npc(npc, after=list) 「…完成之后 <NPC>对话」
  3. request_active(name)      「委托★…」（委托未受理 → 任务不出现）
  4. hr >= n                   「HRn以上」
  5. contribution(village)>=n  「<村>貢献度 n 以上」
  6. hyper_count(scope) >= n   「集★6的狞猛化任务 n つ以上」
  7. large_monster_hunts >= 200「大型怪物200体以上狩猎」
```

> 注意 3 与 1 的**方向相反**：`request_active` 是"任务依赖委托"，而委托的完成条件又可能是该任务
> （§9.1）。实现时必须把"委托受理"与"任务 clear"视为两条独立状态，不能合并成一个布尔。

委托**不是每日刷新**，是固定编号链（2824 全表按 NPC 分组、编号递增）。
（MHXX 没有"每日任务"：带"每日"字样的只有白猫屋台的**每日抽奖**猫饭技能（2960/2505/2506），与任务解锁无关；
存档里的 `cQuestDaily` 是**任务定义结构**（含 mQuestType/mQuestLv/mListData[79] 等参数），不是"每日任务状态" `[未确认]`。）

```
NPC 委托N  ──受理──▶ 出现条件变为「委托★<该委托>」的任务（若有）
                     │
                     └─ 完成（任务 clear 或 納品 交纳） ──▶ 报酬 + 委托N+1 可受理
```

- 委托的「完成条件」可能是 **納品**（交素材）或**某个任务**。若是任务，该任务的"出现条件"就写「委托★…」
  ——形成"委托给任务、任务完成委托"的双向绑定（例：科科特村的村长的委托5 ↔ 村★5翠玉的闪电）。
- 报酬类型固定 8 类：`装备开放`（武器/防具系列）、`随从猫装备开放`、`狩技开放`（含 LV2/LV3）、
  `食材`（猫饭素材）、`入手`（道具/券/羽饰）、`任务报酬`（任务结算素材）、`ルームサービス変更可能`（房间服务/设施）、
  `龙历院点数` / `村貢献度 xxx pts`。

#### 9.2 村贡献度（贡献度）门槛

#### 9.4 委托链的结构性事实（实现要点）

- 每条链的编号是**顺序依赖**：N 未完成时 N+1 不出现（全表无条件列，按编号递增 + 星级递增可验证）。
- 同一 NPC 的链可以跨星级（例：科科特村长的委托 1→7 跨越 村★2/3/5/6/10）。
- 委托任务多数是**普通任务**，不在关键任务表里；但其中 3 条（村★5 的三个四天王任务）被列为关键。
- 委托受理后，任务才出现在列表；**只写任务 cleared 位而不置委托完成位**会出现"任务已完成但委托未完成"，
  反向则出现"委托已完成但任务未解锁" `[推断]`。

## 与存档的关联

> 本节坐标来自 `DEVELOP.md` / `docs/save-layout/CURRENT-RULING.md` / `member4-file-layout.txt`（权威），
> 以及 `editor-src/MHGU存档修改/OtherForm.cs` 的实际写点（可逐字节复算）。`char_off` = 猎人块内偏移。

### 1. 任务三态位域（唯一持久化任务状态）

| 位域 | 对象偏移 | 文件 char_off | 长度 | 语义 |
|---|---|---|---|---|
| cleared | `obj+0x42C` | **`0x2C77`** | 256 B = 2048 bit | 已 clear |
| seen | `obj+0x52C` | **`0x2D77`** | 256 B | 已解锁/已见 |
| achieve | `obj+0x62C` | **`0x2E77`** | 256 B | 语义未定 `[未确认]` |

- 位序：**LSB-first within byte**：`char_off = 0x2C77 + (bit >> 3)`，`mask = 1 << (bit & 7)`。
- 判定位号的两套坐标系（现行定案，swe2 复核）：
  - 存档位域按**记录序号 i**（1 起）寻址，写者 `0x51e6d8` 逐位 or；
  - 运行时位图 `obj+0x35F0/+0x35FC/+0x3608` 按 **questId** 寻址，`0x523e44` 置位，`0x524e58` 每次重建**只增不清**。
  - **M1 假设（采信）：i ≈ questId**，故实现上按 questId 操作位号。残留校验项：id946→`char_off` 11501 bit 实测。
- **不变量**：`cleared ⊆ seen`。旧编辑器只写 cleared 造成 501 个 `cleared=1/seen=0` 矛盾位 → NPC 判定器死锁。
  `seen=1/cleared=0`（已解锁未完成）是**合法态**。
- 运行时位图只增不清 ⇒ 在游戏运行中清位无效，**改档后必须重启**才生效。

### 2. questId 空间重建（决定位号怎么算）

`mhgu.db.quests.sort_order` 是唯一与游戏内顺序同构的列。由三处独立锚点可闭合出下表：

| 区间 | 内容 | 条数 | 证据 |
|---|---|---|---|
| 1 – 944 | 村 + 集会所任务 | 944 = 375 + 569 | `[推断]` 两条独立计数恰好闭合为 `quests.json` 的 944 条；945 视为空位/保留 |
| **946 – 1173** | **特殊许可（二名）** | **228** = 12×16 + 6×6 | `DEVELOP.md` 实测；`mhgu.db` Permit 228 行；sort_order 944–1171（偏移 +2） |
| **1174 – 1180** | **狩猎道场（Hunter Training）** | **7** | clean 档 seen 位命中 1174–1180 |
| 1181 – 1287 | 空白段（107 id） | 107 | `[推断]` 由 1288 起点减出；疑为 MHXX 期配信/Event 任务 |
| **1288 – 1304** | **斗技大会** | **17** | 编辑器 `chkBoxArenaQuest` 写 `char_off` 11544–11546 = bit 1288–1304；`mhgu.db` Arena 17 行（sort_order 1172–1188，偏移 +116） |

关键结论：

1. **斗技大会 id 不与二名连续**（1173→1288 之间隔 114），任何"按列表顺序线性推 id"的实现都会错。
2. 二名段可按 §8.2 的 1–18 顺序精确推出每个 id：旧 12 只 `id = 946 + 16*k + (level-1)`（k=0..11，level=1..16），
   新 6 只 `id = 946 + 192 + 6*(k-12) + (level-11)`（k=12..17，level=11..16）。`[推断，与 228 总数自洽]`
3. `quests.json`/`mhgu.db._id` 不可用于位号；必须用 `sort_order` 或自建表。

### 5. 实现任务解锁的正确顺序（含复合门禁）

```
1. 读 HR (char_off 0x28)；HR < 门槛 → 拒绝或同时抬 HR（否则双置仍不可接）
2. 计算目标位号 bit（§2 表；二名用 §8.2 公式）
3. 写 cleared |= bit，同时 seen |= bit（char_off 0x2C77+/0x2D77+ 同 bit）
4. 前置闭包：把该任务依赖链上的前置任务也置位（§3/§4 的"出现条件"列；委托型前置还需委托状态）
5. 复合门禁（判定器 0x525040 的第三输入）：
   - case11: [member#4+0x958] & bit20（猎人块内，可写）
   - case12: [mgr+0x3618] & 0x7F000（**另一管理器**，编辑器不可达）
   - case2/3/4/15: 等级字节（**另一管理器**）
   → 这几类"只双写任务位"仍不可接，必须另行满足等级腿
6. 关闭游戏 → 改档 → 重启（运行时位图 0x524e58 只增不清）
```

### 6. 本条域对编辑器的直接结论

- 只做「任务 clear」功能时，必须**双写 cleared+seen**，且**不得跨段**（二名区间首尾不得碰 944/945/1174）。
- 「解锁」语义应写 `seen=1, cleared=0`；「完成」语义写两者皆 1。两者不可混用（会造出引擎不产生的向量）。
- 星级推进**不能只置最终任务**：判定器按 questId 查位并叠加等级/委托腿，缺前置会"任务列表为空但不卡对话"。
- 斗技大会 17 位可安全按 1288–1304 整段置位（已与作者写点、DB 条数三方吻合）。
- 二名进度若同时存在"quest 位 + permit 等级块"，只写其中一套有风险；在 permit 块语义定案前，
  建议只写 quest 位并提示"进游戏后二名柜台可能不刷新" `[未确认]`。
