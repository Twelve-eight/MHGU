# 装备机制（武器 / 防具 / 装饰品 / 护石 / 随从猫）

MHGU（= MHXX 日版，机制同源）的装备数值模型与存档记录解码，面向存档编辑器 / 工具开发。
技能点阈值、装饰珠点数细则、猫饭技能见 `skills-arts.md`；任务解锁见 `quests.md`；本文只在装备侧引用。

**核心结论（一句话）**：存档只存「身份 + 等级 + 孔内珠子」，护石额外存两条技能 roll，操虫棍额外存猎虫养成；
攻击 / 防御 / 属性 / 斩味 / 技能点全部由装备表实时查出，存档里没有这些面板字段。

#### 1.2 家族—等级模型（存档武器 id 的关键）

武器表不是「一把武器一个 id」，而是 **家族（family）+ 等级（level）** 两级：

```
family   = class * 256 + familyIndex          # class 1..15，familyIndex 1..136
_id      = (class << 16) | (familyIndex << 8) | (level + 1)
level    = 0 起（显示 LV = level + 1）
```

反过来（JSON → 存档）：

```
class       = _id >> 16
familyIndex = (_id >> 8) & 0xFF
level       = (_id & 0xFF) - 1
saveType    = class + 6
saveID      = familyIndex
saveLV      = level
```

**实证**：`DEVELOP.md` 记录干净档装备箱首条为 `ee 00 2c 00`。
按 36B 布局解出：`type = 0xEE & 0x1F = 0x0E = 14`，`id = 0x002C = 44`，`LV = 0xEE >> 5 = 7`（`+1` 字节为 0）。
- type 14 → class 8 = 太刀；
- 太刀 familyIndex 44 → `familyId = 0x082C = 2092`；
- `docs/data/json/weapons.json` 中 family 2092 = **青熊薙** 一族（`_id` 535553–535560，等级 1–8，第 8 级 `final=1`）；
- wiki `text/1901.txt` 2628–2675 行同为 8 级：青熊薙 1–5 → 青熊长笔【留跳】6/7 → **青熊长笔【鲑兽戏画】8**（攻击 90/120/140/160/180/230/260/350）。

⇒ 存档记录 `(type=14, id=44, LV=7)` = **青熊长笔【鲑兽戏画】8（最终形态）**，三源（存档字节、JSON 家族、wiki 等级表）闭合。
`DEVELOP.md` 同处把 type `0x0E` 注为「锤」是笔误（0x0E=14=太刀）；按编辑器类型表与上式，锤的 type 是 9。

#### 1.4 武器树与最终强化

- 每个 class 的 wiki 树分 1/2 两页（盾斧 / 操虫棍只有 1 页）；树用 `┣ ┗` 画派生，节点 = 家族的一个等级。
- 节点标签：`[生产]`（可锻造）、`[购买]`（武具屋购入）、`[生产G]`（G 级起可生产）、`[XX]`（XX 新增）。
- 每一家族有且仅有一个 `final=1` 的最终形态（= 最大等级）；`text/2700`–`2713` 是「最终强化武器一览」，按期待值降序，可按属性筛选，**不是另一套升级系统**。
- 存档只存「家族 + 等级」，**不存派生历史 / 是否已解锁 / 强化材料**；因此只要 `LV01 < 家族等级数`（显示 LV ≤ 最大 LV），武器即合法。
- 派生/强化材料与解锁条件**不在镜像**；装备解锁由委托报酬驱动（`text/2953`，见 `quests.md` §10.2），存档层没有「装备已解锁」位。

统计：1585 个家族 / 1585 个最终形态 / 家族最大 15 级（5 bit LV 字段足够）。

`text/2700` 的表头写「期待值 / 攻击 / 性能 / 斩位(+2) / 孔槽」，但数据行在「性能」前有 **两个**期待值数字（如 `442+39` / `465+42`），文本镜像未说明两列的区别。例（大剑，按期待值降序）：

| 最终形态 | 期待值① | 期待值② | 攻击 | 性能 | 孔 |
|---|---|---|---|---|---|
| 咬剑【咆黄蛇】9 | 402 | 402 | 290 | 麻痹 42 | ◯ ◯ - |
| 壳剑赤钩爪8 | 442 | 442 | 320 | 防御 +20 | ◯ ◯ ◯ |

注意期待值可高于面板攻击（含会心/斩味/武器种系数），**不能用它反推攻击**；公式页未镜像。

#### 1.5 斩味

- 7 色顺序固定：红 → 橙 → 黄 → 绿 → 蓝 → 白 → 紫。
- JSON 的 `sharpness` 是 **3 段**，段间空格分隔，段内 7 个整数：
  1. 基础斩味；
  2. 匠+1（技能树 35 Handicraft 达 10 点，`Sharpness +1`）；
  3. 匠+2（同树 15 点，`Sharpness +2`）。
  依据：`docs/data/json/skills.json` 中 Handicraft(id 35) 的档位正是 10 → +1、15 → +2。
- 基础段各色求和范围 **15–45**（8721 条近战记录）；数值单位与游戏内点数的换算**镜像未说明**（见 §未确认）。
- **纯文本 wiki 的斩味列不可用**：每把武器渲染成两行、每行 45 个 `.`，颜色与填充长度在文本镜像中全部丢失；需要数值一律读 JSON。
- 存档不存斩味；斩味由 `(家族, 等级)` + 匠技能实时计算。

#### 1.6 属性 / 会心 / 防御 / 孔

- 属性值即 wiki 性能列（如 `火20`、`毒40`、`麻痹42`）；状态与属性共用 `element` 字段，用种类区分。
- 会心为百分数，可负（wiki `会心-70%`）；JSON 为字符串整数。
- 武器防御加成（`防御+10`…`+30`）是武器自带的独立加成，不属于防具防御。
- 孔数 0–3，wiki 记法 `- - -` / `◯ - -` / `◯ ◯ -` / `◯ ◯ ◯`。

#### 2.2 部位与 ID 空间

| 存档 type | 部位 | Kiranico `_id` 基址 | seq 范围（本数据集） | 件数 |
|---|---|---|---|---|
| 1 | Head | `0x140000`（20<<16） | 1..1282 | 1163 |
| 2 | Body | `0x150000`（21<<16） | 1..1286 | 1148 |
| 3 | Arms | `0x160000`（22<<16） | 1..1282 | 1117 |
| 4 | Waist | `0x170000`（23<<16） | 1..1282 | 1073 |
| 5 | Legs | `0x180000`（24<<16） | 1..1282 | 1136 |

即 `base = 0x13 + type`（`0x13` = 19；结果 `0x14..0x18`），`_id = (base<<16) | seq`；存档存 `seq`，也就是 Kiranico `_id` 的低 16 位（u16，≤1286）。JSON 的 `family` 字段逐项等于该低 16 位（head/body 全表 0 例外），可作为交叉校验。
`seq` 的解释为 **[推断]**：由 Kiranico 的「部位基址 + 自增序号」结构、`family == 低16位` 的自洽性、以及编辑器按 `(type<<16)|id` 查表（`EquipsForm.cs:481`）共同推出，尚无真实存档逐条对拍。

#### 2.3 强化与防御上限

- 防具可强化：初始 `defense` → 强化满 `max_defense`（wiki 列显示为 `初始 / 最大`，如 `122 / 160`、`12 / 62`）。
- 强化材料为铠玉系列（`text/2113`）：铠玉 / 上铠玉 / 尖铠玉 / 坚铠玉 / 重铠玉 / 真铠玉 / 王铠玉；各稀有度的等级上限由 `mMaxLvForLimit` 类表控制，镜像未给出逐稀有度上限 → 见 §未确认。
- 编辑器 UI 把防具 LV 限制在 1–20（`numUDnGuardLV.Maximum=20`），但存档字段是 5 bit（0..31），**UI 上限 ≠ 格式上限**。
- 稀有度 11（X / 二名）防具可带 4 条技能（含二名专属树与「真·二名」树），例：红盔头盔 `26/158`，技能 红盔+2 / 防御+2 / 体术+3 / 真·红盔+2。

#### 2.4 技能点与套装合计

- 每件防具提供 1–4 条技能点（引擎允许 5 槽，数据最多 4）：头/胴/腕/腰/脚各一条 `[0..4]` 数组。
- 5 件合计 + 护石 2 条 + 各孔装饰珠 = 每个技能树的总点数；达 ±10 / ±15 / ±20 档位发动（详见 `skills-arts.md` §1）。

- 负点合法（如海盗 J 系列 `反复无常 -2`），与装饰珠/护石负点同一套加法。

### 3. 装饰品

- **id = 道具 id**：`decorations.json` 的 `_id` 范围 **2638–2888**，共 **242** 条；`_id` 就是 36B 记录里 `beadID` 的值（u16，0 = 空）。

  `2717 2718 2720 2776 2788 2817 2839 2840 2843`。
  242 条实际装饰品 + 9 个空洞 = 251，**解释了 242 vs 251 的表面矛盾**。

## 与存档的关联

### 6.1 区段布局（槽数据 / `.hnt` 的 char_off）

`.hnt` = 槽数据裸拷贝，下列偏移对 `.hnt` 与 `system` 的槽块同样成立（`system` = 36B 头 + 3 槽块）。

| 区段 | char_off（dec / hex） | 大小 | 结构 | 闭合校验 |
|---|---|---|---|---|
| 猎人装备箱 | 25326 / `0x62EE` | 72000 | **2000 × 36B** | 25326 + 72000 = 97326 |
| 随从猫装备箱 | 97326 / `0x17C2E` | 36000 | **1000 × 36B** | 97326 + 36000 = 133326 |
| 套装名 / 预设 | 133326 / `0x208CE` | 5440 | **40 × 136B**（名 42B @+0） | 133326 + 5440 = 138766 = `0x21E0E` |
| 预设后连续块 | 138766 / `0x21E0E` | 2064 | 未解析 | — |
| 随从猫记录 | 146358 / `0x23BB6` | 27216 | 84 × 324B（`CatsForm`） | — |

三段恰好首尾相接（`0x62EE + 0x11940 = 0x17C2E`，`+ 0x8CA0 = 0x208CE`），是「装备箱 = 定长数组」的强证据。
装备箱单条：`addr(i) = 25326 + 36*i`，`i = 0..1999`；猫箱同理 `97326 + 36*i`，`i = 0..999`。

wiki 镜像只讲装备面板，不含存档字节语义；下表全部由 `EquipsForm` 的读写代码反推，并经 `DEVELOP.md` 首条记录 `ee 00 2c 00` 校验。

LV 拼接（5 bit，**低 3 位在 `+0` 高位、高 2 位在 `+1` 低位**）：

```
LV01 = ((b1 & 0x03) << 3) | (b0 >> 5)          # 0..31
b0   = ((LV01 & 0x07) << 5) | type
b1   = (LV02 << 2) | (LV01 >> 3)               # 防具
b1   = (LV01 >> 3)                             # 武器（LV02 被清零）
LV02 = b1 >> 2                                 # 防具幻化等级 0..63
```

### 6.4 id 换算（存档 ↔ JSON ↔ 名称表）

```
# 武器
class       = type - 6                      # 7..21 -> 1..15
familyIndex = id                            # u16 @+2..3
level       = LV01                          # 0 基
kiranicoId  = (class << 16) | (familyIndex << 8) | (level + 1)
familyId    = class * 256 + familyIndex

# 防具（type 1..5）
kiranicoId  = ((0x13 + type) << 16) | id    # id = seq @+2..3
# 幻化装备同理：fantasyId = ((0x13 + type) << 16) | (u16 @+4..5)

# 装饰珠
beadId      = 道具 id（2638..2888；251 格索引 = 2638 + 编辑器下标，含 9 个空洞）

# 护石技能
skillTreeId = u8 @+12 / @+13                # 与 skill_trees.json 的 _id 同一命名空间
skillPoints = sbyte @+14 / @+15

# 随从猫（Kiranico 侧）
palicoWeaponId = 0x100000 | seq
palicoArmorId  = ((0x11 或 0x12) << 16) | seq # 头 0x11 / 胴 0x12
```

例：`(type=14, id=44, LV=7)` → `class=8`，`_id = 0x80000 | 0x2C00 | 8 = 535560` → 青熊长笔【鲑兽戏画】8。

**名称表怎么造**：编辑器运行时读 `MHGU_weapon.txt` / `MHGU_guard.txt`，键是十六进制 `(type << 16) | id`（`EquipsForm.cs:255-278`）；
这两个文件不在仓库里，可按上式从 JSON 生成：
```
武器 key = ((class + 6) << 16) | familyIndex      # 值取该家族 LV1 的名字（后续等级会改名）
防具 key = (type << 16) | seq                      # 值取该件名称
```
注意武器是「家族 → 名字」，一个家族只有一个条目；等级名（如 青熊薙 1→8 的多次改名）不在键里。

### 6.5 护石记录（type 6）

- 读：`+2` 种类；`+12/+13` 技能 id；`+14/+15` sbyte 点数；`+16` 孔数。
- 写：`+0=6, +1=0, +2=种类, +3..5=0, +12..16=五字段, +17=0, +18=常量, +19=1, +20..35=0`；`+6..11` 的三颗珠保留。
- 点数可负（sbyte），编辑器 NUD 范围 −50..50；**不要钳到 0**（`skills-arts.md` §5 已定案）。
- 孔数 UI 上限 3。
- 技能 id 在编辑器里只加载 180 行（`MHGU_skill(uni).txt`），因此 UI 只能从这 180 个技能里选；其 id 不保证是 0..179 连续。`skill_trees.json` 有 205 棵树，181..205 多为复合/二名树，护石能否 roll 出未定 → §未确认。

### 6.6 操虫棍猎虫（type 20）

- `+12` insectType（1..31），`+13` insectLV（0..11，显示 +1）。
- `+14..21` = 8 项能力，0 基（编辑器显示 +1），按 UI 位置顺序：
  `力, 重, 速, 火, 水, 雷, 冰, 龙`（`EquipsForm.cs:370-392` 的 NUD 布局 + `:2470-2490` 标签）。
  前三项 UI 上限 20，后五项 37。
- insectType 的编码（编辑器映射，`EquipsForm.cs:728-770`）：
  - 1..11：`style1 = 0`（切断），`style2 = insectType`（1..11）
  - 12..22：`style1 = 1`（打击），`style2 = insectType - 11`（1..11）
  - 26..28：`style1 = 0`，`style2 = insectType - 14`（12..14）
  - 29..31：`style1 = 1`，`style2 = insectType - 17`（12..14）
  - 23：`style1 = 1, style2 = 15`；24：`0, 16`；25：`0, 17`
  - `style2` 的 18 项 = 「---- / 初始 / 力小 红攻击小 / 重小 绿复橙防小 / …」（`EquipsForm.cs:2438-2445`）
- 写回：
  - `insectType == 0` 时强制写 1；
  - `insectLV > 0` 且 `+27 != 3` 时写 `+27=3, +30=40, +31=20, +34=36`；
  - `insectLV == 0` 时把 `+22..35` 清零；
  - `insectLV > 0` 且 `+27 == 3` 时 **`+22..35` 原样保留**。
  这些默认值的语义未解码 → §未确认。

### 6.7 幻化（防具外观）字段

- `+4..5` = 幻化目标防具 id（同部位命名空间），`LV02`（`+1` 的 bit2..7）= 该防具的等级，显示均为 +1。
- 编辑器只为 type 1..5 提供幻化选择（`equipDict` 用 `eqmType << 16` 过滤，`EquipsForm.cs:1470-1474`），因此幻化不能跨部位。
- `+4..5 = 0` 表示无幻化。
- 武器记录写回时 `+4/+5` 与 `LV02` 一律清零；若武器也存在外观系统，该实现会丢数据 → §未确认。
- wiki 镜像没有幻化页，语义来自编辑器作者实现，[未确认]。

### 6.8 装饰珠字段

- 3 个 u16 @ `+6/+8/+10`，顺序即 UI 三个孔位；0 = 空。
- 存档不存「珠子占几孔」——由珠 id 查 `num_slots`；也不存「孔数是否够用」。
- 合法化需要：`Σ num_slots(beads) ≤ 装备孔数`，且珠的类别（通用/剑士/神枪手）与装备类别相容（后者 [推断]）。
- 护石同样有 3 孔，使用同一组字段。

### 6.9 套装名 / 预设（40 × 136B @ `0x208CE`）

- 每条 `+0..41` = UTF-8 名（42B，NUL 填充），其后 94B 为套装内容（编辑器不解析）。
- 编辑器每次保存都会重写全部 40 条名字（`EquipsForm.cs:1970-1975`），写前清空 42B 再写，超长截断。
- 套装内容（5 件 + 护石 + 珠子）的字段布局未解码 → §未确认。

### 6.10 随从猫装备箱（`0x17C2E`，1000 × 36B）

- 与猎人箱同构的 36B stride，容量 1000，恰好接到套装名块（`97326 + 36000 = 133326`）。
- 实测（`DEVELOP.md` / `DEVLOG.md`）：只有前 20 槽有数据，首三条
  `16 00 02 00` / `17 00 01 00` / `18 00 01 00`；其后到猫记录前约 48KB 全零。
- 三种解释：
  1. **（首选）猎人式 36B 记录**：type=22/23/24（猫武器/头/胴）、LV=0、id=2/1/1；
  2. `{u16 id, u16 count}` 的「猫道具列表」（id 22/23/24 + 数量）；
  3. `DEVELOP.md` 另一处称其为「装饰珠候选区」（按 `mEqDeco` 三孔联想）。
- 与名字表对拍：`cAcNyanterEquip` 声明 `mItemType[N]/mItemNum[N]` 共 **160** 项，而存档区容量 **1000**；
  两者可能是「160 个可见槽 + 其余扩展」或名字表只列了部分实例，未定。
- 编辑器未实现该区（0 覆盖），**不要写**。

### 6.11 当前装备栏（cAcPlayerEquip）

装备箱与「当前穿在身上的 7 件」是两个独立对象；后者由 `cAcPlayerEquip` 持有，引擎成员名（`name-dictionary.txt` @`0x155e943`）：

```
cAcPlayerEquip
  mSuperArtsX2Flag
  mWepType[0..]  mWepNo[0..]  mWepLv[1..]  mWepDeco1/2/3[..]
  mCustomAttr[0..]
  mSuperArts1[0..]  mSuperArts2/3  mAccSkillPoint1/2[0..]
  mInsId/Power/Speed/Lv/Tough/Fire/Elec/Water/Ice[0..]
  mEqNo[0..14]（观测下标）  mEqLv[0..]  mEqDeco1/2/3[..]
  mItemType[N]/mItemNum[N]（猫装备，0..159）
```

- 语义：每件装备 = `类型 + 编号 + 等级 + 3 珠`（+ 猎虫/狩技/护石技能点），与 36B 记录一一对应。
  `mWepNo`/`mEqNo` 到底是**装备 id** 还是**装备箱槽索引**尚未定案（`skills-arts.md` §未确认 #21 同项）。
- **char_off 未定位**：成员#4 的 134 行权威表只覆盖任务对象（`0x2C0B..0x5EA2`），不含这些字段；
  需在 `0x51dbb4` 之前/之后的其他 reader 中定位 → §未确认。
- 编辑器只改仓库，不改当前装备栏；改完仓库后需在游戏内重新穿脱一次，这是编辑器使用侧的已知限制。

### 6.12 编辑器写入行为

- 只写 `BeModifyData = true` 的记录；其余 36B 原样保留。
- 记录被修改时按 type 分支重写（见 §6.2 / §6.5 / §6.6），**未使用的字节被清零**：
  - 防具：`+12..35` 清零；`+4/+5/LV02` 按幻化写。
  - 武器（非猎虫）：`+4/+5` 与 `+12..35` 清零。
  - 护石：`+17..35` 重写（`+18/+19` 写常量，其余写 0）。
- 空槽（type 0）：仅当 `b0 > 0` 时清零整条；`b0 == 0` 的记录不触碰。
- 套装名：40 条全部重写（不是只写改动的）。
- 写回是整槽内存缓冲 → `system`/`.hnt` 全量写盘；存档**无校验和**（`DEVELOP.md` §校验和）。

### 6.13 开发校验清单（写装备前应做）

1. `type` ∈ {0..21}（22–24 仅猫箱）；type 6 走护石分支。
2. 武器：`class = type-6`，`id ≤ 该 class 的 familyIndex 最大值`（GS 136 / SnS 128 / Hammer 131 / Lance 126 / HBG 108 / LBG 109 / LS 125 / SA 108 / GL 114 / Bow 107 / DB 125 / HH 111 / IG 82 / CB 80），`LV01 ≤ 该家族最大等级-1`（≤14）。
3. 防具：`id` 与该 type 的 `seq` 空间匹配（≤1286）；`LV01 ≤ 31`（格式）且建议 ≤ `mMaxLvForLimit`（未解码）。
4. 幻化：`fantasyId` 必须属于同一 type；`LV02 ≤ 63`。
5. 珠子：`Σ num_slots ≤ 装备孔数`；珠 id ∈ 2638..2888 且非 9 个空洞；类别相容（[推断]）。
6. 护石：种类 0..10；技能 id ≤ 205；点数 sbyte；孔数 0..3；`+18` 按种类常量写。
7. 猎虫：`insectType` 1..31；`insectLV` 0..11；8 项能力在 UI 范围内（力/重/速 ≤19，元素 ≤36）。
8. 不要写猫装备箱 / 套装内容 / 当前装备栏（语义未定）。

### 6.14 字节模板（按 §6.2 公式生成）

```
# 武器：type 14 (太刀), id 44, LV 7（= 青熊长笔【鲑兽戏画】8）, 无珠
b0 = ((7 & 7) << 5) | 14 = 0xEE
b1 = 7 >> 3 = 0x00
b2 = 0x2C  b3 = 0x00
b4..b35 = 0
=> EE 00 2C 00 00 ...（与 DEVELOP 首条一致）

# 防具：type 1 (头), id 1, 强化等级 12（显示 13）, 无幻化, 无珠
LV01 = 12
b0 = ((12 & 7) << 5) | 1 = 0x81
b1 = (0 << 2) | (12 >> 3) = 0x01
b2 = 0x01  b3 = 0x00
=> 81 01 01 00 00 ...

# 护石：type 6, 种类 3 (骑士), 技能1 = 18 (Attack) -5, 技能2 = 0, 孔 2
b0 = 6  b1 = 0  b2 = 3  b3..b5 = 0  b6..b11 = 0
b12 = 0x12  b13 = 0x00  b14 = 0xFB (−5)  b15 = 0x00  b16 = 2
b17 = 0  b18 = 98 (0x62)  b19 = 1  b20..b35 = 0
=> 06 00 03 00 00 00 00 00 00 00 00 00 12 00 FB 00 02 00 62 01 00 ...
```

负点数用二进制补码存（−5 = `0xFB`），不是「符号位 + 数值」。
