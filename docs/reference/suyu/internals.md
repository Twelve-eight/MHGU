## Answers

### Q1 — how guest ARM32 is lifted, how blocks are split, what is a block start
- One C function per guest basic block, operating on `A32Context`; it ends by writing r15 (next block) and returning to a dispatcher (`a32_to_c.h:4-6`; `a32emit.h:73-84`). Instructions are emitted as C statements using `a32_*` helpers for flags/loads/VFP (`a32_runtime.h:22-42, 117-131, 179-320`). Code is compiled at `-O1`/`/fp:precise` per module (`a32emit.h:222-231`).
- Discovery is control-flow based, not linear: arm literal pools (~930 KB in MHGU main) would decode as garbage (`a32disc.h:1-15`). Roots: .text entry, `MOD0`→`.dynamic` (`DT_INIT/FINI`, STT_FUNC symbols, R_ARM_RELATIVE addends and ABS32/GLOB_DAT/JUMP_SLOT symbols pointing into .text), then every direct B/BL target met, then `push {...,lr}` prologue scans, then the boundary sweep the exporter runs at level 2 (`a32disc.h:184-232, 203-215, 250-260, 333-410`; `game_export.cpp:2314-2316`). Extra roots come from a previous run's `recomp_misses.txt` and shipped `coverage/<build id>.txt` (`game_export.cpp:1935-2000`).
- Literal pools are marked Data whenever a PC-relative load is seen, and a walk stops there (`a32disc.h:170-175, 216-224`).
- A **block start** is any address in `Discovery::block_starts`: module entry, exported function symbol, in-.text relocation target, branch/call target, switch-case target (relative table, `ldr pc,[pc,rX,lsl #2]` table, `add pc,pc,rX,lsl #2` ladder), computed-ladder step (compiler-rt division), prologue-scan/boundary-sweep function start, and runtime-miss/coverage-seed address (`a32disc.h:262-320, 333-410, 184-198`).
- **Splitting**: a block is translated while words are `Code` and no terminator appears; terminators = any instruction that can write PC (B, BX/BLX, LDM with pc, SVC, an untranslated word) (`a32_to_c.h:17, 51, 1795-1798, 1826`). A block also ends at the next recorded block start; if it falls through it stores that PC and returns (`a32emit.h:107-125`). Lookup is `a32_module_lookup(off)` = exact-match binary search over sorted module offsets (`a32emit.h:134-152`), fronted by a 64-entry direct-mapped cache (`arm_recomp32.cpp:1330-1345`). Static branch targets are chained directly via `A32_CHAIN` (budget 64) unless the target is hooked (`a32emit.h:81-105`; `a32_runtime.h:105-113`; `arm_recomp32.cpp:113`).

### Q2 — what runs a PC with no recompiled block, cost, runtime-written code
- dynarmic A32 (`ArmDynarmic32`), created lazily on the first uncovered PC (needs the process and exclusive monitor; otherwise `fallback_unavailable` → `HaltReason::PrefetchAbort`) (`arm_recomp32.cpp:1209-1225, 1352-1359`).
- Triggers: no block at PC; `ctx.thumb` (Thumb is never recompiled, `arm_recomp32.cpp:1318-1320`); `a32_unhandled` (`kHaltUnhandled`) for an instruction the lifter could not translate (`a32_to_c.h:1826`; `a32_runtime.h:129-131`); debugger single-step (`arm_recomp32.cpp:1394-1401`).
- Cost: one full guest-state marshal out and back per entry (`GetContext`/`SetContext`, `arm_recomp32.cpp:1229-1240, 1276-1281`), then up to `kMaxFallbackSteps = 4096` single-stepped JIT instructions (`:118-119, 1245-1265`); when the PC becomes covered again execution returns to native at once. A PC still uncovered after that is put in `long_regions` and its region runs on the JIT until it halts (`g_fb_full_runs`). Report counters: missing block / unhandled / Thumb, plus JIT steps / returns / full runs (`arm_recomp32.cpp:316-322`, `:772-777`).
- Code written into guest memory at runtime: executed **on the JIT** whenever the PC has no block, because the JIT fetches through suyu `Memory` (`arm_dynarmic_32.cpp:42-50`); a mod may therefore inject ARM (or Thumb) code (`forge_pc.h:212-215`; `forge-pc/README.md:207-211`; CHANGELOG.md:13-14). It does **not** affect an already-compiled block (Q5). [INFERENCE] a plugin's `mem_write` over code does not flush existing dynarmic translations: `Memory::WriteBlock` does not call `InvalidateCacheRange` (`memory.cpp:987-990`); only guest cache maintenance (`k_page_table_base.cpp:77-89`) and `ArmRecomp32::InvalidateCacheRange` → fallback do (`arm_recomp32.cpp:1409-1414`).

### Q3 — export pipeline
1. `OnExport`: work dirs, AOT cache written straight to its final path (`game_export.cpp:3860-3888`).
2. ExeFS input: packed NSP/XCI/NCA via VFS, **installed update preferred over base** (`game_export.cpp:1161-1175, 1211-1246`); a directory dump is copied from disk (`:3895-3908`). Needs own keys + base + 1.4.0 update (`INSTALL.md:97-101`).
3. Per module: flat NSO image → `Discover(sweep=2, misses+seeds)` → `EmitProject32` into `exefs/<mod>/` (`game_export.cpp:2307-2331`; `a32emit.h:1-15`).
4. Compile with CMake (MSVC/Ninja) into `recomp_static_<mod>` + one `a32_runtime_shared` (`game_export.cpp:2405-2534`; `a32emit.h:222-231`); a module that fails falls back to JIT and is logged (`game_export.cpp:2485-2494`).
5. Generate `exefs/recomp_registration.c`: module table in NSO load order (`game_export.cpp:2593-2627`; consumed by `suyu.cpp:99-116`).
6. Link: build tree target `suyu-cmd-static`, or in the prebuilt package the **link kit** — suyu-cmd's objects + all its libraries + `link.rsp`, produced by `make_link_kit.py` from a build configured with a stub module; the export only adds the game's registration object, module libs and one runtime lib and runs `link.exe`/`cc` (`game_export.cpp:1700-1755, 2665-2684`; `make_link_kit.py:1-14`; `BUILDING.md:105-127`). Success log: "Built single-file launcher with the link kit" (`game_export.cpp:2682`).
7. Package: `<game>.exe` (static launcher, icon embedded), `exefs/` + `romfs.bin`, runtime DLLs / `lib/`, `mods/`, `user/`, optional prewarmed shader cache; `aot_cache` removed after a successful link unless `SUYU_KEEP_AOT_CACHE` (`game_export.cpp:3002-3381, 3417-3420, 3359-3374`).
8. `user/recomp_report.txt`: per-run runtime report, rewritten every 30 s and at exit — module bases, static blocks/SVCs, JIT fallback counts, "unhandled instructions"/"missing blocks" tables with hit counts, module+offset, first-seen time and caller (BL site), guest profile (per-core busy %, per-module %, hottest 4 KB pages and blocks), host thread CPU (`arm_recomp32.cpp:308-336`). Previous file kept as `recomp_report.prev.txt` (`:993`).
9. Coverage: `coverage/<build id>.txt` = hex code offsets a play session found missing, made by `coverage_seeds.py` from `user/recomp_misses.txt`; the exporter adds the seeds of every module whose build ID matches as discovery roots, so a fresh export is as complete as one with play history (`coverage_seeds.py:1-11`; `game_export.cpp:1975-2000`; `BUILDING.md:136`; no game bytes: `RELEASE.md:24`). Separate, export-time "AOT coverage [mod]" log lines and the `a32cov` tool report lifter/discovery coverage (`game_export.cpp:2347-2367`; `a32cov.cpp:1-10`).

### Q4 — Forge / mod_host API
- Hook kinds: **pre** (CONTINUE / RETURN = skip function and return with r0/r1 or s0/d0 set / JUMP = continue at cpu->r[15], bit 0 = Thumb), **post** (runs when the function returns; may change the return value; args[0..3] = r0-r3 at entry, since 0.2 args[4] = caller LR, args[5] = SP so stack args are there), **override** (0.4: runs instead of the function; the original runs only through `call_original`). Order: pre → override → post once (`forge_pc.h:134-159, 261-281`; `forge-pc/README.md:100-122`; `loader.cpp:1470-1482`).
- **Only at block starts.** `hook_create`/`hook_override` return NULL unless `is_block(target)` ("hooks only work on function entries / branch targets") and then call `ModHostApi.mark` (`forge_pc.h:199-204`; `loader.cpp:585-588, 611`). Marking sets a bit in RecompHooks' one-bit-per-word bitmap that the generated code tests before chaining, so a chained branch to a marked PC returns to the dispatcher instead (`recomp_hooks.h:6-11`; `a32_runtime.h:71-80, 97-113`); the dispatcher's own filter is one bitmap test per block (`mod_host.h:46-58`; `mod_host.cpp:417-419`). Post hooks are implemented by setting LR to `MODHOST_RETURN_PC` and keeping a per-thread frame stack (`loader.cpp:1502-1511, 1379-1398`; `mod_host_api.h:47-48`). No mid-block hooking exists.
- Limits: 24 pre hooks and 8 overrides per address (`loader.cpp:1409`, `:85`); a hook breaks chaining for its target (`a32_runtime.h:109`).
- Guest memory: `mem_isValid/mem_read/mem_write/mem_ptr` on u32 guest addresses (`forge_pc.h:192-196`; `mod_host.cpp:139-158`), plus `mem_alloc/mem_free` over an exe-mapped RW guest heap (ABI v2) that game code can use as ordinary memory (`forge_pc.h:245-251`; `mod_host_api.h:143-153`; `mod_host.cpp:257-280`).
- Guest calls: `call` (and `call_original` for overrides), same game thread only, from `on_dispatch`/`on_game_start`; syscall or runaway fails and restores registers (memory writes stay); code without a block runs on the JIT; hooks don't fire inside (`forge_pc.h:206-217, 260-271`; `arm_recomp32.cpp:1065-1136`).
- Hot reload: plugin DLLs only. Forge loads `<name>.dll.<n>.live` copies, a watcher thread (or the menu's Reload) reloads a changed DLL between frames: drop hooks → wait for callbacks → `forge_onUnload` → load → `forge_onLoad`/`onInit`/`onImGuiInit`; `[plugins] hot_reload=false` disables; guest code a plugin wrote stays in memory (`forge_pc.h:44-52, 214-215`; `forge-pc/README.md:44-47, 215-216`; `loader.cpp:840-866, 1303-1306`). The loader DLL itself is loaded once by the exe and never unloaded (`mod_host.cpp:376-411, 441-446`; no `FreeLibrary`), so replacing forge.dll needs a game restart.
- Plugin path/lifecycle: `<exe>/mods/<title id>/<mod>/plugins/*.dll|*.so`, romfs beside it (`forge_pc.h:14-16`; `forge-pc/README.md:30-40`). Loader path = `game_settings.ini [Mods] loader`, default `Forge/forge.dll` (`Forge/forge.so` on Linux); "none" disables (`game_settings.h:65-70`; `mod_host.cpp:284-292`). The exe loads it before the game's first guest instruction, calls `modhost_attach`, then `on_game_start`; `on_frame` per finished frame; `on_present` per presented frame; `on_shutdown` at exit (`mod_host.cpp:376-446`; `mod_host_api.h:217-241`; `perf_stats.cpp:189`; `vk_present_manager.cpp:503`; `arm_recomp32.cpp:1205`).

### Q5 — consequence for game patches
- Writing guest code bytes does **not** change recompiled code: the instructions were lifted to C and compiled to x64 at export time, so immediates are literals in that C (MOVW → `c->r[D] = 0x0000IIII;`) and the backend drops instruction-cache invalidation for the static image (`a32_to_c.h:181-190`; `arm_recomp32.cpp:1409-1413`; `forge_pc.h:229-231`; `forge-pc/README.md:94-98`; `INSTALL.md:161-163`). Same statement for the AArch64 image: `arm_recomp.cpp:1256-1259`.
- Byte writes do change behaviour exactly where the JIT runs: uncovered PCs, Thumb, unhandled instructions, and code a mod loaded into guest memory (`forge_pc.h:212-215`; `arm_recomp32.cpp:1352-1359`; `arm_dynarmic_32.cpp:42-50`). [INFERENCE] not for translations dynarmic already made, since `mem_write` doesn't invalidate them (Q2).
- Emulating a `movw` immediate edit, in order of cost:
  1. Effect visible at a later block start → hook that block start and rewrite the register/memory there. This is the pattern the export itself uses for fps/aspect/render size (`game_settings.h:22-37, 353-368`; `forge_pc.h:134-142`).
  2. Whole-function replacement: `hook_override` (+ `call_original` for the unpatched path) (`forge_pc.h:273-281`).
  3. Instruction-level, when the `movw` address is a block start: pre hook returns `FORGE_HOOK_JUMP` with r15 = a stub in `mem_alloc` memory containing `movw rD,#new; b <movw+4>`; the stub runs on the JIT and execution returns to native at the next block start (bit 0 selects Thumb) (`forge_pc.h:140-151, 245-251`; `arm_recomp32.cpp:1352-1359`; `forge-pc/README.md:202-206`). If the `movw` is *not* a block start, the same stub must first reproduce the block's instructions up to the patched word.
  4. Permanent: patch the NSO and re-export — the exporter lifts whatever ExeFS it is handed (installed update or a directory dump) (`game_export.cpp:1161-1175, 3895-3908`); there is no `.pchtxt`/`.ips` support (`INSTALL.md:161-163`).
