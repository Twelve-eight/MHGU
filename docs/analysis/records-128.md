## 0. 方法与能力边界（先读）

本 sub-session 工具集 = `read/grep/glob/edit/write`，**没有 exec/eval**（与本批同侪一致，见
`member4-header.md` §0）。因此：

- **不能**新增反汇编、**不能** dump 存档字节。凡"指令原文"只引自库内已存在的转储
  `analysis/qp4/fn-*.txt`、`tools/r1.txt`。
- 但有两个**全 .text 机器索引**可当硬证据用（非人工读码）：
  - `analysis/movw-index.json` = 全 `.text` 的 `movw` 站点 `[vaddr, imm16, reg]`，**172,431 条**。
    （大偏移（>0xFFF）无法编码成 `ldr/str` 位移，`obj+0x2xxx` 只能由 `movw` 或 `add` 立即数构造，
    故该索引 = 该族的**完整代码侧引用集**。）

  - `quest/member4-file-layout.txt`（159 行 reader 序）+ `quest/member4-diff.txt`（clean/dirty 逐字段差分）
    = 已由主会话亲验的权威表。

### 2.3 与实测 FF 数的交叉校验（[M] `member4-diff.txt`）

"FF×N" = dirty 该字节 = `0xFF` 且 clean ≠ `0xFF`：

## 4. 【推测】语义判定

### 4.1 判定

> **本族 = 成员#4（任务/进度对象）内的"逐条结构化记录族"，语义落在"委托/任务记录"一侧；
> 不是奖章（勋章），不是特别许可（deviant）进度位图，也不是随从猫装备解锁位。**

分项与理由：

| 候选 | 判定 | 依据 |
|---|---|---|
| **委托/任务记录**（CURRENT-RULING/DEVELOP 现行标签） | **采信（中高）** | ①族在成员#4（任务/进度对象）内，文件序上紧接 68B 族（`0x404B → 0x408F`），代码侧与 36B 记录对（`0x2A0C/0x2A54`）由同一条 movw 序列依次构造 [M]；②`0x524AC0` 群（任务判定簇 `0x524E58/0x525040` 的紧邻函数）读 **rec0** 两次，同函数还读 `0x2A0C/0x2A54/0x27A8/0x2830` [M]；③15 条 × 128B、逐条 movw 走查 = 定长记录数组 [M]；④记录内有 u8/u16 粒度字段（`0x2E6A/0x2E8E/0x2AF9` 等非 4 对齐）[M]；⑤两档差分数与"进度填充"形态一致（i0..i6 有差、i11..i14 空）[M] |
| 奖章/勋章 | **否** | 勋章条件位是**另一族字段**：`obj+0xC28..`（char_off `0x3157..0x3167`，132 bit），编辑器 Medal01..06 就写那里 [S][M]。位置、容量、粒度均不符 |
| 特别许可（deviant）进度 | **否** | 特殊许可 = questId `946..1173`（**228 个 id**，12×16+6×6 实测）[库内 `quest/quest-table.md` §4]；228 个 id 的状态在 `obj+0x42C/0x52C/0x62C` 三态位图里。15 个槽装不下 228 个许可 |

- 半槽头 **4 字节**：`1F/1E` + 3 字节（槽 7 = `50 c0 f0`；槽 8/9 = `28 18 7e`）。
  `1F` 与 `1E` 只差 bit0 ⇒ 首字节是"类型/标志 + 少量计数位"的混合，**不是**独立 u8 枚举。
- 半槽体 **~20-24 字节**（`00 da 00 64 02 04 60 00 40 00 00 08 0c 00 bc 59 21 00 00 49`），
  其余到 68B 全 0。槽 8 与槽 9 的半槽 A 体**24 字节完全相同** ⇒ 同型记录。
- 与编辑器岛的对应：A1 从槽 7 的 `+0x00` 开始（洪水**正好盖住** `1f 50 c0 f0` 这个头），
  B1 从槽 8 `+0x00` 起、C1 从槽 9 `+0x00` 起 ⇒ **作者确实按 136B 槽的槽首对齐**，
  只是把"整槽 136B"当成"首 64-66B 才是内容"，并把 68B 半槽结构整个忽略。

**交叉验证（两个独立来源吻合）**：`0x6FCCE0` 窗口用的是 `obj+0x2AD4` 的 4 字节 stride 数组
（`{u16 id, u16 value}`）。而 `0x2AD4 = 0x2A78 + 0x5C = 136B 槽 0 的半槽 B（+0x44）再 +0x18`
——**正是上表推出的"半槽 = 4B 头 + `+0x18` 起的数据体"**。hex 与代码在这一点上独立互证。

### 7.3 i8/i9 "超算 FF" 的字节级定位（**已闭环**）

### 7.4 **族内真实网格 = 68B / 136B，不是 128B**（本轮最重要发现）

在 clean hex 里检索重复头：`28 18 7e` 只命中 4 处，且**全部落在 0x408F 起 68B 的整数倍上**：

| 位置 | 相对 0x408F | ÷68 | 头 4 字节 | 后续 |
|---|---|---|---|---|
| `0x44CF` | 1088 | **16** | `1f 28 18 7e` | `00 da 00 64 02 04 60 00 40 00 00 08 0c 00 bc 59 21 00 00 49 03 …` |
| `0x4513` | 1156 | **17** | `1e 28 18 7e` | `00 da 00 64 02 04 40 00 40 00 00 08 0c 00 04 00 …` |
| `0x4557` | 1224 | **18** | `1f 28 18 7e` | 与 0x44CF **前 24B 完全相同** |
| `0x459B` | 1292 | **19** | `1e 28 18 7e` | 与 0x4513 前 10B 相同后分叉 |

- `0x44CF` / `0x4557` 相差 `0x88` = **136B**；`0x4513` / `0x459B` 同样相差 136B；两组之间相差 68B。
- 1920B = **28×68 + 16**；= **14×136 + 16**。
- **编辑器 3 个岛的首地址 0x4447 / 0x44CF / 0x4557 全部落在 136B 网格上（槽 7 / 8 / 9）**，
  且每岛长度 63/57+9/65+1 ≈ **"136B 槽的首 ~64-66B"**。
  ⇒ 编辑器作者用的正是 **136B 记录模板**（与其 `EquipsForm` 136B 约定同源），而实际网格是 68B；
  于是每岛覆盖 "1 个完整 68B 半槽 + 下一个半槽的头部"。

**因此 §1.1 的"15 条 × 128B"只是存档/读写的**分块**（15 个 128B reader 调用，§1.2 那两组 15 站点），
不是语义单位。** 语义单位是 68B（=136B/2）槽，槽数 28（+16B 尾）。

### 8.2 语义定案（修订）

> **本族 = 成员#4 任务/进度对象里的一块"进度状态存储"（1920B），存在两种消费者视图：**
> **(V1) 按 `pos` 寻址的**位数组**（1 bit/pos，`pos` 由任务表查询 `bl 0x6aa9b8` 给出，含"前驱位成立
> 才置后继位"的条件传播）；**(V2) 按 136B 槽**（`1F` 半槽 + `1E` 半槽，体在 `+0x18` 起的 `{u16 id, u16 value}` 小表）。
> 它既不是"每条 128B 一条结构化记录"，也不是随从猫装备解锁数据。

置信度拆分（必须逐条看，勿合并引用）：

| 命题 | 置信 | 依据 |
|---|---|---|
| 属成员#4 任务/进度对象，非装备/非静态配置 | **高** | clean 空 / dirty 满（i0/i4/i13 在 clean 全 0、dirty 全密）+ reader 序位置 |
| 主体是**按位寻址的状态数组**（V1） | **高** | `0x520F80..0x520FFC` 的 `pos>>5` / `1<<(pos&31)` / `bic-orr-str` 原文 |
| `pos` 来自**任务表查询** | **高** | 同窗口 `bl 0x6aa9b8`（= 取任务记录，返回 `[sp,#44]` 的 u16 位号，`0xffff`=无） |
| 每项 **1 bit**（不是 2 bit） | **高（已闭环）** | `families-disasm.txt` 窗口 `0x520FC4..0x520FF8`：`ldr r1,[r1,r3=0x1f28]` → `mov r3,#1` → `tst r1, r3, lsl r2`（r2=`pos&31`）→ `and r0,r0,#31` → `movw r2,#0x2a78` → `ldr r2,[r1,r2]` → `orr r0, r2, r3, lsl r0` → `str r0,[r1,#0]`。掩码恒为 `1<<(pos&31)`，**无 `#3`/`lsl #1`** ⇒ 1 pos = 1 bit |
| 该处语义 = **"A 位图 → B 位图"的条件传播** | **中高** | 同上：先 `tst` `obj+0x1F28` 处的位，**只有该位为 1 才** `orr` 置 `obj+0x2A78` 的同一 pos（`beq` 跳过）。即"若前驱位成立，则置后继位" ⇒ 记录/派生关系，不是独立标志 |
| **15 个 128B 块 = 15 个"组"的独立数组** | **低（与 §7.4 冲突，已改判）** | 15 个独立 `movw` 起点是事实，但 136B 槽网格会把这 15×128B 切开，两者不能同时是语义单位 ⇒ 128B 更可能是**存档格式分块**；真正的"组数组"是 `0x27A8/0x2830` 那类（步长 204=3×68） |
| 每组有 3 个数组（cleared/seen/achieve） | **低** | 步长 68→204、288→864 都是 **3 倍**（支持三元组）；但 i0/i1、i0/i5 都不满足 seen⊇cleared ⇒ 三元的**排列/归属未定** |

### 8.4 仍未知（精确到下一步）

1. **"成对置位"现象的成因**：i0 的 dirty 只出现 2-bit 成对形状（`00/03/0c/30/33/3c/c3`），
   但掩码已确证是 1 bit（§8.2）。两种可能：(a) 该组的任务表把每个任务的 `pos` 分配成相邻两个
   （如 `2i`/`2i+1` 都算"达成"），(b) 存在"同一 quest 有 cleared+reward 两个 pos，且总是同时置位"。
   判据：dump `0x6aa9b8` 的返回表（组 id → pos 序列）看是否步长为 2。
2. **15 块的分组/三态归属**：需 `0x51E6D8` 尾部完整循环的组 id → 基址映射表（`mov r6,#50/51/52/53`
   之后的 `mla` 步长）。
3. **半槽头 `+0x04..+0x17`（20B）的含义**：`00 da 00 64 02 04 60 00 40 00 00 08 0c 00 bc 59 21 00 00 49`
   （槽 8 与槽 9 的这 24B 完全相同）。候选：8 个 u16（其中 `0x00DA`/`0x0064` 若按大端=218/100），
   或位打包字段组。判据：反汇编消费 `obj+0x2ABC/0x2B00` 的函数（下一个待 dump 目标）。
4. **dirty i8/i9/i10 高熵段**（如 `61 72 16 e9 eb c7 dd df`）是否为压缩/加密，还是多 bit 计数：
   若是压缩流，则本族其实是"压缩块"，§8.2 的主体判定需再改。
5. **位数组视图与半槽视图的对应**：`0x2A78` 的位消费者（`pos` 来自 `bl 0x6aa9b8`）到底落在哪个半槽的
   `+0x18` 数组里，两者是否同一编号空间——需一次内存 dump（游戏运行中读 `*(0x145159C)`）。

## 9. 【修订】编辑器建议（可写 / 禁写）

**结论不变且更强：本族整体禁写；`chkBoxCatArmsUnlock` 必须停用。**

新增理由（本轮证据）：

1. **槽对齐是对的、写区是错的**：作者按 **136B 槽**涂（0x4447/0x44CF/0x4557 = 槽 7/8/9 的槽首，✅ 对齐），
   但每个槽只写 **首 64 / 66 / 66 字节**（槽 7：A1 63 + A2 1；槽 8：B1 57 + C0 9；槽 9：C1 65 + C2 1），
   即 **半槽 A（`+0x00..+0x43`）几乎整块被写，半槽 B（`+0x44` 起的 68B）一个字节都没碰**。
   若该槽语义是"`1F` 半 + `1E` 半"两条子记录，则这是"涂了半条、漏了半条" ⇒ 必然造出
   **半新半旧的不一致记录**。
2. **写的是"位/2-bit 打包结构"而非"解锁标记"**：`0x2A78` 系按 `pos>>5`/`pos&31` 置位，
   且 clean 侧同一槽的半槽头（`1f 28 18 7e`）在 0xFF 洪水下被整字节覆盖 ⇒ 头里的类型/计数位一起变成全 1，
   与 `0x42C/0x52C` 洪水同型错误（"位域被全置"+"结构头被涂"两错叠加）。
3. **洪水还盖掉了 clean 侧唯一的"可读样本"**：clean 在 `0x4447`（槽 7 槽首）正好有 `1f 50 c0 f0 …`
   这段结构头，编辑器从同一地址开始涂 ⇒ 该槽在本档内**已无干净副本可对照**。
4. **不得暴露为可编辑字段**：语义仍停在"按组进度状态 + 半槽头未解码"层面（§8.2/§8.4），
   逐字段表未闭环。任何"可编辑"暴露都会让用户继续制造 0x440F..0x45DE 这类毁档。
5. **若将来必须提供"修复/移植"**：只允许**整段移植**（`char_off 0x408F..0x480E` 1920B，或按 **136B 槽整槽**
   复制），从干净参照档整块拷入；禁止按槽只写首 64B、禁止 0xFF 洪水、禁止跨半槽边界写。
6. **数据修复优先级**：dirty 档 `0x4447..0x45DE`（槽 7/8/9 = 3×136B）里被洪水覆盖的
   `0x4447..0x4485 / 0x44CF..0x4510 / 0x4557..0x4598` 已**不可从本档恢复**（clean 是低进度档，
   只能给出"低进度合法值"，不等于玩家原值）→ 若要走"位数组收敛"路线，只应在**位数组层面**做
   （如 `seen |= cleared` 同思路），不要试图重建半槽头。

## 11. 【已证实·跨族对照】编辑器抄的是**另一个族**的形态（对修复最有用的一条）

`families-dump.txt` 给出其它族在 **clean** 档的形态，与 128B 族对照后结论很硬：

| 族 | clean 侧形态（摘要） | 形态类 |
|---|---|---|
| **164B 对** `0x9D0/0xB18`（char 0x2FC7 / 0x306B） | `ff ff ff ff ff ff ff ff ff 3f 00 00 00 06 08 00 00 00 80 ff ff ff ff ff ff ff 07 …` | **FF 主导 + 定点清位** |
| **16B** `0xBDC`（char 0x311F） | `fc fc fc fc fc fc fc fc fc fc fc fc 0a a3 0b 00` | **FF 主导**（FC = FF 少 2 bit） |
| **20B** `0xC28`（char 0x3157，勋章写点） | `00 40 00 40 01 60 10 00 14 00 02 04 21 00 …` | 稀疏位 |
| **288B 族** | r0/r1/r2 全 0；r3..r9 稀疏 `30/33/0c` 形态 | 与 128B 族同形 |
| **68B 族** | r0/r1/r2/r5 全 0；r3/r4 稀疏 | 与 128B 族同形 |
| **128B 族（本片）** | i0/i4/i13 **全 0**；i7/i8/i9 只有小段结构（`1f …`） | **零主导，进度填充** |

**推论（高置信）**：编辑器 `chkBoxCatArmsUnlock` 的写法（**FF 洪水 + 定点清位 + 少量常量**）在形态上
只与 **164B / 16B 族**吻合（那两族 clean 侧本来就是 FF 主导），与本族（clean 全 0）**完全不像**。
⇒ 作者几乎肯定是从 **`obj+0x9D0 / 0xB18 / 0xBDC..0xC64`（char 0x2FC7 / 0x306B / 0x311F..）**那片
FF 主导区抄的向量，却按 `char_off 0x4447..` 写下去 —— **抄对了形态、写错了族。**

**对修复的直接含义**：
1. 本族（`0x408F..0x480E`）不是"解锁位族"，而是"**进度/派生位族**"（clean 空、dirty 满，
   且有 `if (A[pos]) B[pos]=1` 的派生关系，§8.2）⇒ 在此做"全解锁"语义上就不对。
2. 若真要实现"猫装备解锁"，应把目标改到 **164B/16B FF 主导区**，并在**整块移植**框架下做
   （clean 参照档那几段是完整可读的），而不是继续在 0x440F 段涂。
3. 本族若要"修复"，只能**整段移植 clean 的 1920B**（会带回低进度，但一致），或做位层面收敛。
