## 1. 状态与历史（`Q20`）

- 当前动作 = **两个字节**：`em+0x73E0` = state（0..17）、`em+0x73E1` = variant。
- `em+0x73E2` / `em+0x73E3` = **上一步**的 state/variant，各只有 1 个写点 → **GU 只存 1 步**。
  对照 MHRS：`_ActionTableHistory` **存 2 格，但黑名单只判 elem0**（见 `MHRS/.../Q9`）——
  所以 **有效历史都是 1 步，只是存储不同**（MHRS 2 格 / GU 1 格）。别把它读成"MHRS 能记 2~3 招"，也别把 GU 的"深度 1"当成"比 MHRS 少一半语义"。
- 连招数据 = EMC 加权树：`op02` = 百分比轮盘（`u16 % 100`），888/888 个块权重和 = 100。

## 2. 分派（`Q20` + `Q23`）

- 两级内联跳转表：L1 = 18 个 state（表基址 `0xcf1570`，18 项），L2 = 每个 state 自己的变体表。
- `(state,variant) → motion` 的映射**全在代码里**，没有 per-move 数据表可抄。
- 只有一部分 state 有可枚举的 L2 表：`default stub`（`b 0xca118`）、比较链、共享入口这几种没有。

（`0:255`、`1:255`，状态是 `out-of-range-variant`，游戏走 L2 默认分支）；其中 **333 行**能解析出 motion。
所以"有 motion 的比例"要用 **333 / 721**（不是 333/723），"没 motion 的"是剩下的表内格 + 那 2 个越界行，**不要用 723−333 当缺口数**。
**独立复算已回（2026-11-07，`Q29GuReachIndep`，自己写 ARM/EMC 解码器，不调用 `gu-moves.mjs`）**：
- **分母 = 721** `[C]`，逐 state 相加 `7+35+30+99+33+256+5+204+39+4+9`；
- **可达 = 236 个不同 pair** `[C]`，与工具一致；
- 两个口径提醒：① 若把 `(0,255)` 判为"走到结束动作"而不是"能排队"，诚实值是 **234**（它走 `0x76008` 而不是 setter；`(1,255)` 确实到 setter，是真的越界）；② 若把 state 8 的变体 0 也算进分母，分母变 **722**。
- **333（有 motion 的行）差 12：独立得到 321，且它解出的行里"工具没有的"是 0 行**——差距全在工具这边能解释的地方：
  5 行（state 2）+ 2 行（state 4）以**算出来的 `bx r1`** 结束（站点 `0x77470` = `b 0xafda4`），
  5 行（state 7）藏在内联 `add pc` 跳表 `0xd0736c` 后面（play 调用在 `0xd0748c/0xd074f0/0xd07544/0xd07588/0xd075b8/0xd07664`）。
  11 个表状态里 **8 个完全一致**；手解抽样 state 0（5/7）、state 9（5/5）、state 13（9/9）都与工具相同。
  → 所以"能出招的行"当前是 **321–333** 区间，工具那边偏多是因为它把内联跳表也算进去了（那些确实有 play 调用）。
  ~~残余 `[U]`：表驱动 play 的具体 id（`0x77470` 站点）~~ → **已解（2026-11-07，主会话）**：`0x77470` 的 `r1` 来自 `r12`，
  而 `r12` 在这个函数（起点 `0x77370`）里只由两条 `ldrh` 赋值：`0x773d8 ldrh r12,[r1,#48]`（+0x30）或 `0x773f4 ldrh r12,[r1,#32]`（+0x20），
  分支由 `[r0+0x336]` 的 bit 0x20 与 `r2` 的符号决定。⇒ **它是描述符里的一个半字字段**，不是表读、也不是算术产物。
  ~~另一条 `[U]`（"可达"是否该算引擎侧强制转移）~~ → **已解（2026-11-07，`Q43` + 主会话复核）：见 §8，236 是下限，加引擎侧强制转移是 257。**

**含义**：`表里有 = 玩家能打到` **不成立**。做"这招值不值得移植"的判断时必须用**可达集**，不是表大小（721）。
**可达集有两层**：EMC 树能排队的 **236**（下限），和含引擎侧强制转移的 **257**（§8）。筛选用 257，且**不得**因一格不在 236 里就剪掉它。
`--all-variants` 修完 off-by-base 后的 delta 我核过：键集合只多了 `10:204..210` 这 7 个，**没有别的 state 移动**
（`comm` 比对，0 个丢失键）；这 7 行都是 `l2-default`/未解析、全部 `no-motion`，所以 333 与 236 都不变。

## 4. 上一动作判断：不是"前置门"（`Q25-report`）

### 8.5 H1 已闭合：**存在第二个写入点**，不经 `0x76154`

`Q43` 把 H1 留成"未做"，而它正是本工作区栽过的那个坑（769 的 FlagWriters 只看了三个内联写入点，
漏掉通用写入者 `0xc2398`，结论"从不写入"被推翻）。这次先补上，**结论是有第二个写入者**。

**方法**：全镜像扫，不"顺着我知道的那个 setter 找调用者"——
① 全 `.text` 里所有 `movw rX, #0x73e0` / `#0x73e1`（1915 处）；
② 每条之后 12 条指令内、**用同一个寄存器做偏移**的 `strb rD, [rB, rX]`。
工具：`MHGU/tools/mhgu/h1-writers.mjs`。

**结果**：

| 写入点 | 字段 | 基址寄存器 | 说明 |
|---|---|---|---|
| `0x76868` | state | r9 | 已知 setter `0x76154` |
| `0x76870` | variant | r9 | 已知 setter |
| **`0xd9b1b4`** | **variant = 5（常量）** | r4 | **第二个写入点**，不经过 setter |

```
00d9b1ac: e30703e1  movw r0, #0x73e1
00d9b1b0: e3a01005  mov  r1, #5
00d9b1b4: e7c41000  strb r1, [r4, r0]     ; em+0x73E1 = 5
```

**它写谁**：所在函数 `0xd9b0b0(r0=em)` 开头 `movw r0,#0x1428; ldr r0,[r6,r0]!`——即
`[[em+0x1428]+…]` 那条链，与 `Q43` 认定的 `em+0x1428` 描述符一致，**r4 就是敌人对象**。
函数先虚调用 `[em]->[0x9c]` 拿一个枚举：`==22` 走一支，`==5` 走另一支，
**其余全部落到 `0xd9b1ac` 把 variant 强写成 5**（state 保持不变）。

**对数字的影响：对 em001 是 0 格（`Q44`，主会话逐条复核）**。

这条写入**不在 em001 的对象上跑**。链条是：

- 写入者 `0xd9b0b0` 在全镜像只有**一个**静态引用：`0xd9b02c b 0xd9b0b0`；
- 那个站点在函数 `0xd9ae84` 里，而 `0xd9ae84` 只被**一处指针**引用——`uEm017_00` 的 vtable 槽
  **`+0x204`**（`0x17b1054 = 0xd9ae84`，实测读出）；
- `uEm001_00` 的同一个 `+0x204` 槽是 **`0xcf0658`**（`0x179aefc`，实测读出），是它自己的处理器。

所以 `(state,5)` 经这条路径给 em001 增加 **0 格**，**257 对 em001 仍然成立**。
`gu-forced-cells.tsv` 依然只记录经 `0x76154` 的 21 格——不包含这条路径，因为它到不了 em001。

**`+0x1053` 的写入者：全镜像只有两个，且没有别名覆盖**（主会话扫描，2026-11-07）。
扫描覆盖 `movw` 后 10 条内的寄存器形与立即数形 store，要求地址区间**覆盖** `+0x1053`：

| 目标 | 覆盖它的 store |
|---|---|
| `+0x1053` | **2 处**：`0x6bbec`（setter 槽 `0xa0`）、`0x539b24`（基类构造写 `0xFF`） |
| `+0x1052` | 1 处 `STRB@0x539904`（只写 `0x1052`，**不碰** `0x1053`） |

三处都**逐条反汇编确认**过，不是只靠扫描：

```
0006bbe8: movw r2, #0x1053 ; 0006bbec: strb r1, [r0, r2]   <- setter 槽 0xa0
00539b20: movw r0, #0x1053 ; 00539b24: strb r1, [r4, r0]   <- 基类构造
005398fc: movw r0, #0x1052 ; 00539904: strb r5, [r4, r0]   <- 只写 0x1052
```

⇒ `Q44` 留的那条 `[U]`（"`0x1052` 处的 `strh` 可能别名到 `0x1053`"）**已闭合：不存在这种别名写入**。

**独立复现（`Q53c`，2026-11-07 晚，另一套扫描器）**：结果一致——byte store 到 `+0x1053` 仍然**恰好 2 处**
（`0x539b24` / `0x6bbec`），byte read 恰好 2 处（`0x6bbe0` getter + 1 个后来被证伪的 `0xd7b0a4`）。
它比本节多做的三件事，值得并进来：

1. **`0xd7b0a4` 是误判，不是读 `0x1053`**：原始字是
   `0xd7b098 movw r0,#0x1054; 0xd7b09c mov r10,r5; 0xd7b0a4 ldrb r3,[r10,r0]!` ⇒ 读的是 **`[r5+0x1054]`**（带写回），
   是隔壁那个字节。第一遍算出 `0x1053` 是因为窗口里有条 `mvn` 把 r10 污染成 `0xFFFFFFFF`。
2. **它另外列了一类本节没扫的形状**：word 大小、reg-offset 落在 `0x1050/0x1051`（4 字节访问会**覆盖** `0x1053`）的
   store 6 处（`0x12a3d50`/`0x9090e0`/`0x90a284`/`0x90a598`/`0xc592ac`/`0xc5b370`）、load 6 处——
   **只有当基址是 em 对象时才可能命中 `0x1053`**，基址全部未知，仍是 `[U]`。
   （注意这**不是**下面说的 `add rX,#0x1000; strb [rX,#0x53]` 形状；那种仍然没扫。）
3. **扫描器本身的两个坑**：跨过 `bx lr` 继续回放会继承上一条 stub 的常量（`0x6bbe0` 因此漏掉，加 barrier 后才找回）；
   带写回的 `ldrb/strb` 必须按写回后的基址算 EA。

⇒ 结论不变（写入者 2 个），但"全镜像无别名"这句话现在有**两套独立扫描器**支持；
剩下的 `[U]` 只有那 12 个基址未知的 word-size 站点。

**扫描器的两个误判形状**（都真的发生过，记下来以免重犯）：
① 带写回的 `strb`（`0xe7e2...`）被当成 `strh`——它写的是 `[r2+0x1119]`，与 `0x1052` 无关；
② 立即数形 store 不可能用到 `movw` 的寄存器，必须比立即数而不是"同寄存器"——否则 `str r0,[r4,#152]` 会被算到十条之前的 `movw #0x1052` 头上。
扫描边界：只认「`movw` 出偏移 + 同寄存器寻址」与「立即数偏移」两种形状；`add rX,#0x1000` 之后 `strb [rX,#0x53]` 这类没覆盖。

**它分支用的不是状态，是一个基类字节**：`[em]->[0x9c]` 解析到 `0x6bbdc`，实现只有三条指令——

```
0006bbdc: e3011053  movw r1, #0x1053
0006bbe0: e7d00001  ldrb r0, [r0, r1]     ; 返回 *(u8*)(this + 0x1053)
0006bbe4: e12fff1e  bx lr
```

⇒ **同一个字节在 18 个 state 下都一样**，所以"按 state 分类"这个问法本身不成立；它是全有或全无，
取决于 `em+0x1053` 的数据值（基类构造把它置 `0xFF`）。`[U]`：谁在运行时把 `0x1053` 改成 5 或 22
（已知只有 setter 槽 `0xa0 = 0x6bbe8` 和写 `0xFF` 的基类构造 `0x539b24`）。

**结论的边界**：这条路径对 **em001** 是 0 格；对 **em017** 它确实会强制 variant 5。
所以"存在第二个写入点"这个事实成立，但它**不是 em001 的**——引用 257 时要说"对 em001"。

**还有一个方向要分清**：`Q49` 另外找到几条写**越界 variant** 的路径——`0:7`、`0:8`、`0:9`
（state 0 的 L2 表 `max=6`）和 `5:40`（那个 state 根本没有 L2 表）。
这些写入是**真实的、会发生的**，但它们落到表的 **default 项**，而 §8.7 关于 `0:255` 的分析
已经证明 default handler 不播任何动作。所以它们**算「可达」但不算「有内容」**，
不计入 261 的内容格；把动作放在那里同样什么都不会播。
