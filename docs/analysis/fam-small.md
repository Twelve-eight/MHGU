## 结论速览（已证实 / 推测 / 未知）

### 【已证实】（有字节 / 反汇编 / 索引证据）
1. **3 槽一组律**：68B、164B、16B×2、20B、288B 五个族全部满足"每组 [A, 中, B]、中槽不落盘"，
   且每族"槽宽 × 3 × 组数"的族末与下一个落盘字段起点**逐字节闭合**（§1）。
2. **68B = `u32[id>>5]` 位图**：`0x520C6C and r1,r0,#31` → `0x520C74 mov r1,r9,lsl r1`（本片手工解码）
   → `0x520C78 add r7,r6,r7,lsl#2` → `0x520C80 ldr r6,[r7,#0x27a8]` → `biceq/orrne`（§2.3）。
3. **68B 的三个中槽真实存在且被消费**：`0x27EC` @`0x520CA4`/`0x73E8E0`、`0x28B8` @`0x520DCC`、
   `0x2984` @`0x520EF4`（§1 结论B）。
4. **164B A/B = 同一结构的两槽，且 B ⊆ A**：96 个可见字节逐位检验 `B & ~A = 0` 全成立；
   dirty 档两槽 164/164 字节完全相同；obj 间距 `0x148 = 2×0xA4`（§3.2）。
5. **`0xC28` = 勋章 132-bit 位域**：`0xC28`↔`char_off 0x3157`=12631 = 编辑器 Medal01 首字节，
   末写点 `12647` 只写低 4 位 ⇒ 132 bit；dirty 实测 `ff×16 + 0x0f` = **恰好 132 个 1**（§4.3）。
6. **`0xC50` = 同一 132-bit 域的第二槽**：clean 档与 `0xC28` **逐字节相同**，dirty 档保留真实数据（32 位）（§4.2/4.3）。
7. **尾部 3444B 静态引用只有 2 个站点**（`0x51DA98` writer / `0x51E5B0` reader）；`0x3684` 不可 `add imm12` 编码
   ⇒ 引用集完备（§0/§5.2）。
8. **四个假阳性已排除**：`0xA3DB14`（32 位常量拼装）、`0x162814` 群（160B 且与已落盘字段区间重叠）、
   `0x5412FC`（同型常量构造，§8.4a）、`0x295D84`（把 `0xC28` 当参数尾调用，§8.4b）。
9. **编辑器在成员#4 区段内的活写点只有 5 组**（`10251/10255/10263`、`11283..11328`、`11383..11546`、`12631..12647`；
   猫装备段已停用）；`char_off 11547..12630` 与 `12648..140426` **无任何写点** ⇒ `0x9D0/0xB18/0xBDC/0x3684`
   与委托/许可五项都**不在编辑器写入范围**（§6.3）。
10. **164B 对在整个 .text 里只有存档 reader/writer 两处引用**（`0xB18` 不可 `add` 编码 ⇒ 引用集完备）
   ⇒ **可证的"无 gameplay 消费者"**（§8.4）。同理尾部 3444B 也只有这两处。
11. **组步长 = 3 × 槽宽在指令层可见**：288B `mov r0,#864`+`mla`、68B `mov r3,#204`+`mla`；
   且同一 bit 用同一 mask 同时写进 A/中/B 三槽（§8.0）⇒ 三槽是**同位同步**维护。

### 【推测】
- 288B/68B 的中槽 = **同一位域上的第三份状态副本**（中高，§8.0：同例行/同位/同掩码，极性可能各自独立）；"为何只落盘 A 与 B"未知。
- 164B 的 A/B = "宽集 / 窄集"单调双态，A\B = 未确认差集（**中**，§8.2；无指令证据）。
- 20B 实体#2 的 132 bit 按 **6 个据点**分组（中；分组依据是编辑器复选框标签 [S]，非游戏侧证据，§4.3）。

  且位号由"按类别（50/51/52）的运行期表"给出（§8.0c）。

### 【未知】
- 四个族各自的 **id 空间与对应游戏对象**（68B 三组管什么、164B 管什么、20B 实体#1 管什么、3444B 是什么）。
- 164B 族的**实用位数与段边界**（容量 1312 bit，1-bit 已定但边界仍缺 dump）。
- **勋章 0xC28 的真实读取者**（唯一候选 `0x295D84` 已证伪，§8.4b）。
- 164B 与尾部 3444B 的 **gameplay 消费者**（已证"静态引用只有存档 I/O"，但间接指针无法排除）。
- dirty 档 164B 两槽"同值"、`0xBDC` 被灌 `0xFF` 的**写者身份**。

## §0 先解决一个方法论问题：`movw` 站点集何时是"完备引用集"

ARM32 的 `ldr/str` 立即数位移上限 0xFFF，装不下 `obj+0x2xxx` 级偏移；而 `add rX, rY, #imm` 只能编码
"8 位值循环右移偶数位"。因此：

| 偏移 | 可编成 `add imm12`？ | 结论 |
|---|---|---|
| `0x27A8` | 否（置位位跨 3..13，超 8 位窗口） | **movw 站点集 = 全静态引用集** |
| `0x3684` | 否（位跨 2..13） | **movw 站点集 = 全静态引用集** |
| `0xB18` | 否（位跨 3..11） | **movw 站点集 = 全静态引用集** |
| `0xBDC` / `0xBEC` / `0xC14` / `0xC28` | 否（位跨 2..12） | **movw 站点集 = 全静态引用集** |
| `0x9D0` | 是（`0x9D<<4`） | movw 集不完备——已实测走 `add r1,r5,#2512`（[D] 0x51DE4C） |
| `0x2940` | 是（`0xA5<<6`） | movw 集不完备——已实测走 `add r1,r5,#0x2940`（[D] 0x51D7B4/0x51E2CC） |
| `0xC50` | 是（`0xC5<<4`） | movw 集不完备（全 .text 0 个 movw 站点 ≠ 无人引用） |

该判据有两次正向实测（`0x9D0`、`0x2940` 都确实以 `add` 形式出现），可作为"引用集是否完备"的硬依据。

## §1 【已证实】贯穿四族的结构总律：3 槽一组、中槽不落盘

用 `member4-file-layout.txt` 的 obj 偏移做纯算术，四个族（外加已知 288B 族）全部满足**同一条几何律**：

```
一族 = N 组 × [ A槽, 中槽, B槽 ]，槽宽 = 该族单条尺寸；
A、B 落盘（各是一条 reader 记录），中槽永不落盘；
全族容量 = 3 槽的整数倍，且族末正好贴住下一个字段起点。
```

| 族 | 槽宽 | 组数 | 全长 | 族末贴住的下一字段 | 落盘的槽索引 | 不落盘的槽 |
|---|---|---|---|---|---|---|
| 288B（已知） | 0x120 | 5 | 15 槽 = 0x10E0 | 0x16C8+0x10E0 = **0x27A8** | 0,2,3,5,6,8,9,11,12,14 | 1,4,7,10,13 |
| **68B** | 0x44 | 3 | 9 槽 = 0x264 | 0x27A8+0x264 = **0x2A0C** | 0,2,3,5,6,8 | 1,4,7 |
| **164B 对** | 0xA4 | 1 | 3 槽 = 0x1EC | 0x9D0+0x1EC = **0xBBC** | 0,2 | 1（0xA74） |
| **16B（0xBBC 首）** | 0x10 | 1 | 3 槽 = 0x30 | 0xBBC+0x30 = **0xBEC** | 0,2（0xBBC/0xBDC） | 1（0xBCC） |
| **20B（0xBEC 首）** | 0x14 | 2 | 6 槽 = 0x78 | 0xBEC+0x78 = **0xC64** | 0,2,3,5（0xBEC/0xC14、0xC28/0xC50） | 1,4（0xC00/0xC3C） |
| **16B（0xC70 首）** | 0x10 | 1 | 3 槽 = 0x30 | 0xC70+0x30 = **0xCA0**（此后到 0x2A0C 无落盘字段；唯一不贴字段的族） | 0,2（0xC70/0xC90） | 1（0xC80） |
| 128B（已知） | 0x80 | 15 条 | 0x780 | 0x2A78+0x780 = **0x31F8** | 全 15 条 | 无 |

算术来源 [T]：68B 六条 obj 偏移 `0x27A8 0x2830 0x2874 0x28FC 0x2940 0x29C8`（相邻差
`+0x88/+0x44/+0x88/+0x44/+0x88` = 交替 2 槽、1 槽）；288B 十条相邻差交替 `+0x240/+0x120`；16B/20B 见上表。

**结论 A（已证实，几何层）**：这五族都不是"一整块位流"，而是"定长槽数组"，且**每组的中间槽不参与序列化**。
`128B 族没有这种中槽`（15 条紧排），这是它被认为是"结构化记录"、而上述各族被认为是"状态块"的几何分界。

**结论 B（已证实，代码层，仅 68B）**：68B 的三个中槽**确实存在于对象内存且被消费**——
`0x27EC` 的 movw 站点含 `0x520CA4`、`0x73E8E0`；`0x28B8` 含 `0x520DCC`；`0x2984` 含 `0x520EF4` [X]。
即"中槽 = 运行期槽（不落盘但被读写）"，不是布局空洞。

**结论 C（[I]，中高置信；§8.0 已升级为指令级证据，但仅限 288B/68B）**：中槽是**同一位域上的第三份状态副本**
（不是派生值；**"三槽恒等"未获证实**——每槽的置/清条件各自独立）。
依据：①它永不落盘却长期存在；②`0x520C7C` 之后 40 字节处就是 `0x27EC` 的位操作（[D]，见 §2.3），
同一函数对同一组 A/中/B 三槽做同型操作；③同族中槽地址只出现在 gameplay 函数里，从不出现在 0x51DC40
reader / 0x51D414 writer 序列中 [X]；④**§8.0 实测：组步长 `864=3×288` / `204=3×68`，同一 bit 位置用同一掩码写进三槽**。
"为什么只落盘 A 与 B"仍**未知**。**164B 族是反例（B⊂A，且根本没有找到更新器），不能外推。**

## §2 68B 族（obj+0x27A8..0x29C8，file **0x4447..0x45DF**；本节原写 0x3EF7..0x408F = 早 0x550 的旧坐标）

### 2.1 几何 [T]
- 落盘 6 条 × 68B = 408B = 0x198；file `0x3EF7 + 0x198 = 0x408F`（下一条 128B 族起点）精确闭合。
- 组划分：g0 `{0x27A8 / 中 0x27EC / 0x2830}`、g1 `{0x2874 / 0x28B8 / 0x28FC}`、g2 `{0x2940 / 0x2984 / 0x29C8}`。
- obj 与 file 不同序（file 0x3EF7 → obj+0x27A8，file 0x3F3B → obj+0x2830，**跳过 0x27EC**），
  因此"obj 相邻两条"在 file 里是"隔一条截断的槽"——**再次证明中槽不落盘**。

### 2.2 字节规律（`families-dump.txt`，每股 64B 头 + 32B 尾）
（注意：**68B 族的小节编号是 dump 里第二组的 r0..r5，char_off 0x3EF7/0x3F3B/0x3F7F/0x3FC3/0x4007/0x404B**；
第一组 r0..r9 是 288B 族，两者不要混读。）

| 槽 | obj | clean 侧 | dirty 侧（diff） | 读数 |
|---|---|---|---|---|
| r0 | 0x27A8 (g0.A) | **全 0** | 30B 非零，从 byte0 起：`c0 03 00 30 00 30 00 30 … 33 13 03 … c0 c0 … 31 00 1c` | clean 空、dirty 有内容 |
| r1 | 0x2830 (g0.B) | **全 0** | **46B 非零且从头就密**：`31 31 11 04 40 00 33 33 30 10 33 c4 …` | clean 空、dirty 稠密 ⇒ 不是"空槽" |
| r2 | 0x2874 (g1.A) | **全 0** | 仅 **8B** 非零（byte5=`08`、byte31=`02`、byte33..39=`30 10 00 10 10 30 10`） | 两档都近空，dirty 极稀疏 |
| r3 | 0x28FC (g1.B) | 稀疏但有形态：byte4/5=`11 01`、8..10=`03 31 03`、14=`30`、25..28=`30 33 03 03`、32=`03`、47..52=`30 30 00 30 30 10` | 54B 稠密（byte4 起，nibble 级全 3） | clean 有结构→dirty 饱和 |
| r4 | 0x2940 (g2.A) | 稀疏：byte25/29/33=`03`、37..38=`33 0c`、42=`03`、50=`01` | 50B 稠密，头起 `30 33 03 33 00 30 33 33 …` | 稀疏→饱和 |
| r5 | 0x29C8 (g2.B) | **全 0** | 48B 非零，**从 byte4 起**：`30 03 30 33 33 03 33 33 33 c3 00 0c …` | clean 空、dirty 稠密 |

字节层判定：

- **不是 u16/u32/f32 结构**：本批各族 clean/dirty 中都出现"跨 4 字节全 1 段"（如 164B 的 `f0 ff ff ff`，
  作 u32 即 `0xFFFFFFF0`/NaN），且 FF 游程止点落在**非 4 对齐**位置（164B 的 byte9 = `3f`）
  ⇒ 结构是**按 bit 打包的多段位图**，不是字对齐字段。
- 68B/288B 两族的 dirty 侧字节高度集中在 `0x30/0x33/0x31/0x03/0x0c/0xc3/0xcc` 这类取值上（偶见 `0x40/0x04/0xc4/0x1c`）。
  §8.0/§6.4 已判定这些是 **1 bit/项 的稀疏位图**（`lsr #5` + `and #31` + `1<<bit`），
  所以"nibble 只含 0/1/3"只是置位分布，不是小整数数组。
- 位宽已定：**1 bit / 项**（§6.4 用 `lsr #5`+`and #31`+`1<<bit` 判定，二轮补测）。
  r4/r5 的"非零从 byte4 起"与 r3 的"byte0..3 全 0"是槽内局部结构（前 4 字节可能是头/计数），**不足以判定字段类型**。

### 2.3 代码侧（本族的引用集是完备的，§0）
全 .text `movw #0x27A8` 只有 **8 个站点** [X]：
`0x29D364, 0x2A0780, 0x51D764, 0x51E27C, 0x520C7C, 0x524B14, 0x73E8C8, 0x73EC94`
（任务给的线索表就是这 8 个，逐个数值核对一致）。

1. **序列化对（读/写镜像）**——`0x51D764`（[D] 窗口：`movw r0,#0x27a8; mov r2,#68; add r1,r5,r0; bl 0x3df378`）
   与 `0x51E27C`（同型，`bl 0x3df2a8`）。两者前面紧邻
   `0x2448`(288B) / `0x2688`(288B)、后面紧跟六槽余下五槽再进 15×128B（[D] `0x51D7B4 add r1,r5,#0x2940`、
   `0x51D7C4 #0x29c8`、`0x51D7D8 #0x2a78`）⇒ **本族是成员#4 持久块里的数组，与 288B/128B 族同一条 reader 序列**。
2. **位操作消费者**——`0x520C7C`（[D] 窗口 0x520C54..0x520C90）：
   ```
   00520c6c: and r1, r0, #31        ; bit = id & 31
   00520c74: e1a01119  mov r1, r9, lsl r1   ; mask = 1 << (id&31)  ← 本片手工解码
   00520c78: add r7, r6, r7, lsl #2 ; word = obj + idx*4
   00520c7c: movw r6, #0x27a8
   00520c80: ldr  r6, [r7, r6]
   00520c84: biceq r6, r6, r1       ; 条件清位
   00520c88: orrne r6, r6, r1       ; 条件置位
   ```
   ⇒ **`obj+0x27A8` 被当作 `u32[id>>5]` 的位图使用**（按 id 置/清某一位），不是"带类型的记录"。
   紧随其后 `0x520CA4 movw r7,#0x27ec`、`0x520CCC movw r2,#0x2830` [X]，且 g1/g2 同型三连
   （`0x520DA4/0x520DCC/0x520DF4`、`0x520ECC/0x520EF4/0x520F1C`），最后 `0x520FEC #0x2a78`
   ⇒ 这个例行**逐组处理 A/中/B 三槽**，再转到 128B rec0。
3. **任务判定簇消费者**——`0x524B14`（`movw r1,#0x27a8`），同函数内还有
   `0x524AE8 #0x2a54`（36B 记录）、`0x524B44 #0x2830`、`0x524B84/0x524BB8 #0x2a78`（rec0 ×2）[D]
   ⇒ 读本族的函数与"36B 记录对 + 128B rec0"同处一段，且紧邻已知任务判定簇 `0x524E58/0x525040`
   （见 `records-128.md` §1.4 同结论）⇒ **本族在任务/委托判定链上**。
4. **三槽联动**——`0x73E8C8`(g0.A) / `0x73E8E0`(0x27EC) / `0x73E8F0`(0x2830)，`0x73EC94/0x73ECAC/0x73ECBC` 同型 [X]
   ⇒ 同一函数把 g0 的三槽一起处理（§8.0 已证实是"同位同步"，不是派生）。
5. **组步长 3× 与三槽同位同步（[D] §8.0，二轮补测）**：
   - `0x524B04 mov r3,#204`（=3×68）+ `mla` 后接 `movw #0x27a8` ⇒ **按组寻址，组步长 0xCC**；
   - `0x520C7C..0x520CE8` 一个循环里对 `0x27A8` / `0x27EC` / `0x2830` **用同一 mask 同一条件**各做一次
     `biceq/orrne` + `str`，循环上界 `cmp r4,#384`；
   - `0x524A80` 起是一组"逐族同构的 bit-test helper"：288B 用 `mov r0,#864` + `movw #0x1908`，
     36B 记录用 `#0x2a0c`/`#0x2a54`，68B 用 `mov r3,#204` + `movw #0x27a8`。
6. **位号来自运行期表，不是数组下标**：`0x520CEC..0x520D5C` 把类别号 `50/51/52` 存进 `[sp,#52]` →
   `bl 0x6aa9b8` → 取回 `ldrh [sp,#44]`，与哨兵 `movw r5,#0xffff` 比较，相等即跳过
   ⇒ 位号由"按类别的表"给出，`0xFFFF` = 表尾。与 `CURRENT-RULING` 修正18 的任务表机制同型 [D]。

### 2.4 语义判定
> **本族 = 成员#4 内的"按 id 位图"状态数组：3 组 × 2 张持久位图（各 68B = 544 bit）+ 3 张运行期同尺寸影子位图。
> 具体游戏对象的 id 空间未知。**

- 置信度：**"位图 + 分组 + 影子槽"= 高**（[D] 位操作指令 + [T] 几何 + [X] 引用集完备）；
  **"位图管什么（任务/委托/实绩/其它）"= 未知**。
- 支持"任务/委托侧"的弱证据：`0x524B14` 与 36B/128B 记录族同函数（§2.3.3）。
- 反证"勋章"：勋章已定案在 `obj+0xC28`（§4），本族位置/容量都不符。
- 反证"两槽互为镜像/同步增长"：clean 档 g1.A(`0x2874`) 与 g2.B(`0x29C8`) **全 0**，而同档 g1.B(`0x28FC`)、
  g2.A(`0x2940`) 有稀疏内容 ⇒ A/B 可各自独立为空，**不是 §4 勋章那种"两槽逐字节相同"的镜像**。
- 本族**没有** §3/§4 那种可验证的 A⊇B 位包含关系（clean 侧两槽都近空，样本不足以检验）⇒ 双态方向未知。

### 2.5 处置建议：**禁写（硬）**
1. 语义未定，且是位图：按偏移涂 `0xFF` 必然把 544 bit 全部置 1，等价于"对该 id 空间的每一项都打勾"，无合法性保证。
2. 即使要写，也**必须同位置双写 A 与 B 并保持 A⊇B**（§4 的 B⊆A 规律），否则造出与 0x42C/0x52C 同类的矛盾向量。
3. 中槽（0x27EC/0x28B8/0x2984）**从不落盘**，写它既不会保存、也会破坏运行期派生值 → 永不可写。
4. 编辑器现无任何写点落在 `char_off 0x3EF7..0x408F`（[S]：活写点上界 12647，17479 段已停用）⇒ 现状无风险，**保持**。
5. 若将来要开：唯一可接受的做法是整族 **A/B 双槽同步移植**合法档向量（本族 6×68B = 408B 连续块，file 0x3EF7..0x408F），
   不接受"按位/按段涂"。

### 2.6 未知
- 3 组各对应哪 3 个对象（候选：任务类别 / 据点 / 等级段；**无证据**）。
- 544 bit 的 id 空间与位序（低位在前已由 `and #31` + `lsl` 证明是 LSB-first 字内位序）。
- A 与 B 的语义差与包含方向（§2.4：clean 侧 g1.A/g2.B 全 0 而 g1.B/g2.A 有内容 ⇒ 非镜像，但样本不足以定方向）。
- `0x29D364`（0x29D2xx..0x29D7xx 函数）与 `0x2A0780` 两个函数的用途：它们对槽内 **word 粒度**偏移
  （`0x27A8/0x27AC/0x27B0/0x27B4`、`0x2830/0x2834/0x2838`、`0x28BC/0x28DC/0x28F4`、`0x2908/0x290C/0x2910`）
  逐个访问 [D r1.txt]，像"遍历/校验"，但缺该函数反汇编，**判不了**。

## §3 164B 对（obj+0x9D0 @file 0x2FC7 / obj+0xB18 @file 0x306B）

### 3.1 几何 [T]
| file | obj | size | 备注 |
|---|---|---|---|
| 0x2FC7 | +0x9D0 | 164 | A 槽 |
| 0x306B | +0xB18 | 164 | B 槽 |
| （无） | +0xA74 | 164 | 中槽，**不落盘** |

- file 侧 A、B 紧邻（`0x2FC7 + 0xA4 = 0x306B`）；obj 侧相距 `0x148 = 2 × 0xA4` ⇒ **中间正好夹一个 164B 槽**。
- 族末闭合：`0x9D0 + 3 × 0xA4 = 0xBBC` = 下一条落盘字段（16B）起点，一字节不差 [T]。
- 该 164B 槽**不是**编辑器"任务Clear"那 164B（那是 obj+0x42C 这个 256B 数组的**前 164 字节**，file 0x2C77 起）
  ——两者只是长度恰好都是 164B，**不要混**。

### 3.2 字节规律：B ⊆ A（单调包含），dirty 侧两槽同值
clean 侧逐字节比对（`families-dump.txt`，头 64B + 尾 32B，共 96/164 可见）：

```
A(0x9d0) clean: ff×9 3f | 00 00 00 06 | 08 00 00 00 | 80 | ff×7 07 | 00×13 | f0 ff ff ff 03 | 00×15 | f0 ff ff ff
B(0xb18) clean: 22 2b 3f×8 | 00 00 00 00 | 08 00 00 00 | 80 | cf×7 07 | 00×13 | 90 9f 9f 9f 03 | 00×15 | 70 7e 7e 7e
```
（竖线标出的是两槽**完全相同**的骨架字节：`08 00 00 00 80`、`07`、尾 32B **逐字节相同**。）

逐位检验 **B & ~A = 0**（即 B 的每一位 A 都有）：
`0x22,0x2b,0x3f… ⊂ 0xff`；`0xcf ⊂ 0xff`；`0x90 ⊂ 0xf0`；`0x9f ⊂ 0xff`；`0x70 ⊂ 0xf0`；`0x7e ⊂ 0xff` —— **96 个可见字节全部成立**。
⇒ **B 是 A 的位子集**（A 覆盖面更宽），不是两张无关的图。

A clean 的置位呈"长游程 + 非字节对齐尾"：`ff×9+3f`（78 bit 连续 1）、`ff×7+07`（59 bit）、
`f0+ff ff ff+03`（30 bit，从 byte40 的 bit4 起）、`f0+ff ff ff`（28 bit）。
`0x3f/0x07/0x03` 这种"低位满、高位 0"的尾巴只可能出自**按 bit 打包的多段位数组**（每段长度非 8 的倍数），
不可能是 u16/u32/f32 数组（跨 4 字节的 `f0 ff ff ff` 作 u32 是 0xFFFFFFF0）。

dirty 侧：A 与 B **逐字节完全相同**（164/164），形态为"低位大面积置 1 + 骨架字节不变"：
`ff×9 bf | 02 04 00 96 20 | 00 00 00 80 | ff×7 07 | 00×13 | f0 ff ff ff×5 … f7 ff ff ff`。
两个独立槽同时取同一组值，且骨架（`80`@18、`07`@26）与 clean 一致 ⇒ 这是**同一结构的两份实例**（同字段模板），
且**非全 1**（byte9=`0xBF`、byte10..14=`02 04 00 96 20` 都不是 FF，见 §8.3 的措辞边界），
不是"编辑器涂 FF"（涂 FF 会连 `80/07/尾 32B` 一起变，且源码无此写点，见 §6.3）。

### 3.3 代码侧
> 先排除两个**误归属**，否则语义会被带偏：

**(a) `0xA3DB14` 是常量构造，不是字段引用**（[D] `qp4/fn-a3da50.txt`）：
```
00a3db14: movw r1, #0xb18
00a3db18: ldr  r2, [r0, #340]
00a3db1c: orr  r1, r1, r3, lsl #16   ; 拼 0x????0b18
00a3db20: str  r1, [r0, #344]
```
`movw` 只是 32 位立即数的高/低半拼装，访问的是 `[r0,#344]`。⇒ **从 164B-B 站点表删除**。

**(b) `0x162814` 群（0x162814/0x162A68/0x162D2C/0x162FE4/0x163368/0x1635C4/0x1638F0）不能归属成员#4**：
[D] `0x1627FC movw r0,#0xbb8; add r7,r6,r0` / `0x162814 movw r0,#0xb18; mov r2,#160` / `0x162820 mov r0,r7; mov r1,r5`
是"obj+0xB18 ↔ obj+0xBB8 各 160B 互拷"，且整函数里同型代码重复 7 次（站点间距 0x25C..0x384，不等距）。
若 r6 = 成员#4 obj，则 `0xBB8 + 0xA0 = 0xC58` 这一区间与成员#4 **已落盘的 8 个字段**
（`0xBBC/0xBDC/0xBEC/0xC14/0xC28/0xC50` + 中槽 `0xC00/0xC3C`）**重叠** —— 不可能。
且这些拷贝用 160B 而成员#4 的该字段是 164B。⇒ **该函数作用于另一个对象（同偏移的另一实例/类），是"同常数不同对象"的假阳性**。

> **§8.4 二轮补测：剩下两个候选也被证伪** —— `0x5412FC` 是 `movw r1,#0xb18 / orr r1,r1,r3,lsl#16 / str r1,[r0,#344]`
> 的**常量构造**（与 0xA3DB14 同型），`0x5429C8` 同签名、高度可疑同型（无该段反汇编）。
> ⇒ **真正可归属的引用只有 `0x51D344`（writer）与 `0x51DE5C`（reader）两处**，即可证的"无 gameplay 消费者"。

**(c) 序列化上下文**（[D] `0x51DE5C` 窗口）：
```
0051de4c: add r1, r5, #2512   ; = obj+0x9d0（注意：走 add 形式，故 movw 集里查不到 0x9d0）
0051de54: mov r2, #164 ; 0051de58: bl 0x3df2a8   ; 读 A
0051de5c: movw r0, #0xb18 ; mov r2, #164 ; add r1, r5, r0 ; bl 0x3df2a8   ; 读 B
```
writer 侧（0x51D3xx）同型：`0x51D344 #0xb18`，前后 `0x51D358 #0xbbc(16B)`、`0x51D36C #0xbdc(16B)`。
⇒ A/B 在同一条 reader/writer 序列里**相邻落盘**，两者都是"整块 164B 搬运"，无逐字段访问。

### 3.4 语义判定
> **164B 对 = 同一结构的两个持久槽（A @0x9D0、B @0xB18），加一个不落盘的中槽 @0xA74；
> 内容是 1312 bit 的按 bit 打包状态（多段位数组）；A ⊇ B 单调。具体对象未知。**

- **"同一结构的双槽"：高置信（已证）**。证据：①B ⊆ A 的逐位单调关系不可能出现在两个无关结构上；
  ②dirty 档两槽 164/164 字节完全相同；③clean 档两槽的骨架字节（`08 00 00 00 80`/`07`/尾 32B）逐字节相同；
  ④obj 间距恰为 2×164、族末 `0x9D0+3*164=0xBBC` 与下一字段闭合；⑤同一 reader 相邻读两个 164B。
- **"A/B 是两种状态（而非镜像副本）"：高置信**。clean 档 A≠B 且 B⊂A；若是镜像拷贝必须相等。
- **具体状态语义（"见过/达成"之类）：[I] 中低置信**。B⊂A 与"已达成 ⊆ 已见过"同构，但**没有任何指令级证据**
  证明哪一个被哪段代码当门槛；且本族**完全没有 gameplay 消费者**（§8.4 已证），所以"谁用它做判定"暂时无解。
- **dirty 档两槽完全相同：等价于 "A\B = ∅"**（§8.3）。它**不是**镜像机制的证据，但"无条件镜像"已被 clean 档排除
  （clean A≠B）。两槽同值的来源（差集自然为空 / 同位同步写 / 外部整块改写）仍**未定**（非编辑器，§6.3）。

### 3.5 处置建议：**禁写（硬）**
1. 语义未定 + 1312 bit 位图 ⇒ 涂 `0xFF` = 一次性把 1312 个 id 全打勾，且会同时破坏 A⊇B 不变量。
2. 若将来要写：必须 **A/B 双写且保持 B ⊆ A**，并且**只能整块 164B×2 从合法档移植**；
   中槽 0xA74 永不可写真值（不落盘，写它等于给运行期塞脏派生值）。
3. 编辑器现无写点落在 `char_off 0x2FC7..0x310F`（[S] 活写点上界 12647，17479 段已停用）⇒ **现状安全，保持禁写**。

### 3.6 未知
- 1312 bit 各段的分段边界（只能看到 4 段游程止点 `0x3f/0x07/0x03`，其余段在未 dump 的 64..131 字节里）。
- `0x5429C8` 是否与 `0x5412FC` 同型常量构造（缺该段反汇编，[I] 高可疑；§8.4a）。
- 中槽 0xA74 的派生规则：`movw #0xa74` 有 12 个站点（`0x846FF8 / 0xBE6A08 / 0xCD2FF8 / 0x1220A64…`），
  全部落在 0x84xxxx 以上区域，**无一落在成员#4 的 0x51D/0x51E 序列**⇒无法确认它们属于本族（同常数不同对象的可能性高）。
- 该 164B 结构与 §4 的 20B/16B 结构同处 `0x9D0..0xCA0` 这一段、按尺寸递增排列，**是否属于同一"收藏/图鉴"体系：未知**。

## §4 20B 族（obj+0xBDC..0xC64，file 0x311F..0x317F）

### 4.1 几何：**不是"某物的 5 条记录"**
按 §1 的 3 槽律展开（[T] 偏移 + 算术）：

```
0xBBC(16B, file 0x310F)  [中 0xBCC 不落盘]  0xBDC(16B, file 0x311F)   ← 16B 实体#1 的 A / B
0xBEC(20B, file 0x312F)  [中 0xC00 不落盘]  0xC14(20B, file 0x3143)   ← 20B 实体#1 的 A / B
0xC28(20B, file 0x3157)  [中 0xC3C 不落盘]  0xC50(20B, file 0x316B)   ← 20B 实体#2 的 A / B（= 勋章）
0xC64(4B, file 0x317F)                                             ← 下一个字段（只有 I/O 引用）
```
- `0xBEC + 6 × 0x14 = 0xC64` 精确闭合；`0xBBC + 3 × 0x10 = 0xBEC`、`0xC70 + 3 × 0x10 = 0xCA0` 同样精确闭合 [T]。
- **尺寸不齐**：本族 5 条落盘记录 = 1×16B + 4×20B。16B 的那条（0xBDC）不是 20B 记录，而是"16B 实体#1"的 B 槽
  （其 A 槽 = 0xBBC，file 0x310F，不在本次清单里）。
- ⇒ **"5 条同型记录"这个读法不成立**；正确读法是 **2 个 20B 实体 × A/B 双槽，外加 1 个 16B 实体的 B 槽**。
  即：本族不是数组，是一个"每种被计数对象一张位图"的清单，每条尺寸按该对象的条目数定。

### 4.2 字节规律（三对 A/B 的对照）
**(1) 0xBDC（16B，实体#1 的 B）**
```
clean: fc fc fc fc fc fc fc fc fc fc fc fc 0a a3 0b 00     (popcount 81)
dirty: ff ff ff ff ff ff ff ff ff ff ff ff ff ff 1f 00     (popcount 117)
```
前 14 字节 **`clean | 0xFF == dirty` 逐字节精确命中**（`0xFC|0xFF=0xFF` ×12、`0x0a|0xFF=0xFF`、`0xa3|0xFF=0xFF`），
第 15 字节 `0x0b`→`0x1f`（多置 bit2/bit4）、第 16 字节 `0x00` 不变。
⇒ **dirty 档该字段被"按 14 字节灌 0xFF"的第三个写者碰过**（不是本编辑器，见 §6.3），并另有 2 个 bit 的改写。
clean 的 `0xFC`×12 本身高度规律（每字节 bit0/bit1 恒 0），成因**未知**（若按 2-bit 字段读则是 `0,3,3,3` 循环）。

**(2) 0xBEC / 0xC14（20B 实体#1 的 A / B）**
```
A(0xbec) clean: ff ff bf f4 ef ff ff e7 fb 7e ff 2f 1c 40 f8 77 f3 00 00 00
B(0xc14) clean: ff ff bf f4 ef 1f fe e7 fb 7e ff 2f 1c 40 f8 77 f3 00 00 00
                         ^^^^^ 仅 byte5/6 不同：A=ff ff, B=1f fe
dirty(两槽逐字节相同): ff ff bf ff 4f f1 7f 00 08 00 00 c0 e3 1f 06 00 20 00 00 00
```
- clean 侧 **B ⊂ A**，差的正好 4 位：B 的 byte5=`0x1f` 缺 bit45/46/47（A 的 byte5=`0xff`），
  B 的 byte6=`0xfe` 缺 bit48（A 的 byte6=`0xff`）⇒ 与 §3 的 A⊇B 规律同型，是一对"宽/窄"双态。
- 末 3 字节恒 `00 00 00`（两档四槽都一样）⇒ 160 bit 里有效位 ≤ 136 bit，实际容量小于字段尺寸。
- dirty 两槽再次**完全相同**（同 §3 现象：同一结构的两槽在同档里取同值）。

**(3) 0xC28 / 0xC50（20B 实体#2 = 勋章位域）**
```
A(0xc28) clean: 00 40 00 40 01 60 10 00 14 00 02 04 21 00 00 00 00 00 00 00   (popcount 12)
B(0xc50) clean: 00 40 00 40 01 60 10 00 14 00 02 04 21 00 00 00 00 00 00 00   (逐字节相同)
A(0xc28) dirty: ff×16 0f 00 00 00                                        (popcount 132)
B(0xc50) dirty: 00 00 08 02 2c e0 00 10 c1 8a 63 f5 03 16 00 45 00 00 00 00   (popcount 32)
```

### 4.3 【已证实】0xC28 = 勋章（132 bit）位域，0xC50 = 同域第二槽
三重独立证据同时命中：
1. **坐标**：obj+0xC28 ↔ char_off `0x3157` = 12631 = 编辑器 `chkBoxMedal01` 的第一个写入字节（[S] `OtherForm.cs:231`）。
2. **容量**：编辑器 Medal01..06 的写点覆盖 `12631..12647` = `0x3157..0x3167` = 17 字节 = 136 bit，
   最后一字节只写低 4 位（[S] `OtherForm.cs:263-267`，`[12647] = 15`）⇒ **实际使用 132 bit**。
3. **字节**：dirty A 的实测内容是 `ff × 16 + 0x0f + 00 00 00` = **恰好 132 个 1**，与 2 的算术逐位吻合；
   而 clean A 的 byte16 也是 `00`（132 bit 之外不置位）。
⇒ `obj+0xC28` 是**132-bit 勋章/称号位域**，`obj+0xC50` 是其**同型第二槽**（clean 档两槽逐字节相同 = 强镜像证据）。

编辑器作者给 6 个复选框的标签是 **集会所 / 贝尔纳村 / 科科特村 / 波克村 / 结云村 / 集会酒馆**（[S] `:493/:500/:507/:514/:521/:528`），
与"6 段宽度不等（30/25/15/15/15/32 bit，合计 132）"的分块写法自洽。
⇒ **"按 6 个据点分组的勋章位域"= 中高置信**（位置/容量/写点精确吻合；分组含义来自作者标签，非游戏侧证据）。

### 4.4 语义判定（逐条）
| 槽 | 语义（置信度） | 依据 |
|---|---|---|
| `0xC28` | **勋章/称号位域，6 据点分组，132 bit（中高）** | §4.3 三重证据 |
| `0xC50` | **同一 132-bit 域的第二槽（高）** | clean 档 A==B 逐字节；dirty 档仅 A 被涂（32 vs 132 位） |
| `0xBEC` / `0xC14` | 同型双态位域（B⊂A），约 157 bit 有效；**管什么：未知** | §4.2(2) |
| `0xBDC` | 16B 实体的 B 槽，位图；**管什么：未知**；dirty 侧被外部灌过 FF | §4.2(1)、§6.3 |

### 4.5 处置建议
1. **`0xC28` + `0xC50` 必须双写**（当前编辑器只写 A，`OtherForm.cs:231-266` 全部落在 12631..12647）。
   现状等于人为制造"A 满/B 旧"的分歧；若游戏侧以 B 为准（或下次存档时用 B 回灌 A），改勋章**不生效或被回滚**；
   若以 A 为准，则 A/B 不一致本身就是非法中间态。**这一条应立即修：把 132-bit 掩码同值写入两个槽。**
   - A 槽 = file `0x3157..0x3167`（17B，末字节 `0x3167` 只取低 4 位）；
   - B 槽 = file `0x316B..0x317B`（17B，末字节 `0x317B` 只取低 4 位；`0x317C..0x317E` 是该 20B 槽的 3 字节空位）；
   - 双写时必须**只置位不清位**（OR 语义），且 B 只能取 A 的子集（clean 档 A==B，最安全的做法是 B 用与 A 相同的掩码）。
2. `0xBEC/0xC14`、`0xBDC/0xBBC`：**禁写**（语义未定 + 位图；且 `0xBCC/0xC00` 中槽不落盘）。
3. 本族**不支持**"整段涂 FF"：一旦涂了 `0xC14`/`0xC50` 这类 B 槽，就把 A⊇B 关系反转（B 变全 1 而 A 不变）。

### 4.6 未知
- `0xBEC/0xC14` 与 `0xBDC` 的实际对象（候选：图鉴/素材/装备/狩猎记录；**无证据**）。
- 勋章 A/B 谁是游戏读取的那一份：**目前没有任何候选消费者**（`0x295D84` 已被证伪为"把 0xC28 当参数传出"，§8.4b），
  只能靠实机对比（§4.5 第 1 条）或找到真正的读取者。
- clean `0xBDC` 的 `0xFC`×12 成因，以及 dirty 侧"灌 0xFF"的写者（本编辑器无该写点，§6.3）。
- `0xC64`(4B, file 0x317F) 只有 I/O 两个引用 [X]，是否死字段未知。

## §5 尾部 3444B（obj+0x3684 @file **0x50BA..0x5E2D**；原写 0x4B6A 为早 0x550 旧坐标）

### 5.1 几何：**单块，不是数组**
- `0x3684 + 0xD74(3444) = 0x43F8` = 下一条落盘字段（3B）起点；file `0x4B6A + 0xD74 = 0x58DE` 同样精确闭合 [T]
  ⇒ 无空洞、无内嵌步长。
- 与四个"槽族"相反，它**一次整块搬运**（[D] `0x51DA98` 窗口）：
```
0051da74: add  r1, r5, #13952        ; obj+0x3680, 1B
0051da84: movw r0, #0x3682 ; mov r2, #2
0051da98: movw r0, #0x3684
0051da9c: movw r2, #0xd74            ; 一次 3444B
0051daa0: add  r1, r5, r0
0051daa4: mov  r0, r4
0051daa8: bl   0x3df378
```
  对比：68B/128B/288B 族是"每槽一条 movw + bl"，本块是"一条 movw + 一个 0xD74 长度"
  ⇒ **代码作者把它当一个不透明大 blob 处理**，与"定长元素数组"的判据（`records-128.md` §1.2）正好相反。

### 5.2 引用集（完备）
`0x3684` 不能用 `add imm12` 编码（§0）⇒ movw 站点集即全静态引用集：全 .text **只有 2 个**
`0x51DA98`（writer）、`0x51E5B0`（reader）[X]，两者都在成员#4 自己的存档 I/O 序列内。
⇒ **除存档读写外，没有任何代码用 `obj+0x3684` 这个偏移寻址**。
（唯一残余可能：先取 obj 指针再用寄存器间接寻址——本片排除不了，标 [?]。）

### 5.3 字节
**修正（2026-10-23 实测）**：正确区间 `0x50BA..0x5E2D` 在 clean 与 dirty **两档全 0，`diff=0`**（原「diff=104 / FF×22」取样于早 0x550 的错位窗口，作废）。⇒ 3444B 是**保留/未用区**。
即内容集中在中间段、两档差很小 ⇒ 形态像"绝大多数条目为空的稀疏表"，但**看不见任何字段**。

### 5.4 语义判定
> **未知。** 可证实的只有：①单块 3444B、无内嵌步长；②静态引用只有存档 I/O；③两档 97% 相同且稀疏。
- "任务/委托记录表"：**[I] 低置信**——物理上它紧接记录/位图族且在成员#4 尾部，但没有任何字段级或消费者证据。
- **不采信** "CURRENT-RULING 的'尾块 0x3684(22B/3444) 编辑器涂 FF 实锤'"：见 §6.3。

### 5.5 处置建议：**禁写（硬）**
1. 结构未知且 3444B 整块：任何"清零/涂 FF"都会一次性破坏 3444B 未知状态。
2. 更关键的是**它没有 gameplay 侧静态消费者**：写它拿不到任何可观测收益，只有风险。
3. 编辑器现无写点落在此区（[S]：5 位偏移上界 12647，见 §6.3）⇒ 现状安全，保持。

### 5.6 未知
- 完整内容（只看到 96/3444 字节，且都在全 0 的头尾）。
- 是否被指针表间接引用（`0x3684` 不可 `add` 编码，但仍可由指针 + 寄存器偏移到达）。
- 那 22 个 `FF` 的来源（无编辑器写点；unknown-tool 或合法数据）。

```

00524abc: add r0, r0, r2, lsl #2      ; 字下标 = bit>>5
00524acc: (1 << (bit&31)) 与字 & / |
```

若是 2-bit 字段，掩码必然是 `and #15` + `lsr #4`——**代码里不存在这种形式**。
⇒ 288B / 68B 两族（以及同 helper 覆盖的 36B 记录）都是 **1 bit / 项**。
- 68B = 544 项/槽；164B = 1312 项/槽；288B = 2304 项/槽（**容量**，非实用项数；288B 的更新循环上界是 1536）。

## §8.0 顺带升级：**stride = 3 × 槽宽** 已在指令层证实，且三槽是"同位同步"维护

> **摘录记法**：下面代码块里的 `biceq/orrne X,X,rN` 是**相邻两条真实指令的合写**
> （原文成对出现，例如 `00520b48: 01c33005 biceq r3,r3,r5` + `00520b4c: 11833005 orrne r3,r3,r5`）；
> `A ; B ; C` 形式的行同样是多条真实指令的压缩，每条都能在 `followup-dump.txt` 里逐条对上。
> 只有 `;` 之后的注释是本报告加的。

**(a) 288B 族更新器**（[D] `fam288 0x520B00`，属 0x51E6D8..0x52139C 大例行）：
```
00520b2c: mov  r0, #864              ; 0x360 = 3 × 288  ← 组步长
00520b34: mla  r2, r9, r0, r7        ; r2 = 组基址 + r9*0x360   (r9 = 组号)
00520b3c: add  r2, r2, r3, lsl #2    ; + word*4
00520b40: movw r3, #0x16c8           ; A 槽
00520b44: ldr  r3, [r2, r3]
00520b48: biceq r3, r3, r5
00520b4c: orrne r3, r3, r5           ; 同一个 mask r5、同一个条件
00520b54: str  r3, [r2, #0]
00520b5c: mla  r1, r9, r0, r7
00520b6c: movw r2, #0x17e8           ; 中 槽（0x16C8+0x120）
00520b70: ldr  r2, [r1, r2]
00520b74: biceq/orrne r2, r2, r5     ; ← 同一 bit
00520b80: str  r2, [r1, #0]
00520b8c: movw r1, #0x1908           ; B 槽（0x16C8+0x240）
00520b90: ldr  r1, [r0, r1]
00520b94: biceq/orrne r1, r1, r5     ; ← 同一 bit
00520ba0: str  r1, [r0, #0]
00520bbc: cmp  r9, #5                ; 5 个组 ✓（与几何 5 组一致）
00520bc0: bne  0x520a44
```
⇒ **一个 bit 被同时写进同一组的 A/中/B 三槽**（mask 与条件完全相同），组步长 `864 = 3×288`。

**(b) 68B 族更新器**（[D] `famSmall 68B 0x520C7C`）：
```
00520c7c: movw r6, #0x27a8 ; ldr r6,[r7,r6] ; biceq/orrne r6,r6,r1 ; str r6,[r7,#0]
00520ca4: movw r7, #0x27ec ; ldr r7,[r3,r7] ; biceq/orrne r7,r7,r1 ; str r7,[r3,#0]
00520ccc: movw r2, #0x2830 ; ldr r2,[r0,r2] ; biceq/orrne r1,r2,r1 ; str r1,[r0,#0]
```
以及 `0x524B04`（同一 helper 族）：
```
00524b04: mov  r3, #204              ; 0xCC = 3 × 68  ← 组步长
00524b08: mla  r0, r1, r3, r0
00524b14: movw r1, #0x27a8 ; ldr r0,[r0,r1] ; and r1,r2,#31 ; ... ; movwne r0,#1 ; bx lr   ; bit-test
```
⇒ 68B 同样是"组步长 3×68 + 三槽同位同步"，且 `0x524A80` 那一段是**逐族同构的 bit-test helper**
（288B: `mov r0,#864` + `movw #0x1908`；36B×2: `movw #0x2a0c`/`#0x2a54`；68B: `mov r3,#204` + `movw #0x27a8`/`#0x2830`）。

**(c) 位号来源不是数组下标**：`0x520CEC..0x520D5C` 出现
`mov r6,#50 / str r6,[sp,#52]` → `bl 0x6aa9b8` → 结果 `ldrh [sp,#44]`，并与哨兵 `movw r5,#0xffff` 比较跳过
⇒ **位号由一张运行期表（按类别 50/51/52）给出，`0xFFFF` = 表尾**。288B 侧同型（内层上界 `1536`）。
这与 `CURRENT-RULING` 修正18 的"任务表对象 + 逐条取 id"是同一套机制 [D]。

**对 §1 结论C 的修正**：中槽是"同一位域上的**第三份状态副本**"——同一例行、同一 bit 位置、同一掩码地更新
（不是派生值），但**"三槽恒等"未被证实**：窗口里每槽的 `biceq/orrne` 之前都有各自的 `cmp`
（`cmp r8,#0` / `cmp r3,#0` / `cmp r2,#0` / `cmp r5,#0`），所以每槽的**置/清极性可能各自独立**
⇒ 三槽更像"同一 id 空间的三种状态"，而不是"三份逐字节相同的拷贝"。
"为什么只落盘 A 与 B"仍**未知**（候选：两副本做存档完整性校验 / 中槽是运行期工作区）。
这条**只对 288B/68B 成立**；164B 族有反例（§8.3），不能外推。

## §8.1 164B 两槽内部结构：位图，不是 u16 对 / 4B 计数

| 判据 | 观测 | 结论 |
|---|---|---|
| 游程形态 | A clean 有 4 段连续 1：78 / 59 / 30 / 28 bit，止点 `0x3f` / `0x07` / `0x03` / `0x3f` | 位数组，**段长非 8 的倍数** |
| 字对齐 | 跨 4 字节 `f0 ff ff ff`（u32 = 0xFFFFFFF0） | 不可能是计数/浮点 |
| 骨架字节 | 四个样本（A/B × clean/dirty）中**完全一致**的：byte14..18 = `08 00 00 00 80`、byte26 = `07`、byte27..39 = 全 0 | 常量/长度掩码，非数据 |
| 同族机制 | §8.0：288B/68B 都是 `u32[bit>>5]` 位图（`and #31` + `lsr #5` + `ldr [base+word*4]`） | 同区域家族一律位图 |
| 容量 | 164B = 1312 bit；但 288B 内层上界 1536（若按 bit 计仅 192B < 288B） | **槽宽 > 实用位**在本对象里是常态 |

⇒ 结论：**164B/槽 = 1312 bit 容量的按 bit 打包状态数组，实用位数 ≤ 1312，具体段边界未知**（仍缺 byte 64..131）。

## §8.2 B ⊆ A 的机制含义

- clean 档 96 个可见字节逐位满足 `B & ~A = 0`，且差异是"离散小簇"（byte0..8、13、19..25、40..43、60..63），
  **不是整段不同** ⇒ B 是 A 的**真子集**，A\B = "A 有而 B 无"的那一小撮位。
- 与之对照（§8.0）：288B/68B 的三槽由**同一例行、同一 bit 位置、同一掩码**更新（置/清极性可能各自独立）。
  ⇒ 164B 的 A/B 至少**不属于那种"同例行三槽"结构**：本族**没有任何更新器**，且 A/B 呈单调包含。

**机制含义（[I] 中置信）**：A\B = "已发生但未确认/未结算"的差集。这与 `0x42C(cleared) ⊆ 0x52C(seen)`
是同构关系，只是这里没有第三个"achieve"层（中槽运行期不落盘，无法观察）。

## §8.3 【特别回答】dirty 档两槽 164B 完全相同说明什么

**结论：它等价于"A\B = 空集"，是 `B ⊆ A` 不变量下的一个合法端点；既不能证明"写后镜像"机制，也不能排除"同位同步写"。**
但有一条**可以定论**：**"无条件镜像"被 clean 档排除**（clean 档 A≠B 且 B⊂A）。

推理链（严格版）：

```
不变量            B ⊆ A            （clean 档 96 个可见字节全部满足，§3.2）
dirty 实测        A == B 逐字节     ⇒ A\B = ∅
```
- `A\B = ∅` 在 `B ⊆ A` 下是**允许的端点**，不需要任何"写 A 后复制到 B"的动作就能出现：
  只要 A\B 这个差集集合本身变空即可。所以 **dirty 的相同不构成镜像机制的证据**。
- 反方向：若游戏对这两槽做**无条件镜像写**，clean 档必须 A==B；实测 A≠B ⇒ **无条件镜像不存在**。
- 仍开放的解释（本片无法区分）：
  (i) A\B 是"未确认/未结算"差集，dirty 档该差集恰好为空（**最简解释**，§8.2）；
  (ii) 某处存在"同位同步写"（像 §8.0 的 288B/68B 三槽那样同住写入），且它只在满足条件时才跑；
  (iii) dirty 档由外部工具整块改写了两槽（但见 §6.3：dirty 的骨架字节 `80`@18、`07`@26 与 clean 一致，
       且两槽非 FF 的数据字节 `02 04 00 96 20` 也一模一样 ⇒ 更像"同一份数据的两次落盘"而非灌 FF）。

**注意措辞边界**：不能说"dirty 档两槽饱和到全 1"。实测两槽确实逐字节相同，但**并非全 1**：
byte9 = `0xBF`、byte10..14 = `02 04 00 96 20`、byte18 = `0x80`、byte26 = `0x07` 都不是 FF，
且这些非 FF 字节在两槽中完全相同。所以正确的表述是 **"两槽同值"**，不是"两槽打满"。

**与勋章（20B 实体#2）机制不同**：

| | 164B 对 | 勋章 0xC28/0xC50 |
|---|---|---|
| clean 档 A vs B | **A ≠ B（B 真子集）** | **A == B 逐字节相同** |
| dirty 档 A vs B | A == B（差集为空） | **A ≠ B**（A 被编辑器涂满 132 bit，B 保留真实 32 bit） |
| 解释 | 位包含不变量 + 差集为空 | 双拷贝，**编辑器只写 A 造成分歧** |
| 建议 | 不可写；若写必须保 B⊆A 且整块移植 | **必须双写 A+B** |

⇒ 两族**不能套用同一套"镜像"结论**：勋章是"应当相等的双份被打成不等"（编辑器造成），
164B 是"本就允许不等的子集对，此时差集为空"（游戏侧自然态）。


## §8.4 消费场景：**两个候选消费者全部被证伪**

**(a) `0x5412FC` = 32 位常量构造，不是字段访问**（[D] 原文）：
```
005412fc: movw r1, #0xb18
00541300: ldr  r2, [r0, #340]
00541304: orr  r1, r1, r3, lsl #16     ; r1 = (r3<<16) | 0x0b18   ← 0xb18 只是常量的低半
00541308: str  r1, [r0, #344]
0054130c: orr  r1, r2, #3
00541310: str  r1, [r0, #340]          ; 置 flags=3
```
与 §6.2 已判死的 `0xA3DB14` **指令形状逐条相同**（同为 `movw r1,#0xb18` + `orr r1,r1,r3,lsl#16`）。
⇒ 从 164B-B 站点表删除。同函数的其它 movw 立即数（`0x205c` @0x541340、`0x3cb` @0x541374）与
`add r2,r6,#236; add r2,r2,#199680`（→ `r6+0x30CEC`）都属于**另一个对象**，
与成员#4 字段表（159 条）对不上（成员#4 无 `+0x30CEC` 这个单一字段，`+0x54/+0x64/+0xEC` 也不在表内）。
`0x5429C8`（同为 `movw r1,#0xb18`、同为 reg1、距离 0x16CC）**高度可疑为同型常量构造**，但本片无该段反汇编，标 [I]。

**(b) `0x295D84` = 把 `0xC28` 当参数传出去，不是按 `obj+0xC28` 取址**（[D] 原文）：
```
00295d84: movw r1, #0xc28
00295d88: add  sp, sp, #8
00295d8c: pop  {r4, r5, r11, lr}
00295d90: b    0x281b4c              ; 尾调用，r0=对象, r1=0xC28
...
00295e00: movw r1, #0xc27
00295e04: bl   0x281b4c              ; 同一个被调函数，参数 0xC27
00295dec: movw r2, #0x3ed            ; 0x3ED = 1005 = 已知硬编码 questId（CURRENT-RULING 修正18）
00295e08: movw r0, #0x16ec ; mov r1,#0x40000000 ; str r1,[r4,r0]
```
⇒ `0xC27 / 0xC28` 是**成对的参数/ID**（同函数里还出现已知 questId `0x3ED`），不是成员#4 字段偏移。
**`obj+0xC28`（勋章）的游戏侧读取者，本片仍然没有找到。**

**结论：164B 的 A/B 在整个 .text 里的静态引用，只有存档 reader（`0x51DE5C`）与 writer（`0x51D344`）两处。**
配合 §0 的可编码性判据（`0xB18` 不能用 `add imm12` 编码 ⇒ movw 集完备）⇒ 这是**可证的"无 gameplay 消费者"**。
唯一残余可能：先算出一个基址指针（非 obj+0xB18 的 movw 形式）再间接访问——本片排除不了，标 [?]。

## §8.5 164B 对语义定案

> **164B 对 = 成员#4 内的 1 组 [A(0x9D0) / 中(0xA74, 运行期) / B(0xB18)]，各 1312 bit 打包位图；
> A ⊇ B 单调；整个 .text 只有存档 I/O 读写它们。**
> **语义 = "宽集 / 窄集"双态状态位图（A\B = 未确认差集）——中置信；具体管什么 = 未知。**

| 维度 | 结论 | 置信度 | 依据 |
|---|---|---|---|
| 定长/变长 | 定长 164B × 3 槽（1 组） | 高 | [T] 几何 + §1 |
| 字段类型 | 按 bit 打包的位图（非 u16/u32/f32） | 高 | §8.1 |
| A/B 关系 | B ⊆ A（真子集），非同值副本 | 高 | §3.2 + §8.0 对照 |
| dirty 两槽相同 | 等价于 A\B = ∅（端点情形，非镜像证据） | 高 | §8.3 |
| A/B 谁读 | **只被存档 I/O 读**（无 gameplay 消费者） | 高（可证完备） | §8.4 |
| 具体对象/语义 | **未知**（"seen⊇cleared/acked"是最佳候选） | 中（[I]） | §8.2 |
| 分段边界 | 未知（缺 byte 64..131） | — | 仍缺 dump |

### 可写 / 禁写：**禁写（硬）**，且比第一轮更硬
1. **没有任何 gameplay 消费者能找到** ⇒ 写它拿不到可控收益（即使写错也未必立刻可见，属于"静默毁档"最坏型）。
   另一种可能是这些字节**对游戏根本无效**（死数据/中间产物）；但"无法解释的字节一律不写"是项目铁律，
   而且没有证据能证明它是死的（读档后它会进内存、存档时又被原样写回，说明链路是通的）。
2. 语义未定的 1312 bit 位图：按偏移涂 `0xFF` = 一次性把 1312 个 id 全打勾，并破坏 A⊇B 不变量（把 B 打到 A 之上）。
3. 中槽 `0xA74` 不落盘，永不可写；写它等于给运行期塞脏值。
4. 编辑器现无写点（[S] 见 §6.3），**保持现状即可**。
5. 若将来一定要改：唯一形式 = **A/B 双槽整块移植**（2×164B，来自合法档），并保证 `B ⊆ A`；
   不接受"按段涂/按 bit 置"。

## §8.6 本节新增的未知
- `0x5429C8` 是否与 `0x5412FC` 同型常量构造（缺该段反汇编，[I] 高可疑）。
- `0x281b4c` 的语义（`(obj, 0xC27/0xC28)` 参数到底是什么；可能与勋章**无关**）。
- 164B 的 A\B 差集在真实存档里对应什么事件（需要一次"改了某个进度后再存档"的前后对照）。
- 中槽 `0xA74` 的三槽同步规则（164B 族没有找到更新器，无法像 §8.0 那样验证）。
