## 1. 结论先行

1. **签名**：`0x51dbb4(obj, reader)`。`obj` = 单例，经 GOT 槽 `0x145159C` 取出；`reader` = 存档字节流游标。
   [已证实·转引] `fn-3e77b0.txt`：
   ```
   003e77dc: e59f015c  ldr r0, [pc, #348] ; [0x3e7940]=0x145159c
   003e77e0: e1a01004  mov r1, r4
   003e77e4: e79f5000  ldr r5, [pc, r0]
   003e77e8: e5950000  ldr r0, [r5, #0]        ; r0 = *(0x145159C) = 成员#4 obj
   003e77ec: eb04d8f0  bl 0x51dbb4
   ```
2. **`0x51dbb4` 本体（`0x51dbb4..0x51dc3f`；`0x51dc40` 若不是紧随其后的函数起点，则该上界后移，不影响本节结论）内，只有 4 个 `movw`**，全在 `0x51dc40` 之前：
   | vaddr | 指令 | 含义 |
   |---|---|---|
   | `0x51dbdc` | `movw r0, #0x72c` | obj+0x72C |
   | `0x51dbe0` | `movw r2, #0x112` | 长度 274 |
   | `0x51dbf0` | `movw r0, #0x83e` | obj+0x83E |
   | `0x51dbf4` | `movw r2, #0x112` | 长度 274 |
   ⇒ 外层函数**自己**只按"大立即数"读取两个 274 B 块；**它没有任何 `movw` 指向 obj+0x0..0x2C 或 obj+0x424/0x428**。
   （窗口 `0x51dbb4..0x51dc50` 全扫，只有上表 4 条 + `0x51dc50` 那条属于 helper 的 `movw r0,#0x424`。）
3. **obj+0x0..0x424 头区里，`0x51dbb4` 自己在 `bl 0x51dc40` 之前读的只有一处：obj+0x20 起的 1024 B 块**（偏移 0x20 与长度 0x400 都是可旋转立即数，用 `add r1,r5,#0x20` / `mov r2,#0x400` 编码，故不出现在 movw 索引里）。
   落点 = **file `0x280B..0x2C0B`**：起点 `0x280B` 由 `save-load-path.md §4 行4` 实测锚定（上一段口袋区 `0x27BF+76 = 0x280B`），长度 `0x400` 由下一段起点 `0x2C0B`（helper 首字段 `0x424`）反推**唯一确定**。
   [已证实·转引 + 算术闭合]
4. **obj+0x0..0x28 不是角色头副本。多重否证**（详见 §3.3，第二轮修正后含"链终止"硬证据）。最强两条：
   ① **时序**：632 B 角色头（char_off `0x0..0x277`）在 `0x3e0db8` 用 `memcpy` 整块吞掉、`reader.ptr += 632`，随后才进 `0x3e77b0` 调度；
   `0x51dbb4` 是调度器里第 3 个成员调用（`0x3e77ec`），此刻 reader 已 ≥ `0x280B`。**外层函数在结构上不可能读到 char_off 0x0..0x28。**
   ② **链终止**（§7.3）：`0x51dc40` 的 tail-call 链读完 `obj+0x446C` 就 `pop` 返回，**从没读过 `obj+0x0..0x28`** —— 读档不写这些字段。
5. **"头字段在文件开头"是对象坐标系与文件坐标系的混淆**（`obj+off` 序 ≠ 文件字节序）。权威表把 `obj+0x0..0x28` 排在**表尾**
   （第 146..159 行，file `0x5980..0x59AC`，44 B / 14 次读取）。
   **但本报告证明这 14 行不属于 `0x51dc40`**：表第 1..134 行才等于 helper 实测的 134 次 `bl 0x3df2a8`（§3.5），第 135..159 行是越界/换基址产物，
   其 obj 坐标不可信、文件坐标也只是累加值。⇒ **§7.3/§7.4 以实测（反汇编）定案**：`0x51dc40` 的 tail-call 链在读完 `obj+0x446C`（file `0x594E`）后即 `pop` 返回，
   **链里从未出现 `obj+0x1CC/0x1AC/0x0..0x28`**；那 14 + 5 行来自另一个函数（其 `movw` 在 `0x5215d4..0x521778`），文件坐标是累加产物。
   （链尾 `obj+0x446C` 的 file 落点：旧表记 `0x594E`，**经 §8.1 循环修正后为 `0x5E9E`**，链结束于 `0x5EA2`。）
6. 附带纠正：**`0x0..0x28` 段是 44 B（0x0..0x2B），不是 41 B**；`0x2C..0x41F` 由第 3 条的 1024 B 块覆盖；`0x420..0x423` 是唯一空洞。

## 3. [已证实] 证据

### 3.1 外层函数本体的 movw 全扫（硬证据）

对 `movw-index.json` 取窗口 `[0x51dbb4, 0x51dc50)`（即"`0x51dbb4` 全函数 + helper 前 16 B"），结果**只有 5 条**：

```
[5364700, 1836, 0]   -> 0x51dbdc  movw r0, #0x72c     (1836 = 0x72C)
[5364704,  274, 2]   -> 0x51dbe0  movw r2, #0x112     (274 = 0x112)
[5364720, 2110, 0]   -> 0x51dbf0  movw r0, #0x83e     (2110 = 0x83E)
[5364724,  274, 2]   -> 0x51dbf4  movw r2, #0x112
[5364816, 1060, 0]   -> 0x51dc50  movw r0, #0x424     <- helper 0x51dc40 的第一个字段
```
（十进制 vaddr 5364660 = `0x51dbb4`；上表第一列即 json 原值。）

推论（[已证实·机器]）：`0x51dbb4` 自身**没有**任何 `movw` 指向 `0x0..0x2C`、`0x424`、`0x428`。
（原文此处还有一句"也没有指向 `0x2384/0x2388`"——**已撤回**：实测变长描述符用 `ldr r0,[r5,#2384]` / `[r5,#2388]`，
其中 2384/2388 是**十进制**，即 **obj+0x950 / obj+0x954**；机制见 §7.1。）
所有它自己触碰的小偏移（`0x20`、长度 `0x400` 等）都是"可旋转立即数"，编码为 `add`/`mov`，本来就不进 movw 索引 —— 与"1024 B 块用 `add r1,r5,#0x20` + `mov r2,#0x400`"的形态一致。
`0x51dbb4` 函数体只有 `0x51dc3f - 0x51dbb4 + 1 = 0x8C = 140 B`（35 条；若 `0x51dc40` 紧随其后），其中 `0x51dbb4..0x51dbdc` 只有 **10 条指令**的空间：
够"1 次块读（add/mov/bl）+ 1 次 `bl 0x51dc40`"，**不够**读 14 个头部字段。 **[已证实]**（§7.1 实测：全函数 35 条，只有 5 次 `bl 0x3df2a8` + 1 次 `bl 0x51dc40`，无其它读）

### 3.2 helper 头部与权威表对齐（索引可信性证明）

`movw` 盲取 helper 前 3 个字段站点：

```
0x51dc50  movw r0, #0x424      file 0x2C0B   (表行 1)

⇒ 权威表 `member4-file-layout.txt` 的"表行序 = reader 序 = 文件字节序"在头部得到独立机器确认。

### 3.3 "obj+0x0..0x28 是否角色头副本" —— **否**（多重否证，第二轮修正）

1. **时序否证（可证伪，最强）**：`0x3e0db8` 先把 632 B 角色头整块 `memcpy` 到栈并 `reader.ptr += 632`，
   文本实据 [已证实·转引] `save-load-path.md:32`：`memcpy(stack, reader.ptr, 632) // 632 B = 0x278 角色头，未解析，仅跳过`。
   之后才进 `0x3e77b0`；而 `0x51dbb4` 是调度器第 3 个成员调用（`0x3e77ec`），此前已有 道具箱/口袋 两个成员吃掉 `0x278..0x280B`。
   ⇒ 进入 `0x51dbb4` 时 reader 位置 ≥ `0x280B`，**结构上读不到 char_off 0x0..0x28**。
2. **落点否证（坐标）**：按权威表，这 14 行的落点是 `0x5980..0x59AC`（成员#4 数据流尾部），**不是** `0x0..0x2C`。
   `swe2-review.md:100`（B10）把表行 `obj+0..0x28` 当成 `char_off 0x0..0x28` 是**读表错误**：权威表同一行明确写着 `0x05980`。
   （该坐标本身另有存疑，见 §3.6；但无论取哪个坐标，都不在 `0x0..0x2C`。）
3. **形状否证（结构）**：角色头前 `0x2C` 字节的形状是 `名字 UTF-8 32 B @0x00` + `playtime u32 @0x20` + `gold u32 @0x24` + `HR u8 @0x28` + `gender u8 @0x2A`（[已证实·转引] `CURRENT-RULING.md:58`）。
   而 obj+0x0..0x28 的读取切分是 `1,1,4,8,2,4,4,2,2,4,4,2,2,4` —— **没有任何 32 B 连续读**，无法承载名字。
4. **字节否证（差分，第二轮作废）**：`member4-diff.txt` 里这 14 行 `diff=0` —— 但按 §8.5 修正后的映射，旧表坐标 `0x5980..0x59AC` 落在
   **`obj+0x3684` 那个 3444 B 大块**内（块起点 `0x50BA`，即块内 +0x8C6），既不是身份数据也不是位域；**不再用作论据**（见 §4.1）。
5. **链终止否证（第二轮新增，最强）**：`0x51dc40` 的 tail-call 链在读完 `obj+0x446C`（旧表 file `0x594E`；修正后 `0x5E9E`）后 `pop` 返回（`0x51e6cc/0x51e6d0`），
   链内**从未出现** `obj+0x1CC / 0x1AC..0x1BE / 0x0..0x28` 的任何 `bl 0x3df2a8`（§7.3）⇒ 读档过程**根本不写** `obj+0x0..0x28`。

### 3.4 obj+0x20 / 0x24 / 0x1AC..0x1D4 的**双写疑云**（沿 §3.5/§3.6 已大幅收敛）

如果照单全收权威表，同一 obj 偏移会被写两次：

- `OUT`：`obj+0x20..0x41F` = 1024 B ← file `0x280B`（先，**有 movw/算术锚**）
- 表尾 25 行声称：`obj+0x20`=4 B ← `0x59A0`、`obj+0x24`=2 B ← `0x59A4`、`obj+0x26`=2 B ← `0x59A6`、
  `obj+0x1AC/0x1B2/0x1B8/0x1BE`=各 6 B ← `0x5968/0x596E/0x5974/0x597A`、`obj+0x1CC`=8 B ← `0x5960`（后，**无 movw 锚**）

**H-C（本报告采信）**：表尾 25 行根本不是 `0x51dc40` 的读取（§3.5 条数 134 vs 159；§3.6 三条污染证据），
所以"双写"很可能不存在 —— 真正待答的问题变成"**这 90 B 到底被哪个函数、以什么基址读**"，而不是"谁覆盖了 1024 B 块"。

仍需保留的两个备选（若主会话跑出指令列表后 H-C 不成立）：

- **H-A 同一对象**：1024 B 块是模板/默认值，末尾 5 处标量再被覆盖 → 编辑器把 `0x280F` 当"金币副本#2"写会被读档覆盖。
  反证：`0x59A4/0x59A6`（若真是 obj+0x24 = 金币低/高半）在两份不同猎人的档里 `diff=0`，即金币完全相等 —— 不合常理。
- ~~**H-B 换基址**~~：**已实测否掉**（§7.3）—— 末段（`0x51e560..0x51e6d4`）全部是 `add r1, r5, r0` / `add r1, r5, #imm`，
  基址就是 obj（r5），不存在子对象指针。

## 7.2 结构发现：`0x51dc40` 是一条 **tail-call 链**的首段
