# 成员外尾部稀疏/社交段切分：char_off `0x80000..0x11F8A0`

> 坐标系：`char_off` = `.hnt` 猎人块内偏移（块长 1,177,760 B = `0x11F8A0`）；`file_off = hunterAdds[i] + char_off`，`hunterAdds = [0x18CC9C, 0x2AC560, 0x3CBE24]`。
> 样本：clean = `MHGU/save-snapshots/20261022-clean-reference/system_CLEAN`（slot0 = 猎人B @`0x18CC9C`，slot1 = 猎人A @`0x2AC560`）；dirty = `MHGU/save-snapshots/20261022-v6-ready/system`（slot0 = 猎人B @`0x18CC9C`）。
> 执行方式：本 worker 会话无 `bash`/`eval`（`xd://` 实测 `No such tool: xd://eval`），全部扫描脚本由主会话执行，原始证据落 `.tmp/mhgu/tail-sparse/out{,2,3,4}.md`；本报告只引用这四份文件里的实测数字。

## 主结论（先看这 8 条）

1. **区间是 653,472 B 而不是 654,496 B**：`0x11F8A0 − 0x80000 = 0x9F8A0`。派发口径多算 1,024 B。
2. **本段不是「稀疏/社交预留」，是密集记录区**：slot1 非零 **72.62%**（474,575/653,472）；≥256B 零洞全段只有 **16 条、合计 30,043 B**。`coverage-map.md` 的「`0xC95A8..0x1175A8` 采样 18%、319KB 稀疏区」是 4KB 抽样假象，**作废**。
3. **本段是「每档整体重写的缓存区」**：同角色（猎人B）前后两档 **71.969%** 字节不同；跨角色（同档两槽）相同率仅 2.4-2.7%。且 dirty 侧更空（dirty-only-nonzero 93,390 vs clean-only-nonzero 225,499）⇒ **不存在「编辑器涂 FF」污染**。
4. **容器类型随档变化**：slot0 是 62 条 **quest 记录数组**（每组 7 语种路径、80B 步长）；slot1 是 **16B 记录网格**（`ff 00 | 49 92 24 49 92 24 | 8B 数据`，22,940 条、步长恒 16），两槽在同一 char_off 上装的是**不同种类的缓存**。⇒ 边界是**结构性质**的，不是固定偏移表（与主会话实测「尾部不入 `0x3e77b0` 读调度、写侧整块透传、movw 常量 0 命中」一致）。
5. **zlib 不是 1 条而是 50 条同构网格**：`0xC9B99 + k×73`（k=0..49，跨度恰 3,650 B = 50×73），头 `78 9c`、压缩长恒 29（`1d 00 00 00`）、解压恒 **6,328 B 全零**。**`826281`（十进制）= `0xC9BA9`，正是首条流起点 ✔**；派发括号里的 `0xC9E69` 是十进制→十六进制的换算笔误（`0xC9E69 = 826,985`），该处实测不是流起点（`inflate` 报 `Error -3`）。
6. **统一压缩 blob 原语**：`[前缀][u32 压缩长][zlib 流][尾]`。member[13] B1（`0x2C6B4`）的流前缀与这 50 条**逐字节相同**（`78 9c ed c1 31 01 00 00 00 c2 a0 f5 4f 6d 0d 0f a0 00 00 00`），Adler `0x18B80001` 正是 6,328 个零字节的理论值。
7. **quest 缓存只存在于 slot0**（slot1 中 `questData_*` 0 条）——这是「每档缓存」最硬的证据；且 quest 记录把区域切成「27 条 + 174,838 B 未知块 + 35 条」三段，末条正好收在最大零洞 `0x117125` 之前。
8. **尾段 `0x117125..0x11F8A0` 自成一族**：17,681B 零洞 → 206B 计数头（`01 00 03 06 03 10 00` + `01..0f`）→ **470B 记录 ×10**（469B 零 + 1B 状态）→ 104B/2,496B 文本记录带（含 CJK 台词）。

### 3. zlib 流定位（全段枚举 + 逐条 inflate 验证）

扫描规则：`CMF&0x0F==8` + `(CMF<<8|FLG)%31==0` + `FDICT==0` → `zlib.decompressobj()`，要求 `eof`。

| 量 | 值 |
|---|---|
| 命中数 | **50**（两槽同位置：slot1 `out.md` #B、slot0 `out2.md` S6 各 50 条） |
| 起点 | `0xC9BA9 + k×73`，k=0..49；记录起点 `0xC9B99 + k×73` |
| 头 / 压缩长 / 解压长 | 恒 `78 9c` / **29** / **6,328** |
| 解压内容 | **50/50 全零** |
| 网格跨度 | `0xC9B99..0xCA9DB` = **3,650 B = 50×73 整** |
| 相邻起点差 | `73 ×49`（无一例外） |
| 变体 | 全段只出现 `78 9c`；`78 01` / `78 da` / `78 5e` 及 `08/18/28/…` 系列 CMF **0 命中** |

逐条明细（偏移 / 头 / 压缩长 / 解压长 / 解压首 64B / 是否全零，共 50 行）见 `out.md` §B 表；50 条的「解压首 64B」全部是 `00 ×64`。

**坐标换算纠正**：`826281`（十进制）= `0xC9BA9`，**正是首条流起点**——覆盖账的原始观测是对的。派发/覆盖账括号里的 `0xC9E69` 是十进制→十六进制换算笔误（`0xC9E69 = 826,985`）；该处实测 16B 全零、`inflate` 报 `Error -3`，它落在网格内部（前一条流起点 `0xC9E3A`、后一条 `0xC9E83`）。**条数纠正**：不是「1 条」而是「50 条网格」。另：`78 9c + 1d 00 00 00` 的「长度头」观察也正确——`1d 00 00 00` 就是记录里的 u32 压缩长 29。

### 10. 小簇 gap 直方图与 stride 方法论警告（避免后继误判）

Top pitch：**16 ×21,601**、4 ×4,817、20 ×2,553、2 ×1,947、10 ×1,705、5 ×1,676、3 ×1,653、8 ×1,429、6 ×1,315、18 ×1,086、14 ×1,019、7 ×670、12 ×606、11 ×577、22 ×344、13 ×264、36 ×250、24 ×246、9 ×180、19 ×117。
分桶：`2-4 = 3,600`、`4-8 = 8,478`、`8-12 = 3,891`、`12-16 = 1,917`、**`16-24 = 25,950`**、`24-32 = 410`、`32-48 = 463`、`48-96 = 31`、`96-128 = 101`、`≥256 = 20`。
**结论**：`16` 与 `4/8/20` 的峰是「记录内部零字节间距」，**不是记录 pitch**；真实 pitch 见 §4（16 / 324 / 470 / 104 / 2,496 / 80），且必须用零掩码自相关 + 无零块排除后才有意义。

- **零掩码自相关在「无零块」上退化**：`0xB0000..0xC7000` 每 4KB 最佳 stride 报 992/112/768/480/864/… 且 `zmatch=1.00`，只因整块几乎无零字节（z 全 0 时任意 stride 都 100% 匹配）。这些**不是**记录长度。
- 全段 4KB 精确字节周期只出现在 `0xCB000..0xCF000`（period=4）与 `0xCF000..0xDD000`（period=2），即填充族内部。
- `0x80000..0xAF000` 每 4KB 在 `stride=80`（zmatch 0.93-0.98）与 `stride=2/3`（0.95-1.00）间交替，但 `bmatch` 只有 0.29-0.34 ⇒ 有 ~80B 记录格子但记录内数值各不相同（不是字节级重复）。
- 尾部 `0x117125..` 子区 `bmatch` 0.93（远高于前段），是「大段零 + 少量文本」的典型形态。
