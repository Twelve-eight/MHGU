# 覆盖度计量器（2026-11-03 起可复算）

此前 `code-metrics.md` 的 72.8% / 52.2% 来自一次性脚本与 `.tmp` 中间表，重跑不出来。现在整条链路在仓库内，且**种子的真实性被单独验证过**。

```

node tools/mhgu/coverage/stringxref.mjs      # 从指令里重建字符串引用（不信任旧 strings 列）
node tools/mhgu/coverage/seeds-from-xref.mjs # 引用 → 种子（attr-xref.tsv）

```

## 分母修正

`docs/data/functions.csv.gz` 是**区域平铺**（23,885 段），不是函数表：镜像有 **46,087** 个 `push {...,lr}` 前导，28,807 个不是区域起点。这同时让 68,626 个 vtable 槽里的 62,787 个无法归属。重切后 **52,692 个函数**（守卫：BL 目标 23,195 ≈ 23,336、指令和 5,228,277、带字符串函数 1,937、旧起点全保留）。

## 种子真实性：旧 strings 列不可信

- 旧列的字符串是"区域附近出现过"的产物。抽查 `0xf8c`：旧列声称它引用 `AngleLimit`，反汇编显示它是一个纯结构体遍历循环，**没有任何字符串引用**；而 `AngleLimit` 的地址在镜像里**没有任何字指向它**。
- 需要一个字指向字符串地址才算引用：用这个口径重扫，4,461 个旧 token 里只有 **32** 个通过。
- 从指令重建引用（`ldr rD,[pc,#imm]` → rodata 指针；rodata 表 → 表项；`add rD,pc,rX` 偏移）得到 **2,380 个函数 / 4,252 条引用 / 3,214 个不同字符串**，内容包括 `_ZN2nn3ldn…`、`uShellEms101_sp_01`、`weapon\w%02d\%03d`：这是真的引用。

## 到 90% 的剩余量

全部在 tier B（47.1% = 2,462,952 条指令）。可行杠杆，按可验证性排序：

1. **vtable 的 8,360 行 `unknown`**（10.8% 指令）：类名不属于现有 11 条规则（AI、碰撞、资源加载），需要扩充分类规则或按父类继承判定。
2. **逐函数反汇编特征**：立即数、可见字段偏移（`member-offsets.tsv`）、被调函数族——需要新证据，不是传播。

**推断类的第二种验证（整区留出）**：把整个 1MB 区段的标签拿掉后用区外证据预测区内，调用票规则仍有 **95.7%（2,160/2,257 严格版、2,217/2,317 放宽版）**——说明推断类不是证据密度的产物，和摊开标签（同法只有 74.2%）形成对照。这条是评审要求补的对照实验，结论对推断类有利、对摊开类不利。

**摊开标签的真实精度（2026-11-04 二次测量）**：第一次用"留一函数"测得 91.7%（1,198/1,307），看起来合格；但把**整个 1MB 区段**一起留出（区外标签预测区内，更接近摊开标签实际工作的稀疏场景）后只剩 **74.2%（247/333）**。差距说明 91.7% 是被同区段的证据密度抬高的——同一区域内邻居共享证据，跨区就不共享了。因此摊开标签按 **74.2%** 记账，**不计入 ≥90% 覆盖**；此前一度写出的 80.4%/90.3% 两个数都因此作废。

**互斥五分区**（每个函数只算一次，合计 100%）：直接证据 **23.9%** / 仅推断 **36.1%** / 仅签名 **4.0%** / 摊开-已验标签 **12.2%**（合并 96.0%，下界 94.7%）/ 摊开-未验标签 **14.3%** / 完全无标签 **9.6% 指令（24.5% 函数，12,935 个）**。

> **2026-11-04 修的一个报告缺陷**：分区原先只把 `conf==B` 算作摊开标签，tier A 但无直接证据的函数（"spread A"）落进了"无标签"桶——于是"无标签 19.6%"被高估了近一倍。修正后真正的无标签只有 **9.7% 指令**。这个数字以前被引用过，一律以本行为准。。此前报告里的"unattributed 14.6%"是 `total − A − B`，把推断行重复计入了未归属，已改为真分区。

**降级与证据的关系（2026-11-04 修订）**：demote 只压"投票/传播"，不再抹掉直接证据行——旧实现把被降级的函数整个排除在种子之外，导致即使后来有类记录/字符串证据也永远无法恢复。修正后 otomo 降级的 961 行里有 **512 行靠自身证据恢复**（467 行回到 otomo-ot，来源是 `cMonNyan*/sPastOtomo/uUIOtomo*` 类记录 310 + 类身份 87 + 类族 66 + 字符串 4），actor 层的 884 行**一行都没恢复**（它们确实只有传播标签），说明这两批降级的性质不同、处理正确。

**共享 actor/动作层被降级（2026-11-04）**：`0x1120000..0x121ffff` 的 1,955 个函数里 **没有一行直接证据**，884 行是 tier A（全凭两票+地址预测）。独立重扫全镜像的 `movw #0x3328`：724 处站点、530 个函数，其中 453 个就在这一段——同一个 `+0x3328` 内嵌子对象被怪物、玩家、网络三方共用，说明这一段是**角色/动作共享层**而不是怪物模块。据此把该段 884 行 A 降级（`demote-actor-layer.tsv`），tier A 从 58.2% 落到 55.7%，无标签从 9.7% 升到 14.6%：这才是这一段真实的可解释度。

**vtable 越界筛除（2026-11-04）**：槽区间按"连续 in-text 词"读取会越过 vtable 末尾进入相邻 rodata——vtable `0x182e82c` 的 0-9 槽在 `0x125xxxx`，第 10 槽却是 `0xea60`（相距 ~1.2 MB）。因此凡槽目标离本 vtable 中位 ≥256 KB 的行一律筛出，共 60（RTTI 重标）+275（全量扫描）行；这是阈值，不是证明，筛出的行留在 `attr-vtable-ns-suspect.tsv` 与 `attr-vtable-rest.tsv`。

两条独立的 vtable 发现路径（retile 表 vs `vtable-scan.mjs`）在 1,226 个函数上重合，标签零分歧——这是唯一一次真正的双路互证。
tier A 的演进：61.1%（conf=B 也当种子，作废）→ 46.5%（拒收 B）→ 50.1%（+RTTI 重标）→ 59.5%（+全量扫描、+字符串词表）→ 60.7%（+类族接线）→ 58.2%（两票制+未知行回填）→ 55.7%（降级共享 actor 层）→ 57.6%（降级只压传播、不抹证据：有直接证据行的被降级函数重新计入）。每条渠道都要先证明自己的精度，再计入。

**未采用的路线（记录以免重做）**：

- **构造器 vtable 存储（评审建议）**：思路是"构造函数把类 vtable 存进 [obj]/[obj+8]，再拿 vtable 反查类"。实测上限很小：全部证据表加扫描器共有 **6,104 个已知 vtable**（5,531 个带类名），而 .text 里"字面量池取地址 → 4..12 条指令内存入 [obj] 或 [obj+8]"的构造器只有 **17 个**，在 A-direct 上可判定的 5 个里对 2 个（40%），能给无标签函数新增的只有 **1 个**。原因是游戏类大量在运行时装 vtable（\`attr-vtable-retile\` 里 "instance vtable installed by create" 那种），存储的地址不在已知表里——例如样本 \`0xd9a3f4\` 存的 \`0xaac110\` 就不在 6,104 个之中。**不采用**：样本量与收益都不够，记下来免得再试。
- **ldr/str 立即数偏移签名**：与 movw 同法扫 `ldr/str [rX,#imm12]` 的偏移，≥40 个携带者且 ≥99% 同标签时折叠精度只有 **93.9%（108/115）**，低于本项目对单信号通道的 95% 门槛；收紧反而更差（≥80 携带者/99.5% 降到 71.4%，≥120/99% 75.0%），说明剩下的高纯度偏移样本太偏、不能外推。不采用。
- 对剩余 1,015 条 vtable B 行（`attr-vtable-rest.tsv`，类名 `MtFile`/`uShellEm*`/`aQuest` 等）只抽查了 6 个函数的反汇编——它们都是"取单例 + 存 vtable"的构造/注册器，代码本身不暴露子系统，唯一证据就是名字；按名字整族打标会重复 2026-11-03 早间 `Mt` 通配的错误，因此停在 B。要做就逐类做，且每类要有类内证据（注册器字符串、该类独有的成员名集合或该类 vtable 的方法簇）。


## 通道间冲突（2026-11-04 实测）

A-direct 的 13,060 个函数里有 **356 个（2.7%）被两个以上通道给了不同标签**。这不是数字错误，是分类边界本身的模糊，记录在此而不是掩盖：

| 冲突形态 | 数量 | 例子 | 性质 |
|---|---:|---|---|
| UI 壳 vs 主题域 | 148 + 37 | `uUIOtomoArms`：class2/uifamily 判 ui，vtable-fixed 判 otomo-ot | 「獣人装备界面」既是 UI 又是 otomo 数据；`classprefix-map` 的既有约定是主题域优先（`uUISupplyBox`→item），而 `attr-uifamily` 按 uShell→ui |
| 服务器/任务侧 vs 玩家前缀 | 21 | `uPlayerQuest`：xref/registrar 判 quest，prefix 判 player-pl | 玩家在任务中的 actor，两边都说得通 |
| 音频 vs 任务 | 21 | `rSound*` 类被 quest 侧调用 | 需逐函数看，暂无双赢解 |
| 渲染 vs UI | 21 | `uShellPlEffect`：prefix/registrar 判 render-gfx，strings2 判 ui | 玩家特效的 UI 预览 |
| 其余（player-pl/quest、item/ui 等） | 108 | `rKitchenListMenu`（item vs ui） | 同上 |

**处理方式**：`report.mjs` 按通道 rank、再按文件顺序取第一个 A——结果**确定但任意**。所以引用 A-direct 时隐含 ±2.7% 的**标签名**歧义（这 356 个函数「算不算 A」不受影响，它们都有证据）。消歧需要先定一条全局政策（主题域优先 vs 实现层优先），属领域决策，记为 `[U]`。

## 精度实测（2026-11-03，样本 280 行）

对 tier A 抽样 20 行/标签，逐行用函数自身的字节、真正被引用的字符串、被调者身份判定（不看地址、不看 tier 文件）：

| 判定 | 比例 | 含义 |
|---|---:|---|
| 可证实标签正确 | 17.1%（48/280） | 函数本身能证明属于该子系统 |
| 可证实标签错误 | 1.8%（5/280） | 能证明属于另一个子系统 |
| 无证据 | 81.1%（227/280） | 构造函数/thunk/访问器，唯一操作数是 vtable 槽或结构体偏移 |

合并两票（A 120 行 + B 160 行）：可判定 53 行，其中 **48 行正确（90.6%）**、5 行错误。otomo-ot 复现 2026-10-24 的 1/20。

**结论**：tier A 的 48.9% 不能用"正确率"表述。可以说的是"48.9% 的指令具备双预测一致 + 至少一份独立证据支撑的结构位置"，以及"在可判定的样本里 83% 标签正确"。要把"已解释"提高到 90%，必须让更多函数获得**正面证据**（vtable/类/字段/字符串），而不是让传播更远。
