# 覆盖度计量器（2026-11-03 起可复算）

此前 `code-metrics.md` 的 72.8% / 52.2% 来自一次性脚本与 `.tmp` 中间表，重跑不出来。现在整条链路在仓库内，且**种子的真实性被单独验证过**。

## 分母修正

`docs/data/functions.csv.gz` 是**区域平铺**（23,885 段），不是函数表：镜像有 **46,087** 个 `push {...,lr}` 前导，28,807 个不是区域起点。这同时让 68,626 个 vtable 槽里的 62,787 个无法归属。重切后 **52,692 个函数**（守卫：BL 目标 23,195 ≈ 23,336、指令和 5,228,277、带字符串函数 1,937、旧起点全保留）。

## 种子真实性：旧 strings 列不可信

- 旧列的字符串是"区域附近出现过"的产物。抽查 `0xf8c`：旧列声称它引用 `AngleLimit`，反汇编显示它是一个纯结构体遍历循环，**没有任何字符串引用**；而 `AngleLimit` 的地址在镜像里**没有任何字指向它**。
- 需要一个字指向字符串地址才算引用：用这个口径重扫，4,461 个旧 token 里只有 **32** 个通过。
- 从指令重建引用（`ldr rD,[pc,#imm]` → rodata 指针；rodata 表 → 表项；`add rD,pc,rX` 偏移）得到 **2,380 个函数 / 4,252 条引用 / 3,214 个不同字符串**，内容包括 `_ZN2nn3ldn…`、`uShellEms101_sp_01`、`weapon\w%02d\%03d`：这是真的引用。

## 精度实测（2026-11-03，样本 280 行）

对 tier A 抽样 20 行/标签，逐行用函数自身的字节、真正被引用的字符串、被调者身份判定（不看地址、不看 tier 文件）：

| 判定 | 比例 | 含义 |
|---|---:|---|
| 可证实标签正确 | 17.1%（48/280） | 函数本身能证明属于该子系统 |
| 可证实标签错误 | 1.8%（5/280） | 能证明属于另一个子系统 |
| 无证据 | 81.1%（227/280） | 构造函数/thunk/访问器，唯一操作数是 vtable 槽或结构体偏移 |

合并两票（A 120 行 + B 160 行）：可判定 53 行，其中 **48 行正确（90.6%）**、5 行错误。otomo-ot 复现 2026-10-24 的 1/20。

**结论**：tier A 的 48.9% 不能用"正确率"表述。可以说的是"48.9% 的指令具备双预测一致 + 至少一份独立证据支撑的结构位置"，以及"在可判定的样本里 83% 标签正确"。要把"已解释"提高到 90%，必须让更多函数获得**正面证据**（vtable/类/字段/字符串），而不是让传播更远。


## 旧 tierB 抽判本身是残缺的

审计发现旧的 tierB 抽判文件里有 10 处 MISSING：`tierB-slice-05/08/09` 的汇总段是占位符或空表，`tierB2-slice-04/10` 只写到 30/120 与 90/120，`tierB2-slice-09` 写到 60 行就停，`tierB3-slice-13a` 只有 7 行表头。这意味着 `code-metrics.md` 里基于"tierB conf A"的那些数字既不可复算，也不完整——不是口径问题，是数据本身没落完盘。

新的口径不依赖这些文件：`recompute` 从函数表与分类规则重算，证据来自 `attr-*.tsv`（每行都有可引用的依据）。
