## 0. 结论速览

1. 字面量 `0x1108e58` **不是地址，是 pc 相对偏移**。`add r7,pc,r0` 在 `0x5230ac`，`pc=0x5230b4`，故**表基址 = `0x5230b4 + 0x1108e58` = `0x162bf0c`**（在文件映像内，可静态读）。
2. 该表是 **166 项 u16**，不是 137。遍历上界来自 `cmp r6,#332`（字节偏移 0,2,…,330）。
3. 每项编码 `EmId = (variant << 8) | baseId`：低字节 = 基础种编号，高字节 = 变体码（0 原种 / 1 亚种 / 2 稀少种 / 3,5,6 强化个体 / 4 二名）。**`EmId` 与 repo 的 `db_id` 完全同一编号空间**。
4. **表索引 i 不是存档槽号。** i = 怪物主表记录号（0..165）；`0x50b64(EmId)` 才把 EmId 翻成 0..136 的计数器槽号（查不到返回 `-1`）。
5. `cmp r0,#136` 是**计数器数组 137 槽（0..136）** 的边界检查；`-1` 经无符号比较走 `bhi` 被跳过，等价于「查不到就不计」。
6. `0x50b64` 查的是**运行期**建的两张表：搜索表 `0x1a523a4`（137 项 × 8 B，key@+0）、取值 `0x1a52ea4 + idx*8 + 4`。两者都在文件映像末尾 `0x184ae78` 之外（`.bss`）⇒ 镜像里读不到内容；但**其静态源已找到 = `0x1597ea4`**（137 × `{u32 EmId, u32 slot}`，slot 逐项等于行号）。
7. 用 `0x1597ea4` 得到的**真实槽布局**是：**大怪 0..70 + 112..134（94 只），小怪 71..111 + 135..136（43 只）**，共 137，**没有保留槽**。repo 的 `monster-slot-map.json`（93 大 @0..92）+ `monster-slot-map-small.json`（36 小 @93..128）在**槽 71 之后整体错位**（另在 58/61 有一处互换）。
8. 该布局已用两份存档实证（§4.4）：dirty 档在 repo 布局下出现「小怪槽有捕获记录」的**直接违反**，在二进制布局下 0 违反；clean 档的尺寸记录只落在 `0..70`（repo 布局下解释不了 71..92 有讨伐却无尺寸）。

## 4. 与 `obj+0x72C` 的 137 槽对拍

### 4.1 表索引 i **不是**槽号（否定命题）

- 表的遍历是 `i = 0..165`（166 项），而槽区间是 `0..136`（137 项）—— 数量上就对不上。
- `0x52308c` 拿到表项后必须先 `bl 0x50b64` 才能得到数组下标；随后 `mov r0,r0,lsl #1` 再 `ldrh [base, r0]` ⇒ **槽号来自 `0x50b64`，不是来自表索引**。
- 表的内序是「baseId 升序 + 变体」，而槽的内序是「历史追加顺序」（见 4.2），两者不同。

### 4.2 真实 137 槽布局（`0x1597ea4`，slot 逐项 == 行号）

| 区间 | 数量 | 内容 |
|---|---|---|
| `0..70` | 71 | 大怪（按 baseId 升序，变体内联）：Rathian … Great Maccao |
| `71..111` | 41 | 小怪：4097..4144（34 只）+ 4196..4202（7 只，`uEms100..106`） |
| `112..134` | 23 | 余下大怪：Basarios…Ahtal-Ka（含 87=`uEm087_00`） |
| `135..136` | 2 | 大雷光虫(4113)、小桃毛兽(4118) |

## 6. 未知 / 待定

### U1 `0x5230ec` 的 `0xe6f55071` 未定案（不影响本报告的结论）

- 工具解码器渲染为 `ldrb r5,[r5,r1,ror r0]`；按位域：`bits27:25=011`、`bits24:20=0x0f`（P=0,U=1,B=1,W=1,L=1）、`bit4=1`（register shift）、`bits6:5=3`（ROR）、`Rs=r0`、`Rm=r1` ⇒ 即 post-index 且 Rt/Rn 同为 r5，属 UNPREDICTABLE 编码，**语义上不可能是累加**。
- 该字与 `0x523148` / `0x50c3c` / `0x50c48` 的 `e6ff0071` / `e6ff0070` 同族（后者按「halfword extend」位型 = `uxth r0, r1`），但 `e6f55071` 的 op 半字节为 `0x5`，不落在 extend 族的 `0xA/0xB/0xE/0xF` 里。
- 唯一能确定的是：`r5` 是返回值（`0x5230f8 mov r0,r5`），且每轮被写一次 ⇒ 函数输出是 166 个钳制值的某种折叠。注意 `mov r5,#0` 在任何一致的解释下都排除了「把 r5 当基址去解引用」。
- **需要可信反汇编器（capstone / IDA / Ghidra）定案**。本机 venv 无 capstone（脚本已尝试 `import capstone` 并回退到修正版手写解码器）。

### U2 `0x5230d4` 的第二项 `u16@[基址+0x112]`

指令是 `ldrh r1,[r1,r8]`，`r8 = 0x112 = 274`，而 274 = `0x83E - 0x72C` = 捕获数组首地址偏移。即每个命中项加的是 `kills[槽] + u16@[obj+0x83E]`（**同一个值，循环不变量**），而不是 `captures[槽]`。

- 该读法的依据：extra load/store 的 `bit22=0` 为寄存器形式；且若按「立即数 176/184」读，`0x523130` 会得到未对齐的 `#177`（非法），两条指令一起看只有寄存器形式自洽。
- `[INFERENCE]` 该常量项可能是「捕获数总计入」一类设计（或索引 0 被复用为总计）；**语义意图未定**，但机器行为明确。

### U3 `4196..4202` 与 `87` 的名字

DB `monsters` 表只有 129 行，这 8 个 id 无名字。已确证 `uEms100_00` / `uEm087_00`（+ `uEm087_088_ControlUnit`、`uEm087_Rubble`）存在于单元名表，`101..106` 是 id 算术推定。

### U4 运行期表与静态表是否逐字相同

`0x1a523a4` 在 `.bss`，无法静态比对。静态表 `0x1597ea4` 与之在结构、长度、内容（与 repo 前 71 项一致）上完全吻合，判为同一份数据的静态源（`[INFERENCE]`）。
