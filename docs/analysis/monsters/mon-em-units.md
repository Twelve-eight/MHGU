### C2. **`uEm###_00` 没有任何指针数组、没有任何 xref —— 它不是索引表**

`em-units2.out.txt` 的 5 段独立搜索全部为 0：

| 段 | 搜索内容 | 结果 |
|---|---|---|
| B | 全文件 4B 对齐字 == `0x155282E`(uEm019) / `0x15527D4`(uEm001) / `0x15529C8`(uEms001) / `0x15527BF`(cEnemyResourceBroker) / `0x1552BC7`(uEm087_088_RubbleBase) | **0 / 0 / 0 / 0 / 0** |
| C | 任意对齐字落在 `0x1552600..0x1553200` | 87 个目标 / 137 处，**全部指向 `roEm*.cro`，无一指向 `uEm*`** |
| D | id 序列字节模式（BIG 50 项 / SMALL 25 项，u8 与 u16 各一遍）+ 稠密 `1..50`/`0..49` | **0 命中** |
| E | `add rX,pc,#imm`(E28F) 与 `movw/movt` 对指向池内 | **0** |
| G | 所有 `ldr rX,[pc,#imm]` 的**字面量值**落在池内 | **0** |
| F | `crc32("uEm001_00")` 等 | 0（无哈希查表） |

独立复核：同伴 `MonClassMap` 的 `mon-class-map.out.txt` S6 给出
`# monster strings = 201  with xref = 0`，S4 给出 `# runs with monster names = 0`。
两条互不相同的算法得同一结论。

**结论**：`uEm###_00` 是**只读名字字面量（死字符串）**，运行时**不经绝对地址引用**
（该构建无 RTTI `type_info::__name` 指针、无资源名指针数组）。
因此任务书里设想的「索引 k ↔ uEm 名」的表**不存在**：`uEm###_00` 的 k **不是** type id，
**type id 就是名字里那 3 位十进制数本身**（`uEm%03d_00`）。

> 范围限制：以上扫描只覆盖 `main.140`（含 `.text` 与 `main` 的 `.rodata`/`.data`）。
> 同目录下的 `sdk` / `subsdk0` / `rtld` 是**独立模块**，本轮未扫描；如需排除跨模块引用，
> 可对它们跑同一套 `em-units2.py` 的 B/C/E/G 段（把 `FLAT` 换成对应模块）。

### C4. `db_id` 编码：**高字节 = 变体等级，低字节 = 怪物 type id**

对 `mhgu.db.monsters`（129 行）做位分解，并对拍运行时表 `0x162BF0C`：
该表是 `{u8 id; u8 variant}` 的有序数组（`counter-slots.out.txt` G-dump 的
`+0000  01 00 01 01 01 02 01 04 02 00 02 01 02 02 02 04 03 00 03 01 ...`
= `{1,0}{1,1}{1,2}{1,4}{2,0}{2,1}{2,2}{2,4}{3,0}{3,1}{4,0}{4,1}{5,0}{5,1}{5,3}{6,0}`），
按 id 升序排列，且**把 `1303/1323/1343/1351/1042/1056/1069/1081/1084/1085/1090/1103-1107`
等 db_id 原地插在各自基础 id 之后**（例：`1303` 紧跟 `23`，`1042` 紧跟 `18`）。
→ `db_id = (variant << 8) | type_id`。
`variant` 码的**取值**是实测（表中出现 `0,1,2,3,4,5,6`），其**语义**为 `[INFERENCE]`
（由该码落在 db 里的怪物类别归纳）：`0`=通常、`1`=亚种位（MHGU 几乎全空缺）、
`2`=希少種、`3`=特殊個体（旧世代码）、`4`=二名、`5`=激昂/狂击状态/狂爆/浑沌 等「极限个体」、`6`=其它（如 `1549 = {13,6}`）。

**由此大怪 `db_id` 的 67 个基础 type id** 与 db 的对应关系可直接用 `db_id & 0xFF` 取。
小怪则严格 `db_id = 4096 + type_id`（`4097..4144` → `1..17,19..23,25..27,34,35,39..42,44..48`）。

一致性校验（`SELECT class,COUNT(*),MIN(_id),MAX(_id) FROM monsters GROUP BY class`）：
`class 0` = 75 行（`db_id>>8 ∈ {0,1,2,5}`）、`class 1` = 36 行（`>>8 = 16`）、
`class 2` = 18 行（`>>8 = 4`，即全部二名 `1025..1107`）。
75 + 18 = **93 只大怪**，36 只小怪，合计 129 —— 与存档 129 槽完全吻合。

## 空洞与候选原因

### H1. `uEm` 空缺的 7 个 type id（有 db 怪物但无自己的类名）

`2 Rathalos`、`5 Gravios`、`15 Gendrome`、`16 Iodrome`、`34 Giadrome`、`62 Volvidon`、`72 Shagaru Magala`。

**候选原因：它们不拥有独立的行为/单元类，复用「同胞」的资源与代码。**
支持证据链（非单点猜测）：

- `roEm002 / 005 / 015 / 016 / 034 / 062 / 072` 这 7 个资源名 **在 C3 的 137 项中完全不存在**，
  对应槽位全部指向同胞的文件：
  Rathalos 系 槽 3/4/5 → `roEm001`（`k=3/4/5`）；Gravios 槽 72 → `roEm004`（`k=113`，与 Basarios 槽 71 同）；
  Gendrome/Iodrome 槽 12/13 与 Giadrome 槽 81 → `roEm014`（`k=12/13/122`）；
  Shagaru 槽 60 → `roEm071`（`k=60`，与 Gore 槽 59 同）；Volvidon 槽 51 → `roEm060`（`k=51`，无 `roEm062`）。
- 行为上同胞关系成立：Rathalos↔Rathian(1)、Gravios↔Basarios(4)、
  Gendrome/Iodrome/Giadrome↔Velocidrome(14)（三色蓝速龙王系共用骨架与 AI）、
  Volvidon↔Lagombi(61)（同为滚动型牙兽）、Shagaru↔Gore(71)（MH4 起共用模型/动作）。
  这与「无独立单元类 → 无独立资源文件」互为印证。

`[INFERENCE]`：`uEm###_00` 是**每个 em 单元的 C++ 类名**（`uEm087_00::cJointCtrl` /
`uEm087_00::cActCustomExecMonitor` / `uEm087_088_RubbleBase` 这类 `A::B`、`A_B_RubbleBase`
命名只可能是类/嵌套类名，而不是模型名）。缺类名的 7 个 = 无独立单元的复用者。

### H2. em id 空洞（引擎里有 id、但没有 db 怪物）21 个

`6,26,28,29,31,35,39,40,41,48,51,52,53,54,59,64,73,74,75,78,87`

证据：`0x162BF0C` 的 `{u8 id; u8 variant}` 表**对 1..82 连续每个 id 都有 v0 条目**
（见 C4），所以这些 id 在引擎的 em 枚举里是「存在」的；
它们只是没有 `mhgu.db` 行、也没有存档计数器槽。
`87` 例外：它是**实机存在的单元**（有 `roEm087.cro`、有完整类名族），只是不进猎人图鉴。

→ 结论：这些空洞属于**未用于图鉴/任务的 em 定义（遗留或特殊单元）**，不是数据缺失。
`[INFERENCE]`：具体对应哪只未登场怪物（如 MH4G/MHX 未回归者）无法只从二进制确定。

### H3. `uEms` 空缺的 9 个小怪

`8 Melynx`、`10 Genprey`、`11 Ioprey`、`12 Cephalos`、`14 Popo`、`15 Giaprey`、
`20 Hermitaur`、`21 Ceanataur`、`41 Slagtoth`

`[INFERENCE]`（对齐依据：C3 小怪段 `k=71..104` 按小怪 id 升序、允许别名）：与 H1 同理，
这些空缺没有自己的 `uEms` 类，也不存在 `roEms008/010/011/012/014/015/020/021/041`
资源名，槽位改指同胞文件：
8 Melynx → `roEms007`（`k=78`，与 7 Felyne 同）；
10 Genprey / 11 Ioprey / 15 Giaprey → `roEms009`（`k=80/81/85`，与 9 Velociprey 同）；
12 Cephalos → `roEm017`（`k=82`，直接用砂龙王的大怪文件）；
14 Popo → `roEms001`（`k=84`）、41 Slagtoth → `roEms001`（`k=98`）；
20 Hermitaur / 21 Ceanataur → `roEm019`（`k=88/89`，直接用大名盾蟹/镰蟹的大怪文件）。
这与 H1 的规则一致：**先复用同族资源，没有同族才新建文件**。
