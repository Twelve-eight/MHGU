## 0. 结论摘要

1. **`0x163e0c` 是成员#15 的「反序列化函数」，不是 obj 地址**。obj = `*(*(0x1453020))`（GOT 槽两级解引用），由调度器 `0x3e77b0` 在 `0x3e78b8..0x3e78c8` 完成（§1）。
2. 成员#15 = **6 个定长整块顺序 memcpy**，无位域、无逐项小字段：**6,328 + 4,400 + 1,800 + 276 + 13,800 + 1,800 = 28,404 B = `0x6EF4`**，覆盖 **`0x2C6B4..0x335A8`**（§2）。
3. **对既有文档的纠正**：`save-load-path.md §4 row 15` 的「26,604 B，终点 `0x32EA0`」漏掉最后一个**尾调用**块 B6（`0x163ea4: b 0x3df2a8`，size `0x708`）。26,604 正是前 5 块之和。⇒ member#16 起点 `0x32EA0` → **`0x335A8`**，其后的 row 16..19 全部 +1,800（§3）。这与该文档 §8 已记录过的「`0x14b0b0` 漏 1,632 B 尾调用」是同类第二次事故。
4. **「与成员#4 重叠」不成立**：成员#4 文件区 `0x2C0B..0x59AC`、成员#15 `0x2C6B4..0x335A8`，差 `0x263C6`，交集为空；唯一混淆源是成员#4 字段表首字段 `0x2C0B` 与 `0x2C6B4` 差两位数字（§3）。
5. **B1 = 压缩占位块**：`0x2C6B4` 起 **13 B 头 + `78 9C` zlib 流**，解压得 **6,328 B 全零**（`nonzero=0`），clean 与 dirty **逐字节相同**（diff=0/6328）⇒ 存的是"压缩后的空容量"，不是活记录（§4）。
6. **16B / `0x180` FF 段的确切落点**：dirty slot0 里是 **18 个独立 16 B 全 FF 块**（17 个严格落在 `0x2E3E5 + k·0x180` 网格，1 个偏移 +0x30 在 `0x31E95`），首块 **`0x2E3E5` = B2+`0x479` = `obj+0x1D51`**，末块 **止于 `0x31EA5` = B5+`0x25ED` = `obj+0x5805`**；clean slot0 在该网格上 **0 命中**。命中区块 = **B2（自 `+0x479` 起）+ B3（贯穿）+ B5（自 `+0x1AD` 起至 `+0x25ED`）**，**B4 一个都没命中**。它**不是单块内部数组**：在 `0x2F09C`（B2/B3 之间的 `obj+0x2A08` 4 B 指针槽，obj 映射有 4 B 缺口）处网格**不中断**，因此它只可能是按 **char_off** 而非 obj 空间形成的图案（§5）。
   > 主会话口径「污染段属于 B2 前段 + B5 后段」需细化：首块在 **B2 的中段**（+0x479 / 块长 0x1130 = 40 % 处），且中间**完整贯穿 B3**；B4 与 B2 前 0x479 B 均无命中。
7. ⚠ **对「编辑器涂了未使用容量」这条归因的反证**（§6）：同形状的 `16 B`/`0x180` FF 块**也出现在 clean 档**（clean slot1 有 13 块，相位 `0xd5`；clean slot0 另有 50 条 **14 B / 步长 `0x144`(324 B)** 的 FF 块）；而 **dirty slot1 一条都没有**（clean slot1 有 13 条 → dirty slot1 = 0 条）。编辑器只写不擦 ⇒ **能消失的图案不是编辑器写的**。因此这 18 块应判为**游戏自身数据**，而非涂写指纹。

## 4. B1 = 压缩占位块（[已证实]）

```
clean @char 0x2C6B4: 00 00 07 00 00 ff ff fd 00 1d 00 00 00 │ 78 9c ed c1 31 01 00 00 00 c2 a0 f5 4f 6d 0d 0f a0 00 00 00
dirty @char 0x2C6B4: 00 00 07 00 00 ff ff fd 00 1d 00 00 00 │ 78 9c ed c1 31 01 00 00 00 c2 a0 f5 4f 6d 0d 0f a0 00 00 00
```

- `+0x000..+0x00C`（**13 B 头**，两档相同），`+0x00D` 起 `78 9C` = zlib（`0x789C % 31 == 0`，FDICT=0，CM=deflate/CINFO=32K）。
- `inflateSync` 结果（out2 §H）：**输出 6,328 B，`nonzero=0`、`0xFF=0`，全零**；clean 与 dirty 完全一致。
- ⇒ **存档里存的是「13 B 头 + zlib 流」，明文是 6,328 B 零填充**。B1 是**容量/占位 blob**（为"将来填满 6328 B"预留的槽位），不是活记录。
- 两档 `B1 diff = 0/6328`（唯一稳定块）。**稳定 ≠ 可写**：写坏 zlib 流即毁掉该槽位的解压结果。

### 5.2 字节证据（原文摘录）

**首块（`0x2E3E5`）**——dirty 侧 16 B 全 FF，clean 侧同位置是**正常结构化数据**：

```
CLEAN @0x2E3E0: 2b 00 00 39 39 39 39 2c 16 17 49 1b 21 2f 00 00
                60 60 60 01 0c 05 09 00 00 00 00 00 00 00 64 4c   "…dL"
DIRTY @0x2E3E0: 00 f0 cf a8 00 |ff ff ff ff ff ff ff ff ff ff ff| ff ff ff ff ff
                00 00 00 42 00 00 00 42 60 e4 00 00 60 00 00 07     (=32.0f, 32.0f, …)
```
⇒ 起点 `0x2E3E5` 起的 16 B：dirty = `FF×16`；clean = `39 39 2c 16 17 49 1b 21 2f 00 00 60 60 60 01 0c`（**有意义的字节，不是 0**）。这点很重要：clean 侧**不是零**，"涂 FF 覆盖零"的说法在第 1 块上不成立。

**末块（`0x31E95`）**——clean 侧整段全 0：

```
CLEAN @0x31E90: 00 × 32
DIRTY @0x31E90: 00 f0 0f 00 00 |ff ff ff ff ff ff ff ff ff ff ff ff ff ff ff ff| 00 00 00 42 00 00 00 42
```
⇒ 末块是"clean 全 0 / dirty 全 FF"，与首块形态不同（首块 clean 有数据）。

**网格跨缺口不中断**：第 6 块在 `0x2EFE5..0x2EFF5`（B2 末段），第 7 块在 `0x2F165`（B3），两块之间夹着 B2/B3 的文件界 `0x2F09C`；间距仍严格 `0x180` ⇒ 网格与 obj 的 4 B 缺口无关 ⇒ 图案是按**文件偏移**形成的。

### 5.3 读法边界（避免后人踩坑）

1. **`0x2E3E5..0x31EA4` 不是"一整段连续洪水"**：实际是 18 个离散 16 B 块 + 4 处缺格（最大缺口 `0x1B00`，即 `0x30075..0x31B65` 之间整段没有 FF 块）。修正12 的口述把它压成"一串规整 16B 周期段"，会误导后续按连续区间处理。
2. **`0x2E3E5` 只能当"首个可观测差异"**：它是 `dirty=0xFF 且 clean≠0xFF` 的起点，不是结构起点（见 §6 的反证：clean 档里同形状块出现在**别的相位**）。
3. **clean 侧不是全零/全 FF**：clean slot0 在 B2 有 250 个 FF、B5 有 850 个 FF（合法哨兵），所以"FF=污染"是错判据（§6）。

## 6. 归因与风险（含对主会话口径的反证）—— 必读

**主会话口径（记录在案）**：clean 档该网格 0 命中、dirty 17 命中，且 B1 明文全零 ⇒「编辑器把 member#15 的**未使用容量区**涂了 FF」；风险判级**低**（明文本就是 0，涂 FF 只让解压后缓冲非零，可能影响"是否有存档"判断位）。

**本 worker 反证（out2 §D，硬数据）**：同形状的 `16 B / 0x180` FF 块**也存在于 clean 档**，且随存档变化**会消失**：

| 档 / 槽 | `len>=12` FF 游程 | 形状 | 相位 |
|---|---|---|---|
| clean slot0（猎人B 5月） | **50 条** | **14 B**，步长 **`0x144`(324)** | mod 0x180 漂移（`0x11f/0xe3/0xa7/0x6b/0x2f/0x173` 各 2） |
| clean slot1（猎人A 5月） | **13 条** | **16 B**，步长 `0x180` | `0xd5`（`0xd5 × 11`） |
| dirty slot0（猎人B 现档） | **18 条** | **16 B**，步长 `0x180` | `0x65`（`0x65 × 17`） |
| dirty slot1（猎人A 现档） | **0 条** | — | — |
| slot2（空槽，两档皆同） | 0 条 | — | — |

两条决定性推论：
1. **"16 B / 0x180 FF 块"不是 dirty 独有指纹**：clean slot1 有 13 条（相位 `0xd5`）；clean 档还另有一族 **14 B / 324 B 步长**的 FF 块（50 条）。
2. **编辑器只写不擦**：clean slot1 的 13 条在 dirty slot1 里**减少到 0 条**。任何"涂 FF"的写者都不可能把 FF 块**擦掉** ⇒ 这些块是**游戏自己写的易变数据**，不是编辑器涂写。

⇒ **本 worker 的归因结论**：这 18 块属于**成员#15 的正常（易变）内容**，不构成"污染指纹"；`0x2E3E5..0x31EA4` 与"编辑器踩坏"无因果。**不需要修复，也不需要写任何补丁去"清 FF"**（清掉反而会改动游戏自己的合法数据）。

**风险判级**：
| 项 | 级别 | 理由 |
|---|---|---|
| 该段 FF 对存档的破坏性 | **低** | 加载路径是 `0x3df2a8` 纯 memcpy（`0x163e2c/40/64/78/8c/ea4`），无校验、无长度/合法性断言；B1 明文全零说明"容量语义"为主 |
| "编辑器是元凶"这条归因 | **不成立** | §6 反证：clean 档同形状存在、dirty slot1 反而归零 |
| 编辑器对该区做任何写入 | **高** | B2..B6 是变长/易变内容（§7：同角色两档差 9,570 B），没有稳定的"一字段一语义"，任何按偏移的写入都必然改到无关键 |

## 8. 未知 / 待主会话

1. **`0x3cf6d4` / `0x3cf928` 是否消耗流字节**：读侧助手前 48 条是"释放旧子对象图"（`[slot+4]` 计数、`[slot+0xC]` 16 B 记录数组、经 vtable `[+0x34]` 释放后清零），末尾是否再读流未看到。**若消耗，`0x335A8` 还将后移**；当前 28,404 是**下界**（6 次 `0x3df2a8` 是无条件 memcpy，必然消耗）。判定命令：`M.disasm(0x3cf6d4, 120)`。
2. **B2..B6 的语义命名**：只到"变长/易变运行期镜像"这一层（有字符串、浮点、指针簇证据），没有逐记录字段名；要命名需 dump 运行期 obj 对照。
