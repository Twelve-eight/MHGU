## C2 存档路径对尾部零回写（尾部是纯透传字节）

## C4 编辑器回写 = 512 B 差异块写入（扩窗不改写入语义）

`MHGU/editor-src/MHGU存档修改/MainForm.cs:341-355`
```csharp
byte[] array = new byte[821248];
fileStream.Seek(num, SeekOrigin.Begin);
fileStream.Read(array, 0, 821248);            // 写前先重读盘上现状
for (int i = 0; i < 821248; i += 512)
    for (int num2 = 0; num2 < 512; num2++) {
        if (currentHunterBytes[i+num2] != array[i+num2]) {
            fileStream.Seek(num + i, SeekOrigin.Begin);
            fileStream.Write(currentHunterBytes, i, 512);   // 只写有差异的 512B 块
            break;
        }
    }
```
- 内存缓冲在打开存档时**整块**读 1,177,760 B（`MainForm.cs:255` 分配、`:276` 读；切槽 `:730`；导入 `.hnt` `:780`；清槽 `:809/811`），
  尾部本来就在内存里且与盘上一致 ⇒ **不编辑就不产生写入**。
- 扩窗只是把同一段 diff 循环上界从 `821248` 抬到 `1177760`；语义不变。

**⚠ 512 对齐陷阱（必看，否则改完必崩）**：
`821,248 = 1604 × 512` 是 **512 的整数倍**，所以现在的 `i += 512` 循环最后一块恰好齐平。
而 `1,177,760 = 2300 × 512 + 160` —— **不是 512 的整数倍**。
若只把 3 处 `821248` 改成 `1177760`：
- 最后一次迭代 `i = 1,177,600` 会访问 `currentHunterBytes[1,177,600 .. 1,178,111]`，
  但数组长度是 `new byte[1177760]` ⇒ **`IndexOutOfRangeException`（每次保存必抛）**；
- 即便绕过比较，`fileStream.Write(currentHunterBytes, i, 512)` 也会写出 **352 B**：
  越过槽尾 1,177,760，覆盖下一个槽的 36 B 槽头 + 其后 316 B（slot2 则写入文件尾的富余区）。
⇒ 扩窗必须把最后一块**夹紧**：`int n = Math.Min(512, N - i);` 并以 `n` 作比较/写入长度。

## C6 字节级校验字段搜查 —— **0 命中**（主会话实测，脚本 `social/checksum-scan.py`）

扫描口径：对 ~30 个区间（`file_all / file_hdr36 / payload / hunter{0,1,2}` × `all / hdr36 / members /

## C8 填充模式取证（主会话实测 hexdump / `checksum-scan.py` E·F 节）

**a) `0xBD4B1..0xBD722`（0x271 = 625 B）—— 全 `0x10` 填充，判定「预分配未用」**
```
0BD4B1  10 10 10 10 10 10 10 10 10 10 10 10 10 10 10 10
0BD4C1  10 10 …（整段 16B/行 全 0x10）
0BD5A1  10 10 10 10 10 10 10 10 10 10 10 10 10 10 10 10
period p=2 holds for 100.0% of positions
run of bytes in {0x0f,0x10} starting 0xBD4B1 ends at 0xC71BD (len 40204)
8B blocks == 0f10101010101010 (2KB window around 0xBD4B1): 0
```
- 本段是**纯同值填充**（period=1 即成立，脚本从 p=2 起测故报 2/100%）。
- 更宽的 `{0x0f,0x10}` 混排族从 `0xBD4B1` 延伸到 **`0xC71BD`（40,204 B）**；
  在该段的 **2 KB 采样窗口**内**没有任何** 8B 块等于 `0f 10 10 10 10 10 10 10`（0 命中）。
⇒ 覆盖图旧描述「`0f101010` 8B 周期结构（1B tag+3B 值）」是**误读**：真实形态是
**同值/双值填充族**（0x0f、0x10 交替的 padding 模式），不是结构化记录表。
⇒ 判定：**预分配未用区**。

**b) `0x117128` 起 —— 连续 17,681 B 全零，判定「大块空闲/预分配」**
```
contiguous zero run covering 0x117128: 0x117125..0x11B636  len=17681 (0x4511)
bytes before: a0 00 ff 00 | 49 92 24 49 92 24 | 8b 53 c7 3a aa fe c3 f5 | ff 00 | 49 92 24 49 92 24 | 08 43 a7 3a 2d 2a
bytes after : 01 00 03 04 03 0d 00 | 01 02 03 04 05 06 07 08 09 0a 0b 0c | 00 00 …（其后全 0）
tail after run 0x11B636..0x11F8A0 : nonzero=2098 / 17002 (12.3%)
```
- 零段**前**是 `ff 00` + `49 92 24`（= 0b100100100100… 的 3 字节重复**位模式**）交替的填充族，
  中间夹两个 4B 值 `0x3AC7538B`、`0x3AA74308`（[INFERENCE] 时间戳/ID 一类，与本结论无关）。
- 零段**后**是递增序号索引表（`01 00 03 04 03 0d 00 01 02 03 … 0x0b 0x0c`），其后 17,002 B 只有 12.3% 非零。
⇒ 判定：**预分配未用**（17.7 KB 从未被写入），两侧是填充族/索引表，不是"被擦除的数据"。

**c) 综合**：356,512 B 社交区里，"真实内容"集中在 `0xC95A8..0x117125` 的小簇阵与若干定点块；
**填充族（40 KB）+ 零段（17.7 KB + 其他零段）占大头**。这与 C7「两档非零率 56% / 36%、差异 67%」
自洽：两档差异落在"有数据"的那部分，填充部分两档一致 ⇒ 填充区确认是容量预留而非内容。

# 3. 「读入 vs 校验」的判定（任务书第 2 项的核心判断）

游戏对社交区**既没有"读入"，也没有"校验"** —— 它对这块是**完全无感知的字节容器**：

```
system 文件 0x24.. → [整块 fs read 0x4EB898] → payload 缓冲（0x3dfafc 内联：分配→清零→读）
                                                     │
              payload + offset[slot]  ───────────────┘
                     │
                     ├─ 0x3e0db8: memcpy 632B 头 → 0x3e77b0
                     │         └ 18 reader 顺序消耗 0x278..0x3783A（产物进运行时对象）
                     │         └ 指针停在 0x3783A；0x3783A..0x11F8A0 从未被寻址
                     │
                     └─ 保存 0x3e11a8 → 0x3e0ea4：只重写 632B 头 + 成员段；
                               尾部保留缓冲里的原始字节（= 载入时读到的），随整块 0x4EB898 落盘
```

唯一的"判定"是 `payload[4+slot]` 的槽存在标志（`0x3e0980 strb` / `0x3e0ab8 ldrb`），与块内容无关。
**文件头** `0x14` 的 `0x36B2EE74` 这个像 `CRC32/魔数` 的常量**从未被任何代码引用**（C6 反向检验 + 既有
`save-load-path.md` §2），是"存了但不验"的格式戳；`payload[0] = 0xC6`(=198) 同理只是格式版本字，
**读档主路径（`0x3e0db8`/`0x3e77b0`）内没有任何与常量比较的分支**（C1①②）。

# 4. 扩窗的风险账（按严重度排序）

| 风险 | 说明 | 处置 |
|---|---|---|
| **R0 512 对齐必崩**（高，**确定性**） | `1,177,760 % 512 = 160`；裸改上界 → 最后一块越界读 `currentHunterBytes[1,178,111]`（数组长度 1,177,760）⇒ **每次保存必抛 `IndexOutOfRangeException`**；即便绕过，`Write(..., 512)` 也越槽 352 B 覆盖下一槽头 | 最后一块用 `Math.Min(512, N - i)` 夹紧（C4 末段） |
| **R1 数据新鲜度竞态**（中） | 编辑器打开存档时缓存整块；若游戏在编辑器打开期间写过社交区，而用户在尾部做了编辑，diff-write 会按 512 B 块覆盖 → 覆盖游戏新写入的同块数据 | 扩窗时保留"写前重读 + 只写差异块"（现状已如此，`MainForm.cs:343-344`），并**只在用户实际编辑过尾部字段后**才允许写尾部 |
| **R2 子系统语义**（中） | 尾部确有真实数据（char_off 826,281 = 0xC9E69 有合法 zlib 流 `78 9c`；1151 个 17–36 B 小簇）。若有子系统解析它，改坏字节可能让**该功能**（公会名片/配信/画廊）异常或崩溃——但**不影响读档门** | 扩窗只作为"能写"的能力，**先不暴露尾部字段**给 UI；若要暴露，逐块测绘后再开口 |
| **R3 魔数漏改/漂移**（低但会静默） | `821248` 在 `MainForm.cs` 出现 3 处（342 `new byte[]` / 344 `Read` / 345 循环上界），漏改任一处 → 仍是半截窗且不报错 | 提取为常量 `WRITE_WINDOW = 1177760`，三处统一引用 |
| **R4 清槽/导入路径**（低） | `:809/811` 已按 1,177,760 清零/写出——扩窗后与它们**语义对齐**（现状反而是"读满、写半"的不对称） | 扩窗后不一致性消失 |
| R5 校验 | **不存在**（C1–C3、C6、C7） | — |

### 扩窗参考改法（`MainForm.saveCurrentHunter`）

```csharp
private const int HUNTER_SIZE = 1177760;   // 槽长（= .hnt 文件长 / 每个 hunterAdds 跨度的数据长）
private const int WRITE_WINDOW = HUNTER_SIZE;   // 原 821248；扩窗只改这一处

byte[] array = new byte[WRITE_WINDOW];
fileStream.Seek(num, SeekOrigin.Begin);
fileStream.Read(array, 0, WRITE_WINDOW);
for (int i = 0; i < WRITE_WINDOW; i += 512)
{
    int n = Math.Min(512, WRITE_WINDOW - i);   // ← 关键：最后一块 160 B，不能写满 512
    for (int k = 0; k < n; k++)
    {
        if (currentHunterBytes[i + k] != array[i + k])
        {
            fileStream.Seek(num + i, SeekOrigin.Begin);
            fileStream.Write(currentHunterBytes, i, n);
            break;
        }
    }
}
```
配套（可选但推荐）：`num` 为槽基址；`WRITE_WINDOW` 与 `HUNTER_SIZE` 相同后，`Read` 的 `array`
与 `currentHunterBytes` 等长，越界分支彻底消失。

# 5. 需实机验证的步骤（一次即可闭环）

以扩窗后的编辑器对 **slot1（猎人A）** 操作，全程保留 `system` 备份：

1. **备份**：复制 `system` → `system.bak`（或在干净的 `save-snapshots/` 副本上做）。
2. **可逆标记**：在社交区的零段写入 4 字节标记，例如 `char_off 0xC9000`（= 823,296 = **512×1608**，
   恰为一个块的起点；落在 `0xC85A8..0xC95A8` 零间隙内，不触碰任何非零簇；若该 4B 处恰好非零，
   改用该零段内任一 4B 全零位置）写 `EF BE AD DE`。保存。
   - 校验点：编辑器应只写 1 个 512 B 块（可用文件时间戳/`fc /b` 对比确认）。
3. **读档**：yuzu 启动 → 读 slot1。
   - 预期：正常进游戏（角色名/HR/道具/装备全对）⇒ 印证"无硬校验"。
   - 若读档失败/报损坏 ⇒ 结论推翻（概率低，C1/C2/C6/C7 四条独立证据同向）。
4. **功能抽查**：进"设置→公会名片"、随从猫广场、配信/下载界面各转一圈 —— 确认 R2 不成立
   （这些界面若读尾部，标记位于零间隙内不应影响它们）。
5. **回写检验**：在游戏里存一次档，退出 → 用编辑器重读 → 看 `0xC9000` 的 `EF BE AD DE` 是否还在。
   - 仍在 ⇒ 该区纯存储（游戏只透传）；
   - 被改写 ⇒ 该区由游戏活动重建（属于"游戏拥有"的区，编辑器**只应读不应写**）。
6. **复原**：`system.bak` 覆盖回去。

若第 3 步通过、第 5 步显示"游戏会重建该区"，则最终建议是：**技术上可以扩窗（安全），但产品上应
把 ≥0xC8800 定为只读区**——把窗口扩到 1,177,760 只为了"读得到 + 能在必要时落盘"，而不是开放编辑。

# 7. 未知 / 边界（不影响结论）
- **U1** 谁（若有）解析尾部：尾部含合法 zlib 流 ⇒ **确有**子系统消费该区，但该子系统 reader 未定位。
  它是否自带版本/完整性判断未知；只要编辑器不改这些字节就不触发（R2 已按此处置）。
- **U2** literal-pool 形态的 `0xC8800` / `0x11F8A0` 常量未排除（C3 方法边界）。
- **U3** 尾部与"当前活动槽"的联动（工会名片是否只属于某一槽）未验。
- **U4** `0xBD4B1..0xBD722` 所在 `{0f,10}` 填充族（40,204 B）的**边界语义**未定：到底是"整段预留"还是
  "逐槽默认值"，需按 0xC71BD 之后的第一个非填充字节判断；两种解释都不影响「无校验、可扩窗」。同类：
  零段前的 `0x3AC7538B / 0x3AA74308` 两个 4B 值未定性（[INFERENCE] 时间戳/ID）。
- **U5** 前轮 `save-load-path.md` 把整块载入记作 `0x3e08a8`；本次 dump 现场显示
  「分配 0x4EB898 → 清零 → fs read」内联在 `0x3dfafc` 状态机的 `0x3dfb84..0x3dfc00` 段。
  两处说法指向同一行为（整块读），坐标差异以 dump 为准。
