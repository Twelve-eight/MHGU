# 288B 数组族判定（member#4 `obj+0x16C8..0x27A8`，15 槽 / 10 槽落盘）

> ⚠ **坐标勘误（2026-10-23）**：本文的 **`file_off`/char_off 早 0x550**（旧 dump 漏算 `0x51dc40` 两处循环体 840+600B）——**正确值 = 本文值 + 0x550**；**`obj_off` 不受影响**。权威布局以 `member4-file-layout.txt` + `coverage-map.md` 为准。

> ⚠ **本报告分三阶段，结论请直接看 §9（终审）。**
> - §1..§6：仅字节+索引阶段（读法已作废：不是记录表）。
> - §7：反汇编证明是**位图**（`word=bit>>5`、`mask=1<<(bit&31)`），5 组 × 3 个 288B 块。
> - §8：字符串表 + 循环头（`type=44+r9`、`bit=id*4+j`）；§8.4 的“块级副本”读法已作废。
> - **§9（终审）：本族 = `cTrialArts`（狩技）状态位图 —— 5 个实例（记录类码 44..48）× 18 个成员（6 风格 × 3 槽位）× 48B(384bit) = 5 × 864B；每 864B 组被序列化成 3 × 288B，中间那片（`mAirhike[0..2]+mBushi[0..2]`）不落盘。**

坐标系：`vaddr` = NSO 虚拟地址；`char_off` = 猎人块内偏移；`obj` = 成员#4 运行时对象（成员对象 ≠ 文件顺序）。
clean = `20261022-clean-reference/system_CLEAN`（slot1，基址 0x2AC560）；
dirty = `20261022-v6-ready/system`（slot0 猎人B HR198，基址 0x18CC9C）。

证据分级：**[M]** 机器索引/权威表原文（`analysis/movw-index.json`、`quest/member4-file-layout.txt`、`quest/member4-diff.txt`）；

**[I]** 推断；**[X]** 本片取不到（无 exec）。

### 方法与能力边界

本 sub-session 只有 `read/grep/glob/edit/write`，**无 exec**：不能新反汇编、不能 dump 存档。所有指令原文引自库内既有转储，
所有“引用站点全表”来自 `movw-index.json`（全 `.text` 的 `[vaddr, imm16, reg]`，172,431 条；`obj+0x1xxx/0x2xxx` 这类大偏移 ARM32 无法编码进 `ldr/str` 的 imm12，只能由 `movw` 或 `add` 立即数构造 ⇒ 该索引对本族**等价于完整引用集**）。
`read` 支持对 JSON 文件跑 jq 过滤（`?q=[.[]|select(...)]`），因此能对 2.9MB 索引做**定点枚举**（这是能给出“某偏移全 .text 仅 N 处引用”的原因）。

### 2.6 字节层（[B]，每槽仅 64B 头 + 32B 尾可读）

逐槽差分（[M] `member4-diff.txt` 第 70-79 行原文）：

| 槽 | r0 | r1 | r2 | r3 | r4 | r5 | r6 | r7 | r8 | r9 |
|---|---|---|---|---|---|---|---|---|---|---|
| obj | 16C8 | 1908 | 1A28 | 1C68 | 1D88 | 1FC8 | 20E8 | 2328 | 2448 | 2688 |
| diff/288 | 8 | 1 | 42 | 63 | 98 | **162** | **140** | **169** | **153** | **153** |
| FF× | 2 | 0 | 5 | 6 | 1 | 0 | 0 | 0 | 0 | 0 |

1. **强进度相关**：r5..r9 两档差 49%~59%；r0/r1 几乎不变（8/1B）。
2. **clean 低进度档大面积 0**：r0/r1/r2/r8 可见区全 0；r3 唯一非零 `+0x38 = C7 01`（=455）。
3. **dirty 档填到全域**：r5..r9 的头 64B 与尾 32B 同属一类小值密集字节。
4. **字节字母表（本片样本）** = `00 01 02 03 08 0C 10 11 13 20 21 23 30 31 32 33 3C 80 C0 C3`（20 值）；nibble 仅 `0,1,2,3,8,C`；`lane1/lane3` 从不取 1。§7.2 末尾给出位图机制解释。
5. **合法存档里存在指针样/未初始化字节**（raw memory image 证据，偏移按 [B] 原文逐字节数出）：
   - r0(dirty) `+0x00 = FF 01 00 00`（=0x1FF）、`+0x14 = 7D 00 00 00`（=125）
   - r3(clean) `+0x38 = C7 01 00 00`（=455）
   - r3(dirty) `+0x00 = 37 01 40 00`（=0x00400137）；尾 32B 内 10 字节串 `FF DF 3F FD 17 01 93 0A 82 FA` 在 `+0x100..+0x109` 与 `+0x114..+0x11D` 各一次 ⇒ **周期 0x14**
   - r4(dirty) `+0x30 = FF EF CF EC 35 00 20 00`（=0x00200035ECCFEFFF）
   - r2(dirty) `+0x108 = FF 7B 7F E1 37 01 40 00`、`+0x11C = FE 7B 7F 61`
6. 本族 FF× 只有 2/5/6/1 个，且都在上述垃圾串内，与编辑器“连续几十字节 0xFF 洪水”**不同构**；`quest/CURRENT-RULING.md` 也把 288B 族差分列为“正常进度差” ⇒ **本族当前未被编辑器污染**。

## 7. 【已证实·修正】反汇编验证（`analysis/followup-dump.txt`）

本节**推翻** §1/§3/§4 的「记录表 / 6×0x30 子记录 / 2-bit lane 计数器」读法，保留 §2.1/§2.2/§2.3/§2.6 的观测。

### 7.0 一句话修正

> 本族不是「记录数组」，而是**按位寻址的位图（bitmap）**：
> `15 槽 = 5 组 × 3 个状态位图`，`obj+0x16C8+0x360*g`（状态 A）/ `+0x17E8+0x360*g`（状态 M）/ `+0x1908+0x360*g`（状态 B），
> 三者**同 id 空间、同 bit 编号**；A/B 落盘、M 不落盘（运行期派生）。位图单位是 **0x30 = 48B = 384 bit 的 lane**。

### 7.1 决定性证据 A：`0x520B00..0x520BC0` = 「同 bit 写三个状态」的循环体

原文（[D]，`## fam288 0x520B00`）：

```
00520b24: e1a032a6  .word 0xe1a032a6        ; mov r3, r6, lsr #5      ← r3 = bit>>5（字索引）
00520b2c: e3a00e36  mov r0, #864            ; 0x360 = 3 × 288          ← 组步长
00520b30: e2844001  add r4, r4, #1
00520b34: e0227099  mla r2, r9, r0, r7      ; r2 = obj + g*864          (g = r9)
00520b38: e1a0551b  .word 0xe1a0551b        ; [I] 寄存器移位形式，推定为 mask = 1 << (bit&31)
00520b3c: e0822103  add r2, r2, r3, lsl #2  ; + (bit>>5)*4             ← 字节偏移 = 字索引*4
00520b40: e30136c8  movw r3, #0x16c8
00520b44: e7b23003  ldr r3, [r2, r3]        ; 状态 A 的字

00520b5c: e0217099  mla r1, r9, r0, r7      ; 同一组基址

00520b74: 01c22005  biceq r2, r2, r5
00520b78: 11822005  orrne r2, r2, r5
00520b80: e5812000  str r2, [r1, #0]

00520b90: e7b01001  ldr r1, [r0, r1]        ; 状态 B 的字
00520b94: 01c11005  biceq r1, r1, r5
00520b98: 11811005  orrne r1, r1, r5

00520bb4: 1affffa5  bne 0x520a50
00520bb8: e2899001  add r9, r9, #1
00520bbc: e3590005  cmp r9, #5              ; **5 组**
00520bc0: 1affff9f  bne 0x520a44
```

由此**三条硬结论**：
1. **`cmp r9,#5` + `mla r9,#864`** ⇒ 组数 5、组步长 864 = 3×288，与 §2.1 的 `0x16C8 + 0x360*g` 完全一致（不是我先前“排版巧合”的解释）。
2. 三元组 `0x16C8 / 0x17E8 / 0x1908` 是**同一 bit 在三个位图里的同一位置**（同一 `mask`、同一字索引、`biceq`/`orrne` 同一条件）⇒ **三个状态数组**，且中间那个（不落盘的 `0x17E8+0x360g`）**确实被代码读写**。
   ⇒ 这就解释了 §2.2 的“4 个 gap 槽零 movw 引用”：它们不是零引用，而是**用 `mla g*864 + 0x17E8` 一条立即数覆盖全部 5 组**（`0x1B48/0x1EA8/0x2208/0x2568` 无需单独立即数）。
3. 位图寻址是标准 LSB-first：`word = bit>>5`、`byte = word*4`、`mask = 1<<(bit&31)`。**id 空间上界 1536**（= 192B = 4 个 48B lane 的位数）与 `DEVLOG.md` “编辑器从不下写 questId > 1311”同一量级。

### 7.2 决定性证据 B：`0x30` 网格 = 48B / 384bit 的 lane（并解释 §2.4）

### 7.4 `0x6AE4F4` = **误报**（不是本族）

### 7.7 编辑器铁律（更新，比 §5 更硬）

1. **整族禁写**不变。§5 的三条理由（指针样垃圾、编码未解、gap 槽）里“编码未解”已被 §7 解开，但**新增两条更硬的理由**：
2. **必须三状态同步写**：`0x520B00` 的引擎写路径是 `biceq/ornne` 同时作用于 A/M/B；只写 A（或只写 A+B 而 M 不重算）会造出引擎从不产生的状态组合 —— **与任务位域“只写 cleared 不写 seen”卡对话属同一类 bug**。M 不落盘 ⇒ 编辑器无法写 M，也就**无法保证三态一致**。
3. **id 是记录序号（u16），不是 questId 直填**：`ldrh r1,[sp,#48]` 取的是 `0x6aa9b8` 记录迭代器返回的 u16，再 `and #31` 当 bit 号；若将来解锁，必须走同一记录表（类码 50/51/52…）取 id，不能凭 questId 猜。

### 8.2 循环头钉死（1536 / 4 / type = 44+r9 / 终止符）

```
00520a4c: e3a00000  mov r0, #0

00520aac: e3a0201c  mov r2, #28            ; 28 = 0b11100 → 取 id*4 的低 5 位里的 bit2..4
00520ab4: e0021100  and r1, r2, r0, lsl #2 ; (id*4) & 0x1C = 字内 bit 偏移
00520ab8: e1a00100  mov r0, r0, lsl #2     ; r0 = id*4    ← **每 id 4 bit**
00520abc: e58d0018  str r0, [sp, #24]      ; 存「全局 bit 号 = rabbitNo*4」

```

结论：
1. **`type = 44 + r9`，`r9 = 0..4` ⇒ 5 组 = 5 个「记录类型」（类码 44..48）**，不是“5 个状态组”。后续 `0x520BC4/0x520CEC/…` 继续处理 type **50、51、52**（`mov r6,#50/#51/#52` + `mov r7,#3`），⇒ 同一个位图系统按类码**分批**覆盖。
2. **`cmp r0,#1536`（`0x520BB0`）是「最多迭代 1536 条记录」的上限**，不是位图位宽；实际由 `rabbitNo == 0xFFFF` **提前终止**。
3. **内层 `r4 = 0..3`（`cmp r4,#4`）⇒ 每个 id 占 4 个 bit**（`bit = id*4 + j`）。这也解释了 `and #0x1C`（取 `id*4` 的字内偏移）与 `lsr #5`（`bit>>5` → 字索引）。
4. 每状态块的容量仍是 **2304 bit = 288B**，故 `id*4 + 3 < 2304` ⇒ **id ≤ 575**（1536 只是上限，越界会写进相邻块；说明真实数据的 id 远小于 576）。
5. 读侧用 `rabbitRecordNo*4 + r4` 作字索引，从 `[sp,#36] + r9*576` 的 `+0x11CC/+0x128C/+0x134C` 三个数组取“旧值”（`0x520AD4..0x520B0C`），再与本轮要置/清的值做 `and`（`0x520B14/0x520B18` 的 `.word` 组合）⇒ **读旧值→算新值→写 A/M/B** 的三段式。
   （`add r0, r1, r0, lsl #6` 里 `r0 = r9*9`（`0x520AD8: add r0, r9, r9, lsl #3`）⇒ 读侧组步长 = `9*64 = 576`，与写侧组步长 864 不同 ⇒ **读写不是同一数组**，读侧是另一个 base（`[sp,#36]`），本片未证其等于 obj。）

### 8.3 勘误：「三张表」不存在，是同一个全局槽

`0x520BDC: ldr r10, [pc, r0]`（`e79fa000`）的地址是 **pc + r0**，不是 `*(r0)`：

| 分块 | 字面值（pc 补偿加数） | 指令处 pc | 实际加载地址 |
|---|---|---|---|
| type 44..48 之后 | `0x13187A4` | `0x520BE4` | `0x1839388` |
| type 50 | `0x131867C` | `0x520D0C` | `0x1839388` |
| type 51 | `0x1318554` | `0x520E34` | `0x1839388` |

⇒ **三处加载的是同一个全局槽 `0x1839388`**（一个全局对象指针，`ldr r0,[r10,#0]` 取其 vtable/表头后传 `bl 0x6aa9b8`）。
因此 dump 里 `*(0x13187A4)=0xE5900000`、`*(0x131867C)=0xE3061C50`、`*(0x1318554)=0x0A000029` 三值**都是 .text 里的指令字**（`0xE5900000` = `ldr r0,[r0]`），恰好反证“那三个地址在代码段” ⇒ §7.5-Q4 的“每类一张表”**作废**。
正确的下一跳：读 **`*(0x1839388)`** 指向的对象（记录数组/表头）。

### 8.4 「6 个名字 ↔ 15 槽」如何对齐：与 Main 假说的核对

Main 的假说：`mGuild[0..2] ↔ A 组`、`mOld[0..2] ↔ B 组`（即 6 个名字 = 6 个 288B 块中的两组）。

**本报告的核对结果：不采用该假说，理由如下（三条独立算术）**：
1. **尺寸**：6 个名字 × 48B（实测 lane 步长 0x30）= **288B = 恰好一个落盘槽**；若当作“2 组 × 3 块”，每组 3 块 × 288B = 864B，与任何一个可观测单位（槽 288 / 组 864）都对不上“名字数量”。
2. **顺序**：字符串顺序 `mGuild[0],[1],[2], mOld[0],[1],[2]` 与内存顺序 lane0..lane5 同序；若 A/B 是 0x120 相隔的两块，字符串里应出现“块维”的下标（如 `mGuild/ mOld` 各只 1 个名字）而不是连续 3+3。
3. **同类可比**：68B 族实测**每块只有 1 条 384bit lane**（`cmp r4,#384`），其 3 块是 3 个**同 id 空间的状态**；288 族一块有 **6 条 lane**，与 6 个名字一一对应 —— 两族“名字数 = lane 数”自洽。

⇒ **结论**：`mGuild[0..2]`/`mOld[0..2]` 是**同一个 288B 块内的 6 条 lane**；而 A/M/B（`+0x0/+0x120/+0x240`，落盘/不落盘/落盘）是**该 6-lane 结构的 3 份块级拷贝**，其区别（current / scratch / old）**尚未由代码证据确定**。
若 `mOld` 的字面语义（“旧副本”）作用在**块级**，则 B 块 = mOld 副本、A 块 = 当前值 —— 这与 8.1 的 lane 读法冲突，需要 §8.8-#1 的字段描述符表才能终审。**两条读法都保留下，但 lane 读法有 288B 精确算术支撑，优先级更高。**

### 8.5 字节字母表的最终解释（4 bit / id）

§7.2 末尾那条“id 成对 + 2bit 空隙”的解释**作废**，改为：

- `bit = id*4 + j (j=0..3)` ⇒ **每个 nibble = 一个 id 的 4 个 sub-flag**（id 偶数 → 低 nibble，id 奇数 → 高 nibble）。
- 实测 nibble 只取 `0,1,2,3,8,C`（= `0000,0001,0010,0011,1000,1100`）⇒ 一个 id 的 4 个 sub-flag **从不同时出现“低半 + 高半”**，即 (bit0,bit1) 与 (bit2,bit3) 是**两组互斥的 2 bit**。
- 合理解读（[I]）：4 个 sub-flag 实为**两个 2-bit 子字段**（低 2 bit = 一组状态，高 2 bit = 另一组状态），同一 id 只用其中一组；这与“mGuild/mOld 两套语义”呼应，但**未证**。

| 一个 `cTrialArts` | **864B** = 18 × 48 | §9.3 |
| **组数**（类码） | **5**（44..48） | `add r0,r9,#44` + `cmp r9,#5` |

### 9.5 回答 Q2：语义 = **狩技(cTrialArts) × 风格 × 槽位** 的位图，按 rabbit 记录号索引

- 载体：`cTrialArts`（"Trial Arts" = 狩技）。18 个成员名就是 6 个**狩猟スタイル** × 3 个**槽位**。
- 6 个风格名与 MHGU 六风格对照（**[I]，只有 4 个语言上硬对应**）：
  `mGuild`=ギルド ✓ ／ `mAirhike`=エリアル（空中跳）✓ ／ `mBushi`=ブシドー ✓ ／ `mTatsujin`=達人系（?） ／ `mKizuna`=絆系（?） ／ `mOld`=旧来系（ストライカー 最可能，?）
- 索引键：`rabbitNo`（父记录序号，0xFFFF=末）+ `rabbitRecordNo`；`bit = id*4 + j`，`j=0..3` ⇒ **每个 rabbit 记录在每张成员位图里占 4 bit**。
- **这不是“委托完成”位图**：委托三态在 `0x42C/0x52C/0x62C`（`quest/CURRENT-RULING.md`）。本族是**狩技侧的解锁/配置状态**，只是**用 rabbit 记录号当索引**（即“打过哪些委托 → 该委托下可用/已配的狩技槽”）。
- `cTrialArts` 与 `rabbitNo` 同块出现**不是巧合**：它证明两者属同一“试炼/委托记录”结构族（`cTrial*` 系列：cTrialArts / cTrialEquipData / cTrialDataNyanter / cTrialBowBottle…）。
- 中间分片不落盘（`mAirhike`+`mBushi`）⇒ 这两个风格的状态**读档后由游戏重算**（[I]；§7.8-#3 可验证）。

### 9.8 编辑器结论（最终）

1. **整族禁写**（不变）。
2. 位号公式（若要读）：`member = f(风格, 槽位)`，`word = (rabbitNo*4 + j) >> 5`，`mask = 1 << ((rabbitNo*4 + j) & 31)`；`obj = 0x16C8 + 0x360*类码索引 + 0x30*((风格索引*3)+槽位)`。
3. **不要**试图只写落盘分片：分片②（mAirhike/mBushi）由游戏重算，编辑器无法同步 ⇒ 与任务位域同类的一致性风险。
4. 若必须修：整 `cTrialArts`（864B）从干净档移植，且**只**覆盖落盘的 12 个成员（分片①③的两个 288B），不要写分片②。
