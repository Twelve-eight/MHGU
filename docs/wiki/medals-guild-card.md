# 勋章与公会卡片（MHGU / MHXX）

> **本页能查到什么**
> 1. **全部 132 条勋章**的官方简中名称 + 官方原文说明（说明里就写着获得条件），逐条给出 `GC_Medal_chS.gmd` 的字符串索引。
> 2. **计数闭合**：字符串总数 264 = 名称 132 + 说明 132；存档位域 = **132 bit**；6 段宽度 30/25/15/15/15/32 —— 三条互不相干的证据同时落在 132。
> 3. **存档落点**：member#4 的 `obj+0xC28`（A 槽）/ `obj+0xC50`（B 槽），文件偏移 `0x3157..0x3167` / `0x316B..0x317B`，含「必须双写」的硬约束。
> 4. 勋章与公会卡片的关系（界面串、分类提示、获得提示）。

**一句话结论**：勋章是**一个 132 bit 的存档位域**（不是 132 个独立字段），每 bit 对应 `GC_Medal_chS.gmd` 里的一条名称+一条说明；编号只到 **131**，因为 **101 号有「老练/新手」两个变体**（共用一个编号、两条文本）。

**证据等级**（全页统一）：

| 标记 | 含义 | 本页用于 |
|---|---|---|
| `[C]` | romfs 字节 / 主程序代码地址交叉核对 | 264 条字符串的条目数、索引、文本；界面串；位域宽度与写点 |
| `[B]` | 单一字节级来源（存档 dump / 单份分析文档） | 位域 A/B 槽的 clean/dirty 实测形态 |
| `[I]` | 第三方库（mhgu.db）或推断 | 6 组的组名（编辑器标签）；bit 序号 = 文件序的假设 |
| `[U]` | 未知（不作为事实陈述） | 各组「多数/大量」的具体阈值；游戏侧读取者 |

**文本主源**：`romfs/nativeNX/chS/table/GC_Medal_chS.gmd`（26 307 B，`fileHash 0x42d31a32`，`version 0x00010302`，`stringCount 264`，`stringBlockSize 16 778`，`labelBytes 3 176`）；解包产物 `MHGU-private/romfs-extract/gmd/table/GC_Medal_chS.gmd.json`，解包索引 `MHGU-private/romfs-extract/gmd/index.json` 的 `groupName: GC_Medal` 条目。下表的 `i` 列即该 gmd 的字符串序号。

> 注意：`mhgu.db`（MHGenDatabase v2.4.0）**没有勋章表**（38 张表里无 `medal` / `medals`），所以本页不含任何 `[I]` 数值；也没有镜像 wiki 文本覆盖勋章条件，故无 `[W]` 行。

## 2. 存档落点（勋章位域）

| 项 | 值 | 来源 |
|---|---|---|
| 所属对象 | member#4（任务/进度对象） | `docs/save-layout/member4-semantics.md` |
| A 槽（对象内偏移） | `obj+0xC28` | `[B]` `fam-small.md` §4.3 坐标证据 |

| B 槽（对象内偏移） | `obj+0xC50` | `[B]` `fam-small.md` §4.3 |

| clean 档形态 | A 与 B **逐字节相同**：`00 40 00 40 01 60 10 00 14 00 02 04 21 00 …`（popcount 12） | `[B]` `fam-small.md` §4.2(3) |
| dirty 档形态 | A = `ff×16 0f`（popcount 132）；B = 32 bit（编辑器只写了 A 槽） | `[B]` 同上 |
| 编辑器写点 | `OtherForm.cs:231-266` → char_off `12631..12647`（只覆盖 A 槽） | `[B]` `fam-small.md` §4.3/§4.5 |
| 写侧硬约束 | **A/B 必须同值双写**，只置位不清位（OR 语义）；只写 A 会制造「A 满/B 旧」的非法中间态，可能被回灌覆盖 | `[B]` `fam-small.md` §4.5 处置建议 1 |

- 该字段**不是**「132 个独立布尔字段」，而是一块 132 位的打包位图：改勋章 = 位操作，整块覆盖写会连带清掉其它勋章 `[B]`。
- **游戏侧写入者已定位**（§2.1）：授予路径 `0x3EC018` 一族对 `+0xC28` / `+0xC50` 做同值 OR 写。**游戏侧读取者仍未找到**：唯一候选 `0x295D84` 已被证伪为「把 `0xC27/0xC28` 当 flag id 传参」（同函数还有 questId `0x3ED`），`0xC28` 的 consumer 为空；存档 I/O `0x51D344`(writer) / `0x51DE5C`(reader) 只负责搬运 `[B]`（`fam-small.md` §8.4b）。哪一槽是游戏读取的那份 `[U]`。
- 反向结论：**勋章位域与狩技解锁无耦合**（狩技的「村贡献度 400」「村民的委托 5 回」是另一个计数器）；改勋章不会解锁狩技，改狩技记录也不会点亮勋章 `[B]`（`docs/wiki/styles-arts.md` §2.2 四条解锁轨 + §3 共通狩技末注「4 条『村民的委托 5 回』…与『村贡献度 400』是**不同的计数器**」；`docs/mechanics/systems.md`:896-898 把特殊许可 `0x42C/0x52C/0x62C` 与勋章 `0xC28` 列为两个独立字段）。
- 与 128 B 记录族、特殊许可（228 个 questId 在 `0x42C/0x52C/0x62C`）**互不相交** `[B]`（`docs/analysis/fields/records-128.md` §4.1 判定表；同页 §1 是该族的几何布局）。

### 2.1 授予机制与阈值（游戏侧写入者）

本节回答「哪段代码把勋章位置上」。地址为主程序 vaddr（flat − 0x100）。

- **授予入口**：更新函数 `0x3EA6E8`，由流程步函数 `0x38669C` 内的 `0x3866B4` 调用，**每个流程步评估一次，不是每帧** `[C]`。
- **写入点**：某枚勋章的条件满足且该位尚未置位时，`0x3EC018` 一族的求值块执行三次 OR 写 `[+0xC3C] |= bit`、`[+0xC50] |= bit`、`[+0xC28] |= bit`，随后 `bl 0x1630C4(ui, 勋章号)` 发出获得通知 `[C]`。只有置位，没有清位路径，与 §12 的 OR 语义一致。
- **落盘关系**：`+0xC28`（A 槽）与 `+0xC50`（B 槽）由 member#4 存档 I/O（写 `0x51D344`、读 `0x51DE5C`）搬运；`+0xC3C` 是运行期中间副本，不落盘 `[C]`。
- **位与编号的对应**：0 基索引 i 的勋章 ↔ bit i，即编号 = i+1。代码侧已在 idx 57 ↔ bit 26（门控 `tst r1,#0x2000000`）与 idx 59 ↔ bit 27（门控为任务 0x27F 通关）两处核对接缝 `[C]`。
- **通知点覆盖**：共 131 个不同编号有 `mov r1,#idx; bl 0x1630C4` 通知点。idx 58（编号 59）未找到通知点，原因 `[U]`。

### 8.1 101 号为什么有两个版本

- `Medal_101_1` 的说明是**格式化串**（逐字引用，`\r\n` 不折）：`游戏时间：%d小时%02d分\r\nHR：%s\r\nMONSTER HUNTER GENERATIONS的记录` —— 它显示的是**从 MHX（Generations）继承过来的游玩时间与 HR**，即「老练猎人证明」`[C]`。
- `Medal_101_2`「欢迎来到贝鲁纳村！这是你踏上猎人之旅的第一步。」= MHGU 新开档的第一步，即「新手猎人证明」`[C]`。
- 独立佐证：继承说明串 `TitleMsg_chS` → `Convert_Attention_003`「无法继承以下内容：… ･游玩时间 ※**会作为勋章保留**。…」、`Convert_Attention_005`「以下内容仅能继承一部分：… ･HR ※**会作为勋章保留**。…」——与 `Medal_TXT_101_1` 的两栏 `%d小时%02d分` / `HR：%s` 完全对应 `[C]`。
- 因此 **101 只有一个编号、两条互斥的文本**：新档只会看到一条。至于是「两条文本共用 1 bit」还是「占 2 bit、只置 1 位」，位序未在代码侧验证 ⇒ `[U]`（本页按「132 条目 ↔ 132 bit」并列展示）。

### 8.2 G6 结构（32 = 2 + 1 + 3 + 1 + 1 + 1 + 3 + 3 + 2 + 2 + 6 + 7）

变体勋章（101）→ 天彗龙（102）→ 龙识船剧情三件（103 队长之信 / 104 梅尔西 / 105 老山龙迎击）→ 阁螳螂（106）→ 酒吧老板恩怨（107）→ 黑龙（108）→ 村★7 / ★8 / ★9–10（109–111）→ **G★1–2 / G★3 / G★4**（112–114）→ 小/大**大师**皇冠（115–116）→ 斗技 A 全清 / S 全清（117–118）→ **MHXX 新增 6 只二名**（119–124）→ 全二名霸纹（125）→ 无人山岭（126）→ 武器全种类究极强化（127）→ 随从全倾向满级（128）→ 猎人活动备忘录全清（129）→ 全食材（130）→ 宠物服装收藏（131）`[C]`。

- **二名勋章合计 18 枚**：X 代 12（16–27，在 G1）+ XX 新增 6（119–124，在 G6）`[C]`；两个「霸纹」分别对应「全清主猎」与「全二名」（7 / 125）。
- 4 号／112 号是**同一套「红铜/白银/黄金」命名**，但分属上下位与 G 级（4–6 vs 112–114），不要混为一谈 `[C]`。
- 皇冠也是两套：8/9 是「小皇冠/大皇冠」（狩猎许多），115/116 是「小型/大型**大师**皇冠」（狩猎更多）`[C]`。

## 9. 「多数 / 大量 / 所有」的口径

- 官方勋章说明本身**不给数字**，只给量词：`所有`（全部）、`多数`、`绝大部分`、`许多`、`大量`、`部分`、`更多` `[C]`。
- 同一批评定条件在**称号（`GC_Title_1_chS.gmd`，2 618 条）**里被写得更明确，可用来校准量词 `[C]`（称号与勋章是两套不同的奖励，不可互相替代）：

| 勋章 | 勋章说明用词 | 同条件的称号原文（`GC_Title_1_chS`） |
|---|---|---|
| 4 红铜纪念章 | 集会所内**所有**★1～★3 | `name1_TXT_128`「完成了集会所所有的★1、★2与★3任务」 |
| 5 白银纪念章 | 集会所内**多数**★4与★5 | `name1_TXT_129`「完成了集会所大部分的★4与★5任务」 |
| 6 黄金纪念章 | 集会所内**多数**★6与★7 | `name1_TXT_130`「完成了集会所大部分的★6与★7任务」 |
| 7 天地狩猎的霸纹 | **绝大部分**（村★1–6 + 集★1–7） | `name1_TXT_131`「完成除少数任务以外村庄★1到★6与集会所★1到★7的所有任务（除训练任务和斗技大会）」 |
| 1/2/3 村长三件 | 本村**所有**★1–2 / ★3–4 / ★5–6 | `name1_TXT_125/126/127`「完成了村庄所有的★1与★2 / ★3与★4 / ★5与★6任务」 |
| 11/12/13 三盾 | 斗技**多数**（无/A/S） | `name1_TXT_122/123/124`「以B/A/S级…完成了斗技大会的大部分任务」 |
| 112/113/114 G 级勋章 | 集会所**所有**G★1–2 / G★3 / G★4 | `RabbitName1_TXT_13/14/15`「完成了集会所所有的G★1和G★2 / G★3 / G★4任务」 |

- 注意 11 号（碧玉之盾）在勋章里没有明确等级要求，而称号侧对应的最低档是 **B 级**（`name1_TXT_122`）`[C]`；这解释了「碧玉 → 苍玉(A) → 金阳(S)」的阶梯 `[I]`。
- **具体阈值（多少头、多少种、多少 %）全部 `[U]`**：不在 `GC_Medal` 文本里，`mhgu.db` 无勋章表，镜像 wiki 文本也未覆盖。可间接对齐的只有相邻系统：捕获数、狞猛讨伐数、斗技评价、食材收集数各自另有存档计数器（例如怪物讨伐/捕获/尺寸在 `0x5EA2..0x62EE`，见 `docs/mechanics/systems.md`）。

## 10. 与公会卡片的关系

勋章页是**公会卡片的一个分页**，不是独立菜单：

| `GuildCardMsg.Medal`（i=165） | 勋章 | `[C]` |

| `GuildCardMsg.Medal_Information_1`（i=169） | 选择大勋章后将按类别打开勋章列表。 | `[C]` |
| `GuildCardMsg.AllMedal`（i=58） | 【获得 '%s' 的全部勋章！】 | `[C]` |

| `DialogMsg.New_Medal_001`（i=29） | 获得了新的勋章！ | `[C]` |
| `GuildCardMsg` 其余分页 | 怪物狩猎记录 / 斗技大会记录 / 称号 / 自我介绍 / 姿势显示 / 背景 / 登记装备 | `[C]` |

- `AllMedal` 的 `%s` 是**类别名**（「获得『某类别』的全部勋章！」）——这进一步说明列表确实按类别分组；但类别名的字符串来源 `[U]`（见 §1.1）。

- 公会卡片本身的存档字段（卡片文本、友好度、登记装备、狩猎记录明细）未在 `docs/` 里测绘完整 ⇒ `[U]`；已知的怪物狩猎记录数值区段见 `docs/mechanics/systems.md`。

## 11. 未知与待确认

1. **bit 序号**：本页 `bit` 列按「文件序 = 位序」标注，属假设 `[I]`。clean 档实体 `00 40 00 40 01 60 10 00 14 00 02 04 21 00 …` 按 LSB-first 解出 12 位（bit 14、30、32、45、46、52、66、68、81、90、96、101），分布为 G1 1 / G2 5 / G3 2 / G4 1 / G5 2 / G6 1，12 位全部落在各自分段宽度之内；但这只是单份样本的**自洽性**，没有逐位对照实验 `[U]`。
2. **101 号占 1 bit 还是 2 bit** `[U]`（见 §8.1）。
3. **游戏侧读取者**：写入者已定位（§2.1）；读取 A 还是 B 的消费点仍未找到 `[U]`。`0x295D84` 已证伪为传参（`fam-small.md` §8.4b）。
4. **各条件的精确阈值** `[U]`（§9）。
5. **6 个类别在游戏内的显示名** `[U]`（编辑器标签只能作 `[I]`）。
6. **完成度 % 与勋章数的关系** `[U]`。
7. **B 槽 `0x316B` 落在布局漂移窗口内**：`docs/save-layout/coverage-map.md`:298 记录 `0x3157..0x5EA2` 之间存在 4 B 漂移（`0x3157` 之前的行已验证）；A 槽 `0x3157` 是已验证探针，B 槽 `0x316B` 处于尚未夹逼的区间。三份文档（`fam-small.md` §4.3/§4.5、`member4-semantics.md` 行 34、`editor-spec/03-quests-monsters-palico.md` 行 141）一致给出 `0x316B`，且 20 B 槽算术精确闭合（`0x3157+20=0x316B`、`0x316B+20=0x317F`=下一字段 `0xC64`），故风险小但非零 `[B]/[U]`。

## 12. 写改勋章时的注意事项（给存档编辑器）

1. **只置位、不清位**（OR 语义），否则会连带抹掉别的勋章。
2. **A/B 双写**：A = `0x3157..0x3167`、B = `0x316B..0x317B`（各 17 B，末字节只取低 4 位），两槽写同一份 132 bit 掩码 `[B]`。
3. **不要整段涂 `FF`**：`0xC14`/`0xC50` 这类 B 槽被涂满会反转 A⊇B 关系 `[B]`。
4. 两个 20 B 槽各自末尾的 3 B 是空位（A：`0x3168..0x316A`；B：`0x317C..0x317E`），改勋章时不要动 `[B]`。
5. 未找到游戏侧读取者前，「改完不生效」无法排除；判 A/B 方向最便宜的办法是只改 A 观察勋章页、再双写对比 `[B]`。
